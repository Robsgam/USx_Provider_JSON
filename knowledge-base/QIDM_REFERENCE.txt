SECTION 1 -- QIDM PROPERTY REFERENCE
================================================================================

  Full Configuration Structure:
  {
    "version": 1,
    "name": "<PROVIDER>_<QueryName>",
    "description": "Mapping for <QueryName> in <PROVIDER>",
    "type": "QUERYINPUTDATAMAPPING",
    "provider": "<PROVIDER>",
    "providerType": "Commsys",
    "query": "<QueryName>",
    "queryLabel": "<Display Label>",
    "targetEntity": "<Entity>",
    "autoSelect": true,
    "order": 3,
    "queriesToDeselect": ["<OtherQueryName>"],
    "handlerFunction": "CommsysTransactionRequestHandler",
    "attributes": [...],
    "combinations": [...],
    "behaviors": []
  }

  -----------------------------------------------------------------------
  Identity & Versioning
  -----------------------------------------------------------------------
    name          String  REQUIRED  Unique name. Convention: {PROVIDER}_{QueryName}
    version       Integer REQUIRED  Starts at 1, increments on each update
    description   String  optional  Human-readable description
    type          String  REQUIRED  Always 'QUERYINPUTDATAMAPPING'

  -----------------------------------------------------------------------
  Provider & Query Identification
  -----------------------------------------------------------------------
    provider      String  REQUIRED  Must match the name used in the Bundle
    providerType  String  optional  Technology type. Currently supported: 'Commsys'
    query         String  REQUIRED  Internal query name. Matches the form submission
    queryLabel    String  optional  Display label shown in UI. Falls back to query value
    targetEntity  String  REQUIRED  'Person','Vehicle','Gun','Boat','Article'

  -----------------------------------------------------------------------
  UI / Behavior Metadata
  -----------------------------------------------------------------------
    autoSelect    Boolean optional  Whether query checkbox is pre-checked when search
                                    form loads. Defaults to true if omitted.
                                    NOTE: This controls the UI checkbox state, NOT
                                    combo evaluation. set[]/any[] control firing.
    order         Integer optional  Display order within provider group. Lower = first.
    queriesToDeselect  List<String>  optional  Queries to deselect when this one is
                                    selected. Enforces mutual exclusivity (e.g.,
                                    selecting DL deselects DH).

  -----------------------------------------------------------------------
  Request Processing
  -----------------------------------------------------------------------
    handlerFunction  String  REQUIRED  Handler that builds the outgoing message.
                     'CommsysTransactionRequestHandler'      -- Commsys providers
                     'RecordsArchiveRestPayloadHandler'      -- REST-based providers
    behaviors        List    optional  Additional behavioral rules. Currently not
                                       used -- set to empty array [].

  -----------------------------------------------------------------------
  Attribute Properties (elements of the attributes[] array)
  -----------------------------------------------------------------------
    name          String  REQUIRED  Identifier; used in combination primaryFieldReference
    sourceField   List<String>  REQUIRED  Keys from user input map (usually 1 element)
    targetField   String  REQUIRED  Field name in provider's request format
    size          Integer optional  Max character length (truncation/validation)
    rule          Object  optional  Transformation rule. See RULE_HANDLERS.txt
    codeTypeProvider  String  optional  'NIBRS' -- required for sex code fields

    For full attribute handler reference: knowledge-base/RULE_HANDLERS.txt

  PROPERTY NAME RULE: Use 'keyReference' not 'keyRef' on QIDM combinations.
    Wrong property name causes silent null, then import rejection.

SECTION 2 -- COMBINATION BASICS
================================================================================

  Read combination rules from XML first, then PDF.
  MetaData XML is the build authority. DevDoc/PDF is secondary reference only.

  Full combination structure:
  {
    "keyReference": "<unique key>",
    "primaryFieldReference": "<attribute name>",
    "state": "In/Out",
    "requirements": {
      "set": ["field1", "field2"],
      "any": ["field3", "field4"],
      "conditions": [...],       // optional -- see SECTION 2a
      "defaults": [...]          // optional -- see SECTION 2b
    }
  }

  Every combination needs:
    keyReference          -- unique per QIDM (import error if duplicated)
    primaryFieldReference -- attribute name (NOT sourceField name) of the primary field
    state                 -- direction of validity:
                              'In'     = input validation only (user -> provider)
                              'Out'    = output validation only (provider -> user)
                              'In/Out' = both directions (standard for most combos)
    requirements.set[]    -- required fields; ALL must be present to match
    requirements.any[]    -- optional fields; accepted but not required

  set[] and any[] reference QIDM attribute names when those attributes have a
  1:1 sourceField. When an attribute has multiple sourceFields (composite fields
  like Name), set[] and any[] reference the individual sourceField values directly.

  Example:
    Attribute: Name, sourceField=@('NameFirst','NameLast','NameMiddle','NameSuffix')
    Combination set: @('NameLast','NameFirst')   <- sourceField names
    primaryFieldReference: 'Name'                <- attribute name

  set[] fields: M (mandatory) per XML -> always in set[], never in any[]
  any[] fields: O (optional) per XML -> in any[]
  Conditional (C) fields: in set[] of the combination that requires them

  LIMITATION #21: Duplicate keyReference rejected at import
    Confirmed: NJ v3.12, NY v1.13
    Error: "Duplicate key references found in query input data mapping."
    Rule: Each combination within a single QIDM must have a distinct keyReference.
    Fix: Use invented distinct keyRef (e.g., DALL + DALH). Provider routes by field
      content in the XML, not by keyRef. keyRef is platform-internal only.
    Confirmed working: NY v1.19 (invented DALH accepted, both paths fire correctly).
    See also: AP #5 (anti-pattern: duplicate keyReference in one QIDM).

SECTION 2a -- CONDITIONS (Advanced Field Constraints)
================================================================================

  Conditions are extra validation rules applied AFTER set[]/any[] are satisfied.
  All conditions in the list must pass (AND logic). They restrict which combos
  apply based on field VALUES, not just field presence.

  Each condition object:
    operator    String        REQUIRED  The type of check (see table below)
    field       List<String>  REQUIRED  Field(s) the condition applies to
    value       List<String>  depends   Value(s) to compare against

  -----------------------------------------------------------------------
  Available Operators
  -----------------------------------------------------------------------

  Operator      Description                              value required  Backend
  ------------- ---------------------------------------- --------------- -------
  EQUALS        Field value must equal value[0]           Yes (1 value)   Yes
                (case-insensitive)
  NOT_EQUALS    Field value must NOT equal value[0]       Yes (1 value)   Yes
                (case-insensitive)
  IN            Field value must be one of value[]        Yes (1+)        Yes
                (case-insensitive). "null" literal
                matches absent field.
  NOT_IN        Field value must NOT be any of value[]    Yes (1+)        Yes
                (case-insensitive)
  REGEX         Field value must match the full regex     Yes (1 pattern) Yes
                pattern (Pattern.matches)
  EXISTS        Field must have a non-blank value         No              Yes
                (not null, not empty, not whitespace)
  NOT_EXISTS    Field must be absent, null, or blank      No              Yes
  EXCLUSIVE     Only ONE of the listed fields may have    No              NO
                a value at the same time. Enforced by                     (UI only)
                the frontend ONLY -- backend always
                passes this check.

  -----------------------------------------------------------------------
  Condition Examples
  -----------------------------------------------------------------------

  State routing (in-state vs OOS):
    { "field": ["State"], "operator": "EQUALS", "value": ["CA"] }
    -> Valid only if State is exactly "CA".

    { "field": ["RegistrationState"], "operator": "NOT_EQUALS", "value": ["CA"] }
    -> Valid only if RegistrationState is anything other than "CA".

  PurposeCode filtering:
    { "field": ["PurposeCode"], "operator": "IN", "value": ["C", "I", "null"] }
    -> Valid if PurposeCode is "C", "I", or absent ("null" = no value).

    { "field": ["PurposeCode"], "operator": "NOT_IN", "value": ["X", "Y"] }
    -> Valid if PurposeCode is not "X" or "Y".

  ORI format validation:
    { "field": ["ORI"], "operator": "REGEX", "value": ["^[A-Za-z]{2}[A-Za-z0-9]{7}$"] }
    -> Valid if ORI matches 2 letters + 7 alphanumeric.

  Field presence:
    { "field": ["LicensePlateNumber"], "operator": "EXISTS" }
    -> Valid only if LicensePlateNumber is present and non-blank.

    { "field": ["MiddleName"], "operator": "NOT_EXISTS" }
    -> Valid only if MiddleName is absent or blank.

  Mutual exclusion (UI only):
    { "operator": "EXCLUSIVE", "field": ["BirthDate", "Age"] }
    -> User cannot provide both BirthDate and Age. UI-enforced only.

  -----------------------------------------------------------------------
  Build Implications
  -----------------------------------------------------------------------

  Conditions enable combo routing by VALUE without splitting QIDMs:
    - In-state vs OOS: use EQUALS/NOT_EQUALS on State/RegistrationState
    - PurposeCode routing: use IN with allowed purpose codes
    - These are server-side enforced (except EXCLUSIVE) -- they work.
    - CA providers use conditions for RegistrationState + PurposeCode routing.

  When building: if MetaData XML shows the same keyRef with different state
  routing, conditions may already exist in the metadata. Check before inventing
  separate combos.

SECTION 2b -- DEFAULTS (Default Field Values)
================================================================================

  Defaults allow a combination to inject a value for a field when the user has
  not provided it. Applied server-side before sending the request to the provider.

  Rules:
    - The field set as a default MUST also appear in any[] (it's optional)
    - The default is applied only if the field is NOT in the user's input
    - Explicit user values always take precedence
    - Type: List of { "field": "<name>", "value": "<default>" }

  Example:
  {
    "requirements": {
      "set": ["LicensePlateNumber"],
      "any": ["LicensePlateTypeCode"],
      "defaults": [
        { "field": "LicensePlateTypeCode", "value": "PC" }
      ]
    }
  }
  If user does not provide LicensePlateTypeCode, the system injects "PC".

  -----------------------------------------------------------------------
  Build Implications
  -----------------------------------------------------------------------

  - defaults are SERVER-SIDE. Different from QIF initialValue (UI-side).
  - QIF initialValue: sets the form field default that the user sees and can change.
    Platform combo evaluator IGNORES initialValue for set[] (LIMITATION #31).
  - QIDM defaults: injected by the server AFTER combo validation passes.
    The server sends the default to the provider even if the user didn't touch it.
  - Both mechanisms can coexist: initialValue shows "PC" in the dropdown,
    defaults injects "PC" server-side if the user somehow clears it.
  - For our builds: PlateType=PC uses QIF initialValue (visible to user).
    QIDM defaults are used by some CA metadata combos for PurposeCode routing.
  - CRITICAL FOR CAD: CAD dispatch does NOT apply QIF initialValues. Any
    field in any[] with a form initialValue MUST also have a combo default.
    Without it, CAD-dispatched queries omit the field entirely from XML.
    See BUILD_RULES.txt Section 12 for the complete rule and field list.

SECTION 3 -- COMBINATION ROUTING
================================================================================

  The first combination whose set[] fields are ALL present fires.
  Order matters -- put the most specific combination first.
  When the first combination fires: ALL populated attributes in the QIDM are sent
    (not just set[] + any[] fields). Extra fields are ignored by the server.

  LIMITATION #3: First matching combination fires; all populated fields sent.
    Put most-specific combination first in the array.

  Example order (Vehicle merged QIDM):
    1. RVIN (VehicleIdentificationNumber + RegistrationStateOOS) -- most specific
    2. RCAR (VehicleIdentificationNumber only) -- less specific
    3. RVEH (licensePlateNumber) -- plate only, fires last
  If RVIN were listed after RCAR, entering VIN+State would fire RCAR instead of RVIN.

SECTION 4 -- MERGE VS. SPLIT DECISION
================================================================================

  ALWAYS check this decision tree before creating split configs or merging.

  STEP 1: Is LIMITATION #2 a risk?
    Is any other QIDM targeting the same (targetEntity, query) pair?
    -> NO: safe to create a second QIDM; LIMITATION #2 does not apply.
    -> YES: must resolve (see steps below).

    LIMITATION #2: Platform evaluates only ONE QUERYINPUTDATAMAPPING per
      (targetEntity, query) pair. Multiple QIDMs sharing the same
      targetEntity+query -- only one is evaluated. The others are silently
      ignored regardless of autoSelect setting.

  STEP 2: Can you merge?
    Check all keyReferences across both QIDMs.
    -> All keyRefs are DISTINCT: merge into one QIDM. Done.
      Example: NY VehicleRegistrationQuery (RVEH+RCAR in _NY, RVEH+RVIN in _OOS)
               -> After merge: RVEH, RCAR, RVIN all unique. (NY v1.11)
    -> Some keyRefs DUPLICATE: cannot merge (platform rejects duplicate keyRefs).
      Go to STEP 3.

  STEP 3: Duplicate keyRefs -- alternative paths?
    a) Separate MetaData transaction: does the provider XML define a separate
       transaction for the second path with a different query name?
       -> YES: use that transaction. Different query name = different
         (targetEntity, query) pair. LIMITATION #2 does not apply.
         Example: NY DL Name path uses NyNyspinDriverLicenseNameQuery (keyRef=DGRP).
         Different from DriverLicenseQuery/DLIC.
       -> NO: go to (b).
    b) Invent a distinct keyRef for the second combination
       (CONFIRMED v1.19, 2026-04-15):
       keyRef is a PLATFORM-INTERNAL identifier only. The provider (NYSPIN, NJCJIS,
       etc.) does NOT receive or validate keyRef -- it routes by XML field content.
       Use any 4-letter code that is unique within the QIDM.
       Example: DALL (OLN) + DALH (Name).
       Both combinations in the SAME QIDM; distinct keyRefs pass import.
       autoSelect=true works (single QIDM -- no LIMITATION #2 interference).
       CONFIRMED: NY_NYSPIN v1.19 -- DALL/DALH both fire correctly; NYSPIN routes
         by content.
       Note: empty element side effect -- LIMITATION #1 sends all attributes when
         any combination fires. If OLN fires, Name attribute becomes empty <Name/>
         element. Servers tested so far accept empty elements. Monitor per-provider.
    c) DH-suffix fieldId pattern (FL_FCIC): give the second path unique form field
       IDs (NameFirstDH, NameLastDH, BirthDateDH, etc.). The two QIDMs now
       reference different sourceFields in their set[] clauses. Platform sees them
       as different field requirements.
       -> Apply + add autoSelect/queriesToDeselect (see SECTION 6 below).
       -> Test T1-T4 before committing (cold start + warm switch for each path).
    d) No solution: document as NOT IMPLEMENTABLE. Notify vendor to assign distinct
       keyRefs or register a separate transaction in the provider XML. Only reach
       (d) after (a)-(c) fail.

  NOTE: Never use the same keyReference in two combinations within one QIDM --
    platform import will fail (AP #5). Always invent a distinct keyRef if no
    MetaData keyRef is available (option b).

SECTION 5 -- MULTI-QUERY PERSON FORMS (DL + DH)
================================================================================

  Two confirmed architectures. Choose based on whether DL and DH share one form
  or separate forms.

  -----------------------------------------------------------------------
  SCENARIO A: DL and DH on the SAME Person tab (FL_FCIC pattern)
  -----------------------------------------------------------------------
  Apply BOTH parts. Part 1 alone is insufficient.

  PART 1 -- autoSelect + queriesToDeselect (mutual exclusion between QIDMs)

    LIMITATION #24: Two QIDMs on same form -- autoSelect + queriesToDeselect
      Confirmed: FL_FCIC (2026-04-10)
      Rule: When DL and DH share a Person form, add to each QIDM:
        autoSelect: true
        queriesToDeselect: ["<other query name>"]
      Without this: both queries fire on every submission.
      ALWAYS pair with LIMITATION #25 (DH-suffix fieldIds).
      Do NOT put queriesToDeselect on DL QIDMs in separate-form designs
        (deadlocks -- see AP #14).

    WARNING: on a shared form, Part 1 alone deadlocks when both QIDMs have
      the same fieldId (e.g., OperatorLicenseNumber) in their set[]. Both
      match simultaneously; mutual deselect produces undefined behavior.
      MUST pair with Part 2.

  PART 2 -- DH-suffix fieldIds (mutual exclusion within the form)

    LIMITATION #25: DH-suffix fieldIds when DL and DH share a form
      Confirmed: FL_FCIC (2026-04-10)
      Rule: DH form fields use suffixed fieldIds:
        NameFirstDH, NameLastDH, NameMiddleDH, NameSuffixDH,
        BirthDateDH, SexCodeDH, OperatorLicenseNumberDH
      DH QIDM set[]/sourceField reference only DH-suffixed names.
      Result: DL and DH set[] reference different fields -- cannot co-fire
        accidentally.

    DH QIDM combinations reference only DH-suffixed names in set[].
    DH QIDM attributes:
      sourceField=NameFirstDH    targetField=Name (assembled via FormatStringRuleHandler)
      sourceField=BirthDateDH    targetField=BirthDate
      sourceField=SexCodeDH      targetField=SexCode
    DL form fields use standard non-suffixed fieldIds.
    Result: DL set[] and DH set[] reference different sourceFields. Cannot co-fire.
    Source: FL_FCIC.json production.

  -----------------------------------------------------------------------
  SCENARIO B: DL and DH on SEPARATE QIFs (NY v1.15/v1.16 pattern)
  -----------------------------------------------------------------------

  LIMITATION #26: Separate-form DL+DH -- platform uses SHARED field pool for
    ALL Person QIDMs
    Confirmed: NY v1.15 live test (2026-04-14)
    Behavior: Platform evaluates ALL Person QIDMs from a single shared
      field-value pool, regardless of which sub-form is active. Separate QIF
      sub-forms do NOT isolate QIDM evaluation.
    See AP #16 (anti-pattern: assuming separate QIF sub-forms isolate QIDM
      evaluation).

  Consequence: mutual queriesToDeselect on DL + DH deadlocks (LIMITATION #26).
  Entering OLN on the DL form also triggers DH QIDM match. DH checkbox stays
    checked.

  CONFIRMED CORRECT DESIGN (v1.16):
    - Remove queriesToDeselect from DL QIDMs.
    - Keep queriesToDeselect on DH QIDM (deselects both DL QIDMs when DH fires
      alone).
    - Result: DH co-fires with DL on OLN entry. This is correct police workflow --
      both DL and DH results are returned when officer queries a license number.
    - The DH sub-form remains available for OOS/specialized DH use (TransactionName,
      PurposeCode, Requestor) without a DL query firing alongside it.

  IF TRUE ISOLATION IS NEEDED (DH must not fire from DL form at all):
    Use DH-suffix fieldIds (OperatorLicenseNumberDH) on the DH form and DH QIDM
      set[]. DH set[] field is absent from shared pool when DL form is active.
    DH-suffix is only needed for the OLN fieldId (not name/dob -- those are
      DL-only). Pair with autoSelect + queriesToDeselect (Scenario A PART 1).

  -----------------------------------------------------------------------
  SCENARIO C: Provider has DL only, no DH (NJ pattern)
  -----------------------------------------------------------------------
  Single merged DriverLicenseQuery QIDM with OLN and Name combinations
    (distinct keyRefs). autoSelect=true. No queriesToDeselect (nothing to
    deselect). No DH-suffix needed. No separate forms for DH or NCIC.
  Person forms: [State]-NJ + Out of State only.
  Source: NJ_NJCJIS v3.23.

SECTION 6 -- KNOWN QUERY/TRANSACTION PATTERNS
================================================================================

  For per-provider combination requirements (Set/Any/Choice fields, keyReferences,
  MC expansion candidates), see the auto-generated metadata reference:
    docs/<PROVIDER>_METADATA_REFERENCE.txt
  Generated by: tools/extract_metadata_reference.ps1

  The patterns below are cross-provider archetypes. For the authoritative
  combination requirements of any specific provider, always check that
  provider's METADATA_REFERENCE.txt first.

    query='DriverLicenseQuery'  keyRef=DLIC  targetEntity='Person'
    set=['OperatorLicenseNumber']  any=['ImageIndicator','State fields']

    query='NyNyspinDriverLicenseNameQuery'  keyRef=DGRP  targetEntity='Person'
    set=['NameLast','NameFirst']
    any=['BirthDate','NameMiddle','NameSuffix','SexCode']
    NOTE: This is a SEPARATE TRANSACTION from DriverLicenseQuery. Different query
      name = no LIMITATION #2. Only available in NY_NYSPIN MetaData. Verify per
      provider.

  DriverLicenseQuery (Name/DOB) -- NJ pattern
    query='DriverLicenseQuery'  keyRef=DQ  targetEntity='Person'
    Uses DH-suffix pattern to separate from OLN path in same merged QIDM.

  DriverHistoryQuery (OLN) -- STANDARD PATTERN: 2 combos per OLN path
    query='DriverHistoryQuery'  targetEntity='Person'
    REQUIRED: Both in-state and OOS combos (see LIMITATION #32 Choice-set).
    In-state: keyRef=DALL,  set=[operatorLicenseNumberDH],
              any=[imageIndicator, registrationState, purposeCodeDH, requestorDH, nyNyspinTransactionName]
    OOS:      keyRef=DALLOUT, set=[operatorLicenseNumberDH, purposeCodeDH, requestorDH, registrationState],
              any=[imageIndicator, nyNyspinTransactionName]
    any=[...'Attention','PurposeCode'] (AZ -- KQ keyRef pattern, no OOS split needed)

  DriverHistoryQuery (Name) -- RESOLVED via invented keyRef + 2 combos per path
    (CONFIRMED NY v1.19, AZ v1.0)
    Both OLN and Name paths share keyRef in MetaData XML. Resolution: INVENT a
      distinct keyRef for the second combination (e.g., DALH for NY, KQH for AZ).
      The provider does NOT validate keyRef -- it routes by field content in the XML.
    NY FULL PATTERN (4 DH combos):
      DALHOUT: set=[birthDateDH, nameLastDH, nameFirstDH, sexCodeDH, purposeCodeDH, requestorDH, registrationState]  -- OOS Name
      DALH:    set=[birthDateDH, nameLastDH, nameFirstDH, sexCodeDH]                                                 -- in-state Name
      DALLOUT: set=[operatorLicenseNumberDH, purposeCodeDH, requestorDH, registrationState]                          -- OOS OLN
      DALL:    set=[operatorLicenseNumberDH]                                                                          -- in-state OLN
    Ordering: DALHOUT (7 set) > DALH (4 set) > DALLOUT (4 set) > DALL (1 set)
    AZ 2-combo pattern (KQ+KQH) remains valid if provider has no OOS DH requirement.
    NOTE: DH-suffix fieldIds (operatorLicenseNumberDH, nameFirstDH etc.) are
      required to isolate DH QIDM from the DL field pool (LIMITATION #26 shared field pool).
    Prior status "NOT IMPLEMENTABLE" was WRONG -- invented keyRef resolves it. See AP #17.
    PurposeCode+Requestor: required for OOS DH only (see LIMITATION #32).
    NyNyspinTransactionName: in any[], defaults to DALL if absent -- no form field needed.

  VehicleRegistrationQuery (merged -- confirmed pattern)
    query='VehicleRegistrationQuery'  targetEntity='Vehicle'
    Combinations: RVEH (plate), RCAR (VIN, no state), RVIN (VIN + OOS state)
    All three keyRefs are distinct -- safe to merge.
    Confirmed: NY v1.11 T1-T4 all PASS.

  BoatQuery
    query='BoatQuery'  targetEntity='Boat'
    Combinations: RVEH (NY reg), RCAR (NY hull), BVEH (OOS reg), BVIN (OOS hull)
    Note: RVEH and RCAR keyRefs are shared with VehicleRegistrationQuery.

SECTION 8 -- IMPORT VALIDATION RULES
================================================================================

  When a QUERYINPUTDATAMAPPING is imported, the system validates:

  1. combinations must not be empty
  2. Each combination must have at least one field in set[] or any[]
  3. keyReference values must be unique within the configuration
  4. All field names in set[] and any[] must have a corresponding attribute
  5. Each attribute must have non-blank name, non-blank targetField,
     and at least one entry in sourceField

  Our validator (tools/validate.ps1) checks rules 3-5. Rules 1-2 are caught
  by the platform import. If the validator passes clean, import should succeed
  for structural QIDM issues.

================================================================================
SECTION 9 -- SYSTEM PROCESSING FLOW
================================================================================

  How the system uses QUERYINPUTDATAMAPPING configurations at runtime:

  User submits query form
        |
        v
  System identifies targetEntity (Person, Vehicle, etc.)
        |
        v
  Loads all QUERYINPUTDATAMAPPING configs for the department
    -> filters by targetEntity
    -> groups by provider
        |
        v
  For each provider + query:
    -> validates user input against combinations (first match fires)
    -> if valid: runs attributes through their rules (handlers)
    -> calls handlerFunction to build the outgoing message
    -> sends to the Interface Agent / provider

  The `order` field controls display sequence in the UI.
  The `queriesToDeselect` field is used by the frontend to deselect related queries.
  The `autoSelect` field determines whether the query checkbox is pre-checked.

  IMPORTANT: Platform evaluates ONE QIDM per (targetEntity, query) pair
    (LIMITATION #2). Multiple QIDMs with the same targetEntity+query -- only
    one is evaluated. The others are silently ignored.

SECTION 10 -- COMBINATION EXAMPLES (from engineering reference)
================================================================================

  Simple -- OLN only:
  {
    "keyReference": "OperatorLicenseNumber",
    "primaryFieldReference": "OperatorLicenseNumber",
    "state": "In",
    "requirements": { "set": ["OperatorLicenseNumber"], "any": null }
  }

  With optional fields:
  {
    "keyReference": "BirthDateNameSexCode",
    "primaryFieldReference": "BirthDate",
    "state": "In/Out",
    "requirements": {
      "set": ["BirthDate", "Name", "SexCode"],
      "any": ["ExpandedNameSearchCode", "ImageIndicator", "RaceCode", "State"]
    }
  }

  With EXCLUSIVE condition:
  {
    "keyReference": "PurposeCodeNameLastBirthDate",
    "primaryFieldReference": "Name",
    "requirements": {
      "set": ["PurposeCode", "NameFirst", "NameLast", "BirthDate"],
      "any": ["ORI"],
      "conditions": [
        { "operator": "EXCLUSIVE", "field": ["BirthDate", "Age"] }
      ]
