WHAT THIS FILE IS, AND WHAT IT DELIBERATELY NO LONGER HOLDS
-----------------------------------------------------------
Until 2026-08-11 this file carried two more columns -- "Last Comment ID" and a free-text
"Test Status" -- and BOTH had been frozen since 2026-07-06/07-20 while the tickets and the
providers moved on. It asserted CA_CLETS's newest comment was 772071 (six comments stale), TX
"v4.2 BUILT, UNTESTED" (the provider is v4.19 ALL-PASS), FL "118/118" (it is 116), NY "73/73"
(69). Every one of those numbers is derived state that something else already owns:

  - CURRENT VERSION / TEST STATE  -> tools\portfolio_status.ps1  (run it verbatim; log-derived)
  - POSTED COMMENT IDS + WHAT IS OWED -> providers/<P>/docs/tracking/DEX_TICKET.md
  - AND THAT FILE IS ITSELF A CLAIM   -> the TICKET is authoritative. getJiraIssue <KEY>
    fields:["comment"]. DEX_TICKET.md has demonstrably lied twice (HI indexed 2 of 16; FL
    produced a confidently wrong "nine versions owed"). audit_lifecycle (enforce 2r) reads the
    FILE, not the ticket, so it can PASS on a lie and FAIL on the truth.

So this file now holds only what does not change: the provider -> ticket mapping, and the
procedure. Do not re-add a status or comment-id column -- that is the drift this rewrite removed.

THE POSTING PROCEDURE
---------------------
1. JIRA UPDATES ARE HELD (Rob, 2026-07-31) until the process and results are fully trusted.
2. DRAFT AND WAIT, every provider, EVERY time. Approval on one provider does not authorize the
   next one, and approval of one comment does not authorize a follow-up.
3. FORMAT IS FIXED -- knowledge-base/JIRA_COMMENT_TEMPLATE.txt is the single source. Six numbered
   sections in a fixed order, every one present, an explicit "None" rather than an omitted
   section. Do not restate the template here; it would drift from itself. Two providers' comments
   placed side by side must differ only in their VALUES.
4. ONE COMMENT PER RELEASE -- not one per version (Rob 2026-08-03: the per-version format
   "becomes tldr").
5. IF THE NUMBERS MOVE BEFORE THE NEXT RELEASE, EDIT THAT COMMENT IN PLACE. Never post the
   correction as a sibling (Rob, 2026-08-11). Posting corrections as siblings is what left FL
   claiming ALL-PASS at 121/121, then 118, then 117, then 116, and NJ at 35, then 36, then 40 --
   four and three mutually exclusive completion claims in one thread each, with no way for a
   reader to tell which was current. 73 comments had to be rewritten to stubs to undo it.
6. THERE IS NO DELETE-COMMENT TOOL. addCommentToJiraIssue with a commentId EDITS IN PLACE and the
   edit is IRREVERSIBLE -- capture the original body before overwriting it. Superseded comments
   are rewritten to the stub form in the template, never removed. Do not plan around a delete
   that does not exist; deleting requires Rob in the Jira UI and he declined in favour of stubs.
7. ONLY EDIT COMMENTS THE AUTOMATION AUTHORED (the leading robot attribution line). Never Rob's
   own manual notes, never a third party's. DO NOT identify authorship by displayName -- the
   automation posts under Rob's account, so displayName cannot distinguish them; the attribution
   line can.
8. TENANT INFO STAYS OFF THE TICKETS (Rob, 2026-08-03): no attachment note, no catalog post, no
   Foundation import line. Those go in providers/IMPORT_LEDGER.md sections B and C.
9. EVERY NUMBER COMES FROM A TOOL, never from memory or from a tracking file:
   report_test_status.ps1 for pass counts, the gate outputs for gate lines,
   audit_test_coverage.ps1 for combo counts. A stale count restated confidently is exactly the
   defect this file used to embody.
