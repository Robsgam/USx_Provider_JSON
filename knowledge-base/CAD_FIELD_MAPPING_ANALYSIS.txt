CAD FIELD MAPPING ANALYSIS
===========================
Date: 2026-05-05
Purpose: Compare CAD dispatch field names against CA_ESUN (reference), NJ v2.1, FL v3.0
Source: Engineering feedback + CA_ESUN.json template + provider builds

EXECUTIVE SUMMARY
-----------------
The CAD field list provided by engineering appears to be derived from CA_ESUN.
Evidence: field names match CA_ESUN QIF fieldIds (PascalCase -> camelCase), including
CA-specific fields like PurposeCode, LojackID, AddressCity, and Name fields on Vehicle.

However, the CAD list also includes fields NOT in CA_ESUN (imageIndicator,
relatedHitSearchIndicator, articleCategory), suggesting it's a SUPERSET of all
provider fields, not CA-specific. This means some CAD fields may be provider-specific.

CRITICAL FINDING: The QIDM sourceField->targetField mapping is PROVIDER-SPECIFIC.
Different providers use different targetField names for the same conceptual field
(e.g., CA: CaRequestPurposeCode, NJ: has no PurposeCode, FL: PurposeCode).
The CAD list only affects sourceField (QIF fieldId). targetField is CommSys XML spec.

SECTION 4: KEY FINDINGS
================================================================================

1. CAD LIST IS CA_ESUN-BASED WITH ADDITIONS
   39 of 43 unique field names in the CAD list match CA_ESUN fieldIds (camelCase).
   The remaining 4 are either from other providers (driverHistoryPurposeCode) or
   additions to the broader platform (imageIndicator, relatedHitSearchIndicator).

2. NAMING CONFLICTS BETWEEN CAD AND CA_ESUN
   - gunCaliber (CAD) vs FirearmCaliber (CA) -- different prefix convention
   - gunTypeCode (CAD) vs FirearmType (CA) -- different prefix convention
   - serialNumber (CAD Article) vs ArticleSerialNumber (CA) -- CA prefixes with entity
   These suggest the CAD list may be normalized/generic rather than provider-specific.

3. PROVIDER-SPECIFIC FIELDS NOT IN CAD LIST
   These exist in our builds but are NOT in the CAD list. CAD won't auto-populate them.
   Officers must enter them manually:
   - NCICNumber, ProcessControlNumber (NJ, FL -- NCIC-specific)
   - CoastGuardDocumentNumber (FL -- boat-only)
   - DecalNumber, TitleLienInformation (FL -- FL-specific)
   - OwnerAppliedNumber (FL -- article)
   - RandomRequest (NJ -- NJ-specific)
   - DH-suffix fields: NameFirstDH, OperatorLicenseNumberDH, etc. (FL)
   This is EXPECTED. These are provider-specific fields that CAD doesn't know about.

4. CA-SPECIFIC FIELDS IN CAD LIST BUT NOT IN OTHER PROVIDERS
   These are in the CAD list because CA uses them, but NJ/FL don't:
   - purposeCode on Vehicle/Firearm/Article/Boat (CA has PurposeCode everywhere)
   - lojackID (CA only -- CAILojackQuery)
   - addressCity, addressStreetNumber on Vehicle (CA name/address vehicle combos)
   - age on Firearm (CA gun query by person age)
   - articleBrand (CA article search)
   - Most Person address fields (address, addressCity, addressState, etc.)

5. FL IS STILL PascalCase
   FL v3.0 has not been converted to camelCase. NJ v2.1 is the test build.
   If NJ import succeeds, FL and all other providers need the same conversion.
   FL has additional complexity: DH-suffix fields, RelatedHitSearchIndicator.

6. FIELD NAME STANDARDIZATION NEEDED
   Before rolling camelCase to all providers, resolve the CAD naming conflicts:
   - Is it gunCaliber or firearmCaliber? (CAD says gun, CA says Firearm)
   - Is it gunTypeCode or firearmType? (same conflict)
   - Does the CAD list change per provider, or is it universal?
   Engineering should confirm the authoritative CAD field list per provider.

================================================================================
SECTION 5: RECOMMENDED QUESTIONS FOR ENGINEERING
================================================================================

1. Is the CAD field list provider-specific or universal?
   If provider-specific, we need a list per provider.
   If universal, we need to resolve the gunCaliber/firearmCaliber naming conflict.

2. Does CAD auto-populate fields not in its list?
   Provider-specific fields (NCICNumber, CoastGuardDocumentNumber, etc.) are not
   in the CAD list. Do they need to be, or does the officer always enter them manually?

3. What is the authoritative source for CAD field names?
   The list provided has conflicts with CA_ESUN (gun vs Firearm prefix).
   Is there a CAD schema or mapping document?

4. Does PurposeCode apply to all providers or just CA?
   CA has PurposeCode on every entity form. NJ/FL do not (except FL DH).
   The CAD list includes purposeCode on every inquiry type.

5. Should DH-suffix fields (FL pattern) have CAD mappings?
   FL uses NameFirstDH, BirthDateDH, etc. for Driver History. Does CAD send
   driverHistoryPurposeCode/nameFirst for DH fields, or are these manual-only?
