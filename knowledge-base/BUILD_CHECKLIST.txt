CONNECTCIC BUILD CHECKLIST
===========================
Run through these steps for every build, import, and test session.
Last updated: 2026-04-30 (added MANDATORY GATES, canonical repo structure, shared test log tool)

================================================================================
BUILD PHASE MODEL (follow this order -- do not skip phases)
================================================================================

  PHASE 1 -- STANDUP (single entity, single card)
    Goal: confirm every query path and QIDM combination works.
    One QIF per entity. One card per QIF. All fields on that card.
    No multi-card. No split entity. No UX decisions.
    This is the only baseline that isolates QIDM/combination problems from layout problems.
    Complete 100% of query path testing before leaving Phase 1.
    Output: <PROVIDER>_BASE.json (save a copy -- this is the phase 1 reference forever)

  PHASE 2 -- MULTI-CARD
    Goal: improve operator UX by separating search paths onto distinct cards.
    Start from the confirmed Phase 1 BASE.json. Build multi-card layout for entities that
    have 2+ search paths (Vehicle: Plate vs VIN; Person: OLN vs Name).
    QIDM does not change. Only the form layout changes.
    Retest only affected entities after layout promotion.

  PHASE 3 -- SPLIT ENTITY (only if needed)
    Goal: handle cases where two search paths require fundamentally different hidden state
    fields and cannot share a common state model in one QIF.
    Examples: in-state form needs SelH+InpH; OOS form needs visible RegistrationStateOOS.
    Retest all entities after split.
    Most providers do not need Phase 3 if the NCIC state pattern works (see FORM_ARCHITECTURE.txt).

  WHY THIS ORDER MATTERS (lessons from NJ and NY):
    NJ went through multi-card and split-entity in Phase 1. When tests failed it was
    impossible to tell if the failure was the QIDM, the layout, or the state model.
    Starting single-card eliminates layout as a variable. QIDM problems surface cleanly.
    NY introduced multi-card before QIDM combinations were confirmed. Same confusion.
    Phase 1 single-card is the only way to establish a clean causal baseline.

  [ ] Read ANTI_PATTERNS.txt before writing any field definitions
  [ ] Check FIELD_RULES.txt codeType table for every dropdown field
  [ ] Confirm all target transactions are in the provider XML (MessageKey list)
      Any missing -> flag in LIMITATIONS.txt and include in gap summary
  [ ] Run PDF vs XML gap check before first build (see build guide for prompt)
  [ ] Check NJ_NJCJIS.json and NY_NYSPIN_EJUSTICE.json as structural reference

  OPERATIONAL IDENTITY FIELDS (ask before writing any form field or QIDM):
  [ ] Does the provider XML include BadgeNumber (or equivalent officer identity field)
      in any query transaction combinations?
      YES -> decide now: VISIBLE or AUTO-POPULATED?

      OPTION A -- Visible (officer types badge manually):
        Form:  Inp 'BadgeNumber' 'Badge Number' '<maxLen>' '<rowId>'
        QIDM:  sourceField = @('BadgeNumber'), targetField = 'BadgeNumber'
        Combinations: set/any refs use 'BadgeNumber'

      OPTION B -- Auto-populated from officer RMS profile (RECOMMENDED):
        Form:  InpH 'dexStateUserId' 'Badge (auto)' @{} '<rowId>' (hidden row)
        QIDM:  sourceField = @('dexStateUserId'), targetField = 'BadgeNumber'
        Combinations: set/any refs use 'dexStateUserId'
        AUTHENTICATION: CommsysGetDexStateUserIdRuleHandler is already wired in AUTH config.
        No other AUTH changes needed.

      If unsure: ask the end user. "Should officers type their badge each time,
      or should it be filled automatically from their RMS profile?"
      Confirmed auto-populate pattern: AZ_AZDPS v1.1 (2026-04-20).

      DO NOT default to visible just because it appears as a form field in the XML spec.
      The XML spec describes what can be sent -- it does not dictate whether the officer
      types it or the system fills it. This is a UX and deployment decision.
      See FIELD_RULES.txt Section 5 and ANTI_PATTERNS.txt #20.

  PHASE 1 FORM DECISIONS (make these before Phase 1 build -- layout decisions are deferred):
  [ ] Identify all query types from provider XML (MessageKey list).
  [ ] Identify all search paths per query type (OLN vs Name, Plate vs VIN, etc.).
  [ ] Identify all optional fields per path from XML.
  [ ] Does provider have DriverHistoryQuery? Note for Phase 2 planning.
  [ ] Does provider have WINQ/MINQ? Note for Phase 2 planning.
      (Phase 1: DH goes on same Person QIF as DL; Phase 2: split if needed)
  [ ] For every QIDM covering multiple paths: check keyRefs in MetaData.
      -> All keyRefs distinct: merge into one QIDM with multiple combinations.
      -> Duplicate keyRefs: invent distinct keyRefs (e.g., DALL + DALH). Provider routes
         by field content, NOT by keyRef. Confirmed: NY v1.19. See QIDM_ARCHITECTURE.txt Section 3.
      -> Only reach "not implementable" after confirming ALL three options fail:
         (a) separate MetaData transaction, (b) invented keyRef, (c) DH-suffix isolation.

  NAME FIELD CHECK:
  [ ] Check provider MetaData: does it accept NameMiddle and NameSuffix in Name field?
      YES -> 4-field name, FormatStringRuleHandler arguments = @(' ',' ',' ')
      NO  -> 2-field name, FormatStringRuleHandler arguments = @(' ')
      Mismatch causes malformed Name output. See ANTI_PATTERNS.txt #15.

================================================================================
AUTONOMOUS DESIGN DECISIONS (apply without prompting)
================================================================================

  These decisions must be made automatically when designing a new provider JSON.
  Do not wait for a test failure or explicit instruction to apply them.

  PHASE 1 LAYOUT RULE (always single card)
    Phase 1 always produces single entity, single card per QIF.
    Do NOT pre-build multi-card or split-entity in Phase 1 -- even if you know it will
    be needed later. Confirm all query paths first. Then promote layout in Phase 2.

  MULTI-CARD FORMS (Phase 2 only)
    Promote to multi-card after Phase 1 standup confirms all paths.
    Any entity with 2+ search paths (Plate vs VIN, OLN vs Name) gets one card per path.
    Each card gets a clear ALL-CAPS title identifying its search path.
    Examples: 'DRIVER LICENSE - LICENSE NUMBER' / 'DRIVER LICENSE - NAME'
              'DRIVER HISTORY - LICENSE NUMBER' / 'DRIVER HISTORY - NAME'
    QIDM does not change in Phase 2. Layout only.

  SPLIT ENTITY FORMS (Phase 3 only -- most providers never need this)
    Promote to split entity only after Phase 2 multi-card reveals a genuine state model
    conflict that cannot be handled within one QIF.
    In-state form: dual hidden state fields (SelH + InpH with initialValue).
    OOS form: visible RegistrationStateOOS dropdown (no hidden state).
    If NCIC state pattern is confirmed on this instance: split entity is rarely needed.

  DH-SUFFIX FIELDIDS
    Any DH form that coexists with a DL form -> DH-suffix fieldIds automatically.
    OperatorLicenseNumberDH, NameFirstDH, NameLastDH, NameMiddleDH, NameSuffixDH,
    BirthDateDH, SexCodeDH on DH form fields AND in DH QIDM sourceField/set[].
    This is structural isolation -- no queriesToDeselect needed or useful.

  DUPLICATE KEYREF IN METADATA
    MetaData assigns the same keyRef to two paths of the same transaction ->
    use invented distinct keyRef for the second combination (e.g., DALL + DALH).
    keyRef is platform-internal only; provider routes by XML field content.
    Single QIDM, two combinations, distinct keyRefs = import passes, both paths fire.
    Do not declare "not implementable" until (a) separate transaction, (b) invented keyRef,
    and (c) DH-suffix isolation have all been tried and failed.

  QIDM MERGE
    Multiple paths, same (targetEntity, query) -> single merged QIDM always preferred.
    Split into 2 QIDMs only when keyRefs are confirmed duplicates AND no invented keyRef
    workaround exists AND no separate MetaData transaction exists.

  COMBINATION ORDERING
    Most-specific combination (most fields in set[]) goes first.
    Less-specific last. This prevents a broad combination from swallowing
    a more specific match before it can be evaluated (LIMITATION #3).

  EMPTY ELEMENT SIDE EFFECT (LIMITATION #1)
    When a multi-path QIDM fires, ALL attributes serialize. Paths with empty
    sourceFields produce empty XML elements (e.g., <Name/> on OLN queries).
    Servers tested so far accept empty elements. Include a note in build comments.
    Monitor per provider -- if a server rejects empty elements, split QIDM is needed.

STANDARD RMS PATCHES (REQUIRED FOR EVERY PROVIDER -- NOT IN HIDLE)
================================================================================

  These patches are NOT present in HIDLE.json. They must be applied manually in every
  build script. They are confirmed working in NJ_NJCJIS v1.2 (2026-04-20).

  PATCH 1 -- Vehicle plate + state (RMS Vehicle QIDM)
    Add RegistrationState to RMS Vehicle licensePlateIn combination any[].
    Without this: plate search fires but state filter absent from RMS elastic query.
    Target field: vehicle.registrationStateAttrIds (array, AttributeArrayWrapperRuleHandler)
    useAttributeId=true

  PATCH 2 -- Vehicle OOS state cleanup (RMS Vehicle QIDM)
    Drop RegistrationStateOut from RMS Vehicle licensePlateOutAndState set[].
    HIDLE includes RegistrationStateOut as required -- this breaks OOS plate search.
    Without this: OOS plate combination never fires (RegistrationStateOut never populated).

  PATCH 3 -- Person state (RMS Person QIDM) -- CONFIRMED NJ v1.2 2026-04-20
    Add registrationState attribute to RMS Person QIDM:
      name='registrationState', sourceField=['RegistrationState'],
      targetField='registrationStateAttrId', useAttributeId=true
    Add 'RegistrationState' to ALL person combination any[] arrays.
    Without this: person searches (OLN, Name) fire without state filter in RMS elastic query.
    Target field: registrationStateAttrId (singular string, NO ArrayWrapper -- unlike vehicle)

  PATCH 6 -- RMS cleanup (ALWAYS apply AFTER all other patches) -- CONFIRMED 2026-04-24
    Remove unused HIDLE attrs/combos that have no matching form fieldId.
    Vehicle: remove LicensePlateNumberOut, RegistrationStateOut, OwnerFirstName, OwnerLastName
             remove combos: licensePlateOutAndState, OwnerFirstAndLastName
             clean any[] refs to removed attrs
    Person:  remove socialSecurityNumber, licenseNumberOOS, firstNameOOS, lastNameOOS,
             dateOfBirthOOS, sexOOS
             remove combos: firstNameLastNameSocialSecurityNumber, driversLicenseNumberOOS,
             firstNameLastNameDriversLicenseNumberOOS, firstNameLastNameDateOfBirthOOS,
             firstNameLastNameOOS
    Exception: keep OOS attrs if provider uses DH-suffix fieldIds (e.g., FL_FCIC).
    See BUNDLE_ARCHITECTURE.txt Section 5 Patch 6 for full reference.

  RULE: Always verify after import that registrationStateAttrId:"[attrId]" appears in
  person RMS elastic query for DQN (OLN) search. Missing = Patch 3 not applied or wrong fieldId.

BEFORE EACH BUILD
================================================================================

  [ ] Confirm JSON version bumped (do not overwrite a tested version)
  [ ] Check every new FormSelect: is codeTypeCategory + codeTypeSource correct?
      (See FIELD_RULES.txt -- do not guess; look up in the confirmed table)
  [ ] Check every attributeTypeId: is it STATE only, for a SelH, not in QIDM?
  [ ] Check every SEX field: verify instance-specific reverse-lookup status first
      NJ confirmed: attributeTypeId=SEX + codeTypeProvider=NIBRS (CommSys + RMS both work)
      FL confirmed: NIBRS_SEX + CommSys-only (reverse-lookup fails on FL instance)
      Unknown instance: default to codeTypeCategory=NIBRS_SEX (CommSys-only; safe)
      See SEX_CODE_PATTERN.txt for per-instance status and the three-layer chain.
  [ ] Check every RACE field: codeTypeCategory=NIBRS_RACE, NOT attributeTypeId=RACE
  [ ] Check every state field: dual-field pattern in place?
      (SelH 'RegistrationState' for RMS + InpH 'RegistrationStateNY' for XML)
  [ ] Check every QIDM: all keyReferences unique within each QIDM?
  [ ] Check every combination: set[] and any[] values reference valid sourceField names?
  [ ] Check ENTITIES bundle order.default: using targetEntity values?
  [ ] Check every FormatStringRuleHandler: argument count = sourceField count minus 1?
      (NJ: 2 fields / 1 arg; NY: 4 fields / 3 args -- see ANTI_PATTERNS.txt #15)
  [ ] If DH form present: two-card layout in place (CARD_DH_OLN + CARD_DH_NAME)?
      DH-suffix fieldIds on all DH form fields and QIDM sourceFields?
      DALL (OLN) + DALH (Name) or equivalent distinct keyRefs in single QIDM?
  [ ] If DL+DH on same form (FL pattern): DH-suffix fieldIds + autoSelect + queriesToDeselect?
  [ ] queriesToDeselect on DL QIDMs? -> NO (platform shared pool; queriesToDeselect deadlocks).
      queriesToDeselect on DH QIDM? -> NOT NEEDED with single unified QIDM (v1.19 pattern).
      autoSelect=true on all person QIDMs that should fire automatically?
  [ ] Check RMS Person QIDM: does it include registrationStateAttrId? (HIDLE does NOT have it)
      ALWAYS add Patch 3 manually: registrationState -> registrationStateAttrId, useAttributeId=true
      AND add RegistrationState to every person combination any[] array.
      CONFIRMED pattern: NJ_NJCJIS v1.2 -- registrationStateAttrId:"[attrId]" (singular string, no ArrayWrapper)
      RMS Vehicle is DIFFERENT: registrationStateAttrIds (array, AttributeArrayWrapperRuleHandler, Patch 1)
  [ ] Check every queryLabel value against the standard (FIELD_RULES.txt Section 6):
      VehicleRegistrationQuery -> "Vehicle Registration"
      DriverLicenseQuery       -> "Driver License"
      DriverHistoryQuery       -> "Driver History"
      GunQuery                 -> "Firearm"
      ArticleSingleQuery       -> "Article"
      BoatQuery                -> "Boat"
      Do NOT use entity names ("Vehicle","Person"), system names ("NCIC"), or generic labels.
      See AP #25.
  [ ] Check all card titles (MC only): ASCII characters only.
      No em dashes, en dashes, or smart quotes -- they render as mojibake. See AP #26.
  [ ] VehicleMakeCode: if present on form, use attributeTypeId='VEHICLE_MAKE' for dropdown.
      Accept that this field does NOT serialize to CommSys XML (platform limitation).
      Keep codeTypeProvider='NCIC' on QIDM attribute for graceful omission.
      Do NOT use NCIC_FIREARM_MAKE -- that is FIREARM makes only. See AP #24.
  [ ] Verify Patch 6 (RMS cleanup) is applied after all other patches.
      Dead HIDLE attrs with no form fieldId = bloat + false RMS search hits.
  [ ] Verify every RMS QIDM combo set[]/any[] field has a matching attribute (AP #27).
      No orphan field references allowed. CommSys fields with no RMS equivalent
      (e.g., LicensePlateYear) must NOT appear in RMS combos.
  [ ] Check State initialValue: do NOT set initialValue on State when provider has
      separate in-state vs OOS keyRefs (changes combo routing). See LIMITATION #30.
      OK to use initialValue when provider has no separate in-state keyRefs (e.g., NJ).
  [ ] Run validator: powershell.exe -ExecutionPolicy Bypass -File "tools/validate.ps1" -Path <your-json>
      Catches: BOM, templateColumns type (AP #21), maxLength type (AP #22),
      autoSelect conflicts (AP #23), duplicate targetField, phantom sourceField,
      LIMITATION #2 (duplicate entity+query), combination field resolution, missing Auth/QMF/Results.
      Build aborts on [FAIL]. Fix all FAILs before importing.

BEFORE EACH IMPORT
================================================================================

  [ ] Validator passes clean (0 FAIL, 0 unexpected WARN):
      powershell.exe -ExecutionPolicy Bypass -File "tools/validate.ps1" -Path <your-json> -ShowDetail
  [ ] CommSys provider bundle: type='BUNDLE' present on the bundle object?
  [ ] ENTITIES bundle: type='BUNDLE' present on the bundle object?
      (Both bundles require type='BUNDLE'. If omitted, platform silently ignores configs.)
  [ ] ENTITIES bundle: order is a nested object {default:[...], CAD_DISPATCH:[...], FIRST_RESPONDER:[...]}?
      (NOT a flat array. Flat array causes entity ordering failure and forms may not render.)
  [ ] ENTITIES bundle: provider='MARK43' present? (REQUIRED -- either on the bundle object
      OR on every individual QIF config. If absent from both -> forms will not render after import.
      NEVER use the CommSys provider name on QIF configs -- confirmed failure mode AZ v2.0 2026-04-20.)
  [ ] Backup current installed JSON (use bump_version.ps1 or archive manually)
  [ ] Import into ConnectCIC dev/test environment first (not production)
  [ ] Confirm entity tabs render in expected order after import

================================================================================
STANDARD TEST SEQUENCE PER QUERY PATH
================================================================================

  T1: Minimum required fields only (cleanest request)
  T2: Required + one optional field
  T3: Required + all optional fields
  T4: All form fields filled (confirm LIMITATION #1 -- extra fields ignored by server)
  T5: OOS variant if applicable

  For split config testing (LIMITATION #2 check):
  T1: Cold start, path A only
  T2: Cold start, path B only (if T2 fails -> LIMITATION #2 confirmed, must merge/alternate)
  T3: Warm switch A->B
  T4: Warm switch B->A
  If T3 fails: LIMITATION #2. See QIDM_ARCHITECTURE.txt Section 3.

================================================================================
WHEN A TEST FAILS
================================================================================

  1. Read the outbound XML carefully before making any changes.
     Confirm which fields were sent and what values they carried.
  2. Check: is the QIDM being evaluated at all?
     If the XML request shows no provider query -- LIMITATION #2. Merge.
  3. Check: is a field sending a wrong value (numeric ID vs code)?
     See ANTI_PATTERNS.txt #1-3 (STATE/SEX/RACE numeric ID bugs).
  4. Check: is a combination routing incorrectly?
     Review set[] order and combination priority (QIDM_ARCHITECTURE.txt Section 2).
  5. Check: is a dropdown empty on the form?
     Confirm codeTypeCategory + codeTypeSource (FIELD_RULES.txt Section 2).
  6. Update BUILD_NOTES.txt CHANGED and REASON stubs after every fix.
  7. Save test log immediately. Do not wait.
