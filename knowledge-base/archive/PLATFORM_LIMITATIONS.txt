CONNECTCIC PLATFORM LIMITATIONS
=================================
Immutable platform behaviors that cannot be changed by JSON config alone.
These are server-side constraints that build scripts must design around.
Last updated: 2026-05-04

Legend:  CONFIRMED = verified in live testing
         SERVER-SIDE = no config fix available; requires platform changes

See also:
  JSON_LIMITATIONS.txt      -- JSON structural/config rules (how to build correctly)
  TESTING_LIMITATIONS.txt   -- Instance-specific verification requirements
  PROVIDER_LIMITATIONS.txt  -- Per-provider exceptions and constraints

================================================================================
SECTION 1 -- QUERY ROUTING AND COMBINATION BEHAVIOR
================================================================================

LIMITATION #1: set[] and any[] control combination selection -- not field sending
  Confirmed: NJ v2.1 (2026-04-08), NJ v2.0-mc live test (2026-04-29)
  Behavior: When a combination fires, ALL populated attributes in the QIDM config
    are sent to the provider, regardless of whether they appear in set[] or any[].
    set/any cannot filter or suppress which attributes are serialized.
  Impact: Split configs are required for true field isolation. Single merged config
    will send extra fields from the unused path.
  Workaround: Server is tolerant of extra fields. OLN path sent Name/DOB/Sex as
    extras in NJ v2.1 and still returned results. Merge is preferred unless server
    rejects specific unknown fields.

  OPERATIONAL CONCERN (flagged 2026-04-29):
    When priority routing selects one combo over another (e.g., RQ wins over RQN
    because both Plate and VIN are filled), the "losing" combo's SET fields still
    appear in the XML because they are populated QIDM attributes. Examples:
      - Plate+VIN filled: VehicleReg RQ fires but VIN is in the XML
      - Plate+VIN filled: VehicleStolen QVP fires but VIN is in the XML
      - OLN+Name+DOB filled: DQN fires but Name+DOB are in the XML
      - RegNum+HullId filled: QB fires but HullId is in the XML
    This is EXPECTED platform behavior and cannot be changed at the JSON level.
    Monitor provider responses for signs of rejection on extra fields.
    As of 2026-04-29, NJ CommSys tolerates the extra fields with no errors.

LIMITATION #2: Platform evaluates only ONE QUERYINPUTDATAMAPPING per (targetEntity, query) pair
  Confirmed: NJ v2.6 (2026-04-08); NY v1.8-v1.10 (2026-04-13); NY v1.18b (2026-04-15)
  Behavior: When multiple QIDMs share the same targetEntity and query value, only
    one is evaluated. The others are silently ignored regardless of which entity
    form is active, what fields are populated, or whether autoSelect is true or false.
  Diagnostic trigger: Form data confirms field IS populated but query still does not
    fire. STOP iterating set[] changes -- the QIDM itself is never evaluated.
  Resolution: Merge into one QIDM (when all keyRefs are distinct), use a separate
    transaction, or use DH-suffix fieldIds. See JSON_LIMITATIONS.txt for patterns.

LIMITATION #3: Combination fires the first match -- all populated fields sent
  Confirmed: NJ v2.0
  Behavior: First combination whose set[] fields are all present fires. Its any[]
    determines which optional fields are included in routing. All populated QIDM
    attributes are still sent (see #1).
  Impact: Put most-specific combination first in the array.

SECTION 2 -- FIELD ENCODING AND STATE HANDLING
================================================================================

LIMITATION #4: attributeTypeId='STATE' sends internal numeric attribute ID
  Confirmed: NJ v3.x, NY v1.0
  Behavior: Any FormSelect with attributeTypeId='STATE' sends the platform's
    internal attribute ID (e.g., NJ=69509884952, NY=69509802469) instead of
    the 2-letter state code.
  Correct use: ONLY on visible Sel for RMS elastic search (fieldId='RegistrationState').
    Never map this field in a QIDM targetField for outbound XML without codeTypeProvider.
  Fix for outbound XML: codeTypeProvider='NCIC' on QIDM attribute enables reverse-lookup
    from attribute ID to 2-letter code. Fallback: InpH with initialValue.

LIMITATION #5: RMS elastic search fatals on VIN/OLN when state is plain text
  Confirmed: NJ v3.11
  Behavior: RMS recognizes fieldId='RegistrationState' and expects an attribute ID.
    Sending plain text (e.g., 'NJ', 'NY') causes RMS to throw a fatal local error.
  Scope: VIN and OLN queries only. Plate-only queries do not trigger this.
  Fix: Use attributeTypeId='STATE' on form field (stores attr ID, not text).

LIMITATION #7: Query display summary shows internal attribute ID for hidden state field
  Confirmed: NJ v3.14 -- SERVER-SIDE (no fix found)
  Behavior: Summary widget surfaces raw value of any field with attributeTypeId.
  Functional impact: NONE. Outbound XML and RMS work correctly. Cosmetic only.

LIMITATION #9: Blank FormInput = not sent; cleared FormSelect = not sent
  Confirmed: NJ v1.9
  Behavior: Platform does not serialize fields with no value.
  Impact: Use initialValue for fields that must always be sent.

SECTION 3 -- MULTI-ENTITY AND SHARED FORM BEHAVIOR
================================================================================

LIMITATION #26: Separate-form DL+DH -- platform uses SHARED field pool for ALL Person QIDMs
  CONFIRMED: NY v1.15 live test (2026-04-14)
  Behavior: Platform evaluates ALL Person QIDMs from a single shared field-value pool,
    regardless of which sub-form (QIF sub-tab) is currently active. Separate QIF sub-forms
    do NOT isolate QIDM evaluation to the active form's fields only.
  Consequence: When OLN is entered on the DL form, the DH QIDM also matches.
    queriesToDeselect is ineffective in BOTH directions (confirmed NY v1.16 T7a).
  Net behavior: DL + DH always co-fire whenever OLN is present = correct police workflow.
  True isolation requires: DH-suffix fieldIds (OperatorLicenseNumberDH on DH form).

LIMITATION #28: Entity-split (multiple QIFs per entity) breaks codeTypeProvider reverse-lookup
  SERVER-SIDE -- no config fix available
  Confirmed: FL_FCIC v2.0, v2.3, v2.4 (2026-04-20 through 2026-04-21). 3 tests, all failed.
  Control: FL_FCIC v2.2 single-QIF WORKS on same instance.
  Behavior: When multiple QIFs target the same entity, codeTypeProvider reverse-lookup
    on QIDM attributes fails. The QIDM sends raw attribute ID instead of resolved code.
  Root cause: Shared field pool (see #26). Inactive QIF's empty value interferes with
    reverse-lookup on active QIF's populated value.
  Design constraint: To use codeTypeProvider reverse-lookup, each entity must have
    exactly ONE QIF. Multi-card layouts within a single QIF are unaffected.
  Full investigation: FL_FCIC_entity_split_investigation.zip

LIMITATION #29: Attention field overridden by platform with user session data
  CONFIRMED -- SERVER-SIDE
  Confirmed: FL_FCIC KQ (DriverHistoryQuery) 2026-04-23
  Behavior: User types a value in Attention field, but platform substitutes logged-in
    user's name (LASTNAME FIRSTINITIAL) in outbound XML <Attention> element.
  Override happens AFTER form submit and BEFORE XML generation.
  Workaround: CommsysGetLastNameFirstNameInitialRuleHandler on QIDM Attention attribute
    (CA_eSUN, LA_LEMS pattern). Do NOT add visible FormInput for Attention.
  Open: Whether this applies to all providers or only FL_FCIC; whether this applies
    to all queries or only DriverHistoryQuery.

SECTION 4 -- TRANSACTION AND IMPORT
================================================================================

LIMITATION #23: Unregistered transactions cannot be built
  Behavior: QIDM cannot target a transaction type that the CommSys server has not
    registered. No import error, but query will never fire.
  Check at standup: Confirm all target transactions are in the provider XML metadata.
  Examples: NJ VehicleStolenQuery (registered late), NY WINQ/MINQ (no transaction XML).

SECTION 5 -- COMBO ROUTING INTERACTIONS
================================================================================

LIMITATION #30: initialValue on State field changes combo routing (in-state -> OOS)
  CONFIRMED -- by design (#1 + #3 interaction)
  Confirmed: NY_NYSPIN_EJUSTICE MC 2026-04-24
  Behavior: Setting initialValue (e.g., 'NY') on State dropdown causes State to always
    be populated. OOS combo (which includes State in set[]) fires instead of in-state combo.
  Example: Without initialValue, VIN only -> RCAR fires (in-state).
           With initialValue='NY', VIN + State(NY) -> RVIN fires (OOS).
  Workaround: Use card title hint ("Leave blank for NY queries").
  Safe to use initialValue: When provider has no separate in-state keyRef (e.g., NJ).
  Do NOT use initialValue: When provider has separate in-state vs OOS combos (e.g., NY).
