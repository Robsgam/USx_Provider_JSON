SECTION 1 -- INSTANCE-SPECIFIC BEHAVIORS (TEST ON FIRST IMPORT)
================================================================================

These behaviors are confirmed on some instances but must be verified per provider
on first import. Do not assume they work -- run the specified test.

NCIC STATE PATTERN:
  Test: In-state plate query (ST-1). Check CommSys XML for <State> element.
  If <State> contains 2-letter code: NCIC reverse-lookup works on this instance.
  If <State> is absent or contains numeric ID: fall back to dual-field pattern.
  Confirmed: NJ (2026-04-20), AZ (2026-04-20), NY (confirmed working)
  Unconfirmed: FL, HI, TX, LA
  Why instance-specific: codeTypeProvider=NCIC requires a registered reverse-lookup
    entry in the instance's code type registry. NJ_NIBRS was NOT registered on NJ
    but NCIC was. Each instance may differ.

SEXCODE REVERSE-LOOKUP:
  Test: Person query with Sex field populated. Check CommSys XML for <SexCode>.
  If <SexCode> contains M/F/U: reverse-lookup works.
  If <SexCode> contains numeric ID: reverse-lookup broken (check for entity-split #28).
  Confirmed: NJ (2026-04-17), AZ (2026-04-20), FL single-QIF (2026-04-21)
  Broken: FL entity-split (LIMITATION #28 -- SERVER-SIDE, no fix)
  Unconfirmed: NY, HI, TX, LA
  Default: Use NIBRS_SEX/NIBRS CommSys-only + remove sex from RMS until confirmed.

DEXSTATEUSERID (Badge auto-population):
  Test: Check if BadgeNumber field auto-populates with officer's badge from session.
  Confirmed: AZ (2026-04-20)
  Unconfirmed: NJ, FL, NY, HI, TX, LA
  If auto-populates: hide BadgeNumber field (not needed on form).
  If not: keep visible for manual entry.

VEHICLE_BODY_STYLE / VEHICLE_TYPE:
  Test: Import and check dropdown populates.
  Mapping varies by instance -- see JSON_LIMITATIONS.txt #20.
  NCIC source = empty dropdown. Must find correct source per provider.

SECTION 3 -- VALIDATOR MARKERS
================================================================================

The validator (tools/validate.ps1) emits three severity levels:

  [PASS]       -- Check passed. No action needed.
  [WARN]       -- Fixable issue. Should be resolved before import.
  [LIMITATION] -- Known platform constraint. Document in SQVR but cannot fix.
  [FAIL]       -- Must fix before import. JSON will not work correctly.

LIMITATION markers the validator emits:
  - Generic LicensePlateNumber (should be LicensePlateNumberIn/Out) -- #8
  - Card title with HTML tags -- #11
  - State field with attributeTypeId='STATE' patterns
  - SexCode field chain validation
  - Attention field auto-fill patterns (when handler is present)

Target: 0 FAIL, 0 WARN on every JSON before import.
LIMITATIONs are expected and should be documented in the provider's SQVR.

================================================================================
SECTION 4 -- TESTING WORKFLOW CONSTRAINTS
================================================================================

XML CAPTURE:
  Browser dev tools (F12 > Network) must be open BEFORE submitting a query.
  XML is in the POST request body to the CommSys endpoint.
  RMS payload is in a separate POST to the RMS endpoint.
  Both must be captured for full test verification.

ATTENTION FIELD:
  Cannot reliably test user-entered Attention values -- platform overrides with
  session identity (see PLATFORM_LIMITATIONS.txt #29). Test that the <Attention>
  element IS present in XML, not that it matches the form value.

COMBO PRIORITY:
  When testing combo priority (most-specific first), fill ALL fields and verify
  which combo fires. The "losing" combo's set[] fields will still appear in XML
  (PLATFORM_LIMITATIONS.txt #1). This is expected -- verify the keyReference in
  the XML matches the expected combo, not the field list.

CO-FIRE TESTING:
  Person DL+DH co-fire is expected when OLN is present (PLATFORM_LIMITATIONS.txt #26).
  Do not report this as a failure -- it is correct police workflow.
  RMS co-fire with CommSys is also expected -- verify both payloads.
