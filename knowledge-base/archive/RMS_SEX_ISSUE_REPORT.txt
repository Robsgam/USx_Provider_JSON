RMS SEX FILTERING ISSUE REPORT — NJ NJCJIS / NY NYSPIN / FL FCIC
=================================================================
Date: 2026-04-17 (final -- all config options exhausted)
Affects: NJ NJCJIS, NY NYSPIN, FL FCIC (all NIBRS-based providers)


THE PROBLEM
-----------
CommSys XML requires NIBRS codes (M/F/U) for <SexCode>. RMS elastic requires
a numeric attribute ID for sexAttrId (Male=69509891711, Female=69509894381,
Unknown=69509886562).


THE MECHANISM (confirmed working -- HIDLE test 2026-04-17)
-----------------------------------------------------------
Three-layer chain:

  1. Form field: attributeTypeId=SEX, codeTypeProvider=NIBRS
     -> User selects from dropdown. Form stores the attribute ID as the value
        (e.g. Female = 69509894381).

  2. CommSys QIDM SexCode attribute: codeTypeProvider=NIBRS
     -> Performs reverse lookup: attribute ID 69509894381 -> NIBRS code "F"
     -> CommSys XML: <SexCode>F</SexCode>  [CORRECT]

  3. RMS QIDM sex attribute: useAttributeId=True
     -> Receives the attribute ID and passes it through directly.
     -> RMS elastic: sexAttrId:"69509894381"  [CORRECT]

Confirmed with HIDLE (HI_HCJDC) on 2026-04-17:
  - Male selected:   CommSys <SexCode>M</SexCode>,  RMS sexAttrId:69509891711
  - Female selected: CommSys <SexCode>F</SexCode>,  RMS sexAttrId:69509894381
  - Both correct simultaneously for active user selection (not just initialValue).
  - HIDLE initialValue=M is NOT the mechanism -- female test proved the conversion
    is real and general, not a pre-set string bypass.


RESOLUTION (2026-04-17) -- FULLY CONFIRMED
------------------------------------------

reverse lookup works for all providers without separate admin registration.

on form, codeTypeProvider=NIBRS on QIDM SexCode attribute, useAttributeId=true on RMS.

Confirmed working on NJ_NJCJIS (2026-04-17, v3.25): same configuration.

FUNDAMENTAL CONSTRAINT (confirmed after Options A-S)
-----------------------------------------------------
For NJ_NJCJIS, two form configurations are possible:

  codeTypeCategory=NIBRS_SEX, codeTypeSource=NIBRS
    -> Form stores NIBRS code "M"/"F"/"U"
    -> CommSys XML: <SexCode>M</SexCode>  [CORRECT]
    -> RMS useAttributeId=True: receives "M", cannot convert to attribute ID  [FAIL]

  attributeTypeId=SEX (with or without codeTypeProvider=NIBRS)
    -> Form stores numeric attribute ID (69509891711)
    -> CommSys XML: <SexCode>69509891711</SexCode>  [FAIL -- no NJ registration]
    -> RMS useAttributeId=True: passes attribute ID through  [CORRECT]

These two paths are mutually exclusive without platform registration.
No rule handler, prop ordering, or codeTypeProvider variant resolves this.
The fix is the admin registration task below -- no engineering required.
