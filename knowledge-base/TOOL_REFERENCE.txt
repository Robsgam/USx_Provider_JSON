TOOL REFERENCE -- the WHY behind each shared tool
=================================================

Relocated verbatim from the CLAUDE.md Tools table on 2026-09-08, because CLAUDE.md
had grown to 156,874 chars against a 150,000-char load limit and the Tools section
alone was 53% of the file -- meaning the TAIL of CLAUDE.md (the new-provider Quick
Start, whose Step 0 is the naming gate) was at risk of never reaching context.

NOTHING WAS DELETED. Each section below is the original table cell, verbatim. The
CLAUDE.md table keeps each tool one line -- purpose + flags -- and points here.
Read this file when deciding whether a gate PASS is evidence, when a finding looks
novel, or before changing a tool: the incident that produced each rule is recorded.

Index: the CLAUDE.md Tools table. Flags: still in CLAUDE.md, not repeated here.

  build_report.ps1
==============================================================================
**Master orchestrator** — always runs 1, 5-9 + saves reports to docs/, then prunes orphaned variant reports (build-owned report files for a JSON variant no longer present — e.g. after consolidating branches). Pass `-IncludeExtended` to also run 2-4 (layout/query/picklist reports) plus 10-11, lint/label-review/officer-guide/test-conductor (8 advisory outputs demoted from the default run 2026-07-06 -- nothing gates on them)

  doctor.ps1
==============================================================================
**ONE-SHOT HEALTH DASHBOARD** -- read-only snapshot: score_all -Quick + poisoned-array sweep (validate G-31) + git status + reverse-propagation status + variant sync + PS-5.1 parse + **suppression scope / tool portability / provider linkage** (the three repo-scope advisories, added 2026-08-02 -- they were ORPHANS that no orchestrator ran, so their findings only surfaced if someone thought to ask)

==============================================================================
  audit_variant_sync.ps1
==============================================================================
Base↔variant lockstep drift check. For each provider declaring `# BASE-SYNC: <BASE> vX.Y` in its build script (marker-driven, no name-heuristic false positives), flags drift if the marker is behind the base's current version. Catches the class where a variant (CCH) silently falls behind its base (TX_TLETS). Composed into doctor.ps1. See "Provider Variants". **CHECK 2 -- ADJUDICATION-REGISTRY DRIFT (added 2026-08-24), because CHECK 1 compares the VERSION MARKER and nothing else.** It answers "was the base-6 re-synced?", never "did the base's REASONING come with it?". TX_TLETS_CCH read `[PASS]` here -- marker current at v4.21 -- while carrying a stale SUBSET of TX_TLETS's `ACCEPTED_DIVERGENCES`: **8 base rows absent, 4 of them producing live `audit_requirement_fidelity` OVER-PERMITTED findings the base had closed on 2026-07-30**. Same metadata XML (byte-identical), same devdoc, same combinations, opposite verdicts -- and **the marker being CURRENT is exactly what made it invisible**. Scoped by BUILT QUERY (a base row for a query the variant does not build is not drift). **Not-inheriting is often the RIGHT answer, so a decision recorded as a COMMENT naming the keyRef + field reports `[NOTE]`, not `[FAIL]`** -- copying a base row is NOT always safe: an EXISTENCE-class rule (`shadow`/`unbuilt`/`dead-combo`) makes fidelity skip that keyRef's ENTIRE comparison, so inheriting one can DROP branches while the finding count still reads 0. Three TX rows are deliberately not inherited: two name keyRefs that ARE built, and `RSDWW` -- which I expected to be free because it appears ZERO times in the JSON, and **measured at 36 -> 35 branches**. "The keyRef is not built" is NOT sufficient licence for an existence-class row; measure the denominator, do not reason about it. LAW 2 proven four ways: PASS clean, FAIL on a removed row (naming it), `[NOTE] DID NOT RUN` on a missing registry, PASS on restore. Baseline 2026-08-24: **1 variant / 23 base rows in scope / 20 inherited / 3 recorded / 0 DRIFTED**

==============================================================================
  emit_decision_trail.ps1
==============================================================================
**THE REASONING POINTER FOR A RESTARTED SESSION** — third SessionStart hook, injected after `SESSION_STATE.md`. That file restores STATE and `usx-resume` restores ENVIRONMENT, so a new session knows *where* things stand; neither restores JUDGEMENT, which is what a long session actually accumulates. The richest record of it — commit BODIES — was the one thing no session ever opened. Prints the last N commit subjects as an index, then surfaces the self-correction lines from their bodies verbatim (cues: `THE LESSON`, `PROCESS NOTE`, `GOT ... WRONG`, `NEARLY`, `was wrong`, `HONEST ABOUT`, …), skipping wrapped-line fragments so each reads as a complete thought. Derived fresh from git every run — **never hand-maintained, so it cannot go stale, and it duplicates nothing.** Deliberately NOT folded into `SESSION_STATE.md`, which is capped ~120 lines and is current-state-only by design

==============================================================================
  audit_wiring_closure.ps1
==============================================================================
**FORM <-> QIDM WIRING CLOSURE** — the direction nothing else checks. Every other gate validates the REQUEST against an AUTHORITY (devdoc, metadata, reachability, logs); none asks whether every officer-visible control actually reaches the wire, and whether every wired field has somewhere to type it. Five silent breaks: **A** dead control (officer input discarded), **B** orphan attribute (nothing can populate it), **C** unfillable requirement (no human can satisfy the combo), **D** inert condition (routing gate that never changes anything), **E** inert default (never applied). Exists because CA_SAN_LUIS_OBISPO shipped a VISIBLE prefilled "Purpose Code (DH)" control that was in no combination's `any[]` — silently discarded on every DH query, with validator/verify_build/audit_metadata/audit_cad/reachability/fidelity/spec-plan all green. Counts RMS QIDMs as reaching the wire (they are form-fed too) and excludes CAD/FR context controls

==============================================================================
  audit_name_components.ps1
==============================================================================
**METADATA COMPONENT -> FORM CONTROL COVERAGE** — the authority→built direction at COMPONENT granularity, and the twin nobody built. `audit_devdoc_combinations` closes this gap for COMBINATIONS; every other gate enumerates the JSON and is therefore closed under what we built, so **a metadata-defined name component with no control generates no control to audit, no attribute to orphan, and — because the plan is derived FROM the JSON — no test that can fail.** It cannot be found by looking harder at what exists. **Cost of not having it (2026-08-17): 15 of 20 providers ship NO middle-name and NO suffix control** while their own metadata declares request `Name` with four components (First/Last/Middle/Suffix) on the queries we built — all 15 at `0 FAIL / 0 WARN`, four of them (NJ/FL/IL/CA_CLETS) tenant-verified ALL-PASS. **Worse, 6 of those controls were DELETED on 2026-08-02** after `audit_wiring_closure` correctly reported them unwired: that gate walks JSON→JSON so it can say a control is *useless*, never that one is *MISSING*, and its answer was misread as "should not exist". **Capability is wire-PROVEN, not theoretical** — AZ_AZDPS v3.11, 10 captures: `FormatStringRuleHandler` emits `DOE, JOHN A JR` and degrades cleanly (`DOE, JOHN JR`, no double space). ⚠️ **SCOPE IS DERIVED — do not "simplify" to a name whitelist.** `First+Last+Middle+Suffix` is a GENERIC TYPE SIGNATURE stamped on 100+ non-person fields (`ChemicalName`, `SchoolName`, `AddressStreetName`, `EnhancedNameSearchIndicator`; one is nonsense — `SupervisorName :: Day+Month+Year`), and component-count is never control-count in general (`Day+Month+Year` composites → ONE FormDate). Filtering to composites **referenced by a BUILT transaction's combinations** leaves EXACTLY ONE field, `Name`, with zero noise across 125 built transactions — so it self-extends to any future composite. **Resolves the control through the attribute's own `sourceField`, never a token search of the form**: Person carries TWO name pools (DL + DH-suffixed) on the SAME entity, and an entity-wide match reported HI's DL against `nameMiddleDH`. Three classes: **C1 no-control** (officer cannot enter it) and **C2 not-composed** (control absent from the composite `sourceField`) BLOCK; **C3 not-in-pool** (composed but in no `set[]`/`any[]`) is `[NOTE]` only because its impact is **UNPROVEN** — `audit_wiring_closure` class A requires "no attribute sources it **AND** no combo references it", so it deliberately calls HI closed, and neither position has a committed log. Settle C3 with ONE HI DL query filling middle+suffix. 0 components compared = `[FAIL]`. Baseline 2026-08-17: **20 compared / 216 components / 80 C1 / 0 C2 / 4 C3** — clean on AZ, NY, TX, TX_CCH

==============================================================================
  audit_sqvr_integrity.ps1
==============================================================================
**SQVR TRUTH GATE** (enforce 2j) -- the SQVR is hand-maintained prose asserting which combos exist/how many/what version, and nothing verified it, so it rotted on every combo add-remove; it's also what a tester reads to decide what to test. Checks SQVR-named keyRefs exist in the JSON (blocks/sections marked DORMANT-REMOVED-NOT BUILT-OUT OF SCOPE report [NOTE]), stated combo/QIDM totals match, and stated JSON version matches. Does NOT require every combo to have a block (13 providers use a lighter format). **CHECK 2 PRINTS ITS DENOMINATOR (2026-08-10, LAW 2):** the totals check matched three EXACT phrasings and therefore compared **nothing on 17 of 20 providers** while still printing `[PASS] SQVR consistent with the JSON` — a vacuous pass on the one thing this gate exists for. Caught on HI_HCJDC_OFML, which wrote `Total combos: 12 CommSys` (the word *after* the number, so every pattern missed) and had asserted **17 combos against a JSON holding 12**, plus `CONFIRMED: none on v4.6` / `PENDING: ALL 5 entities` on a provider tenant-verified ALL-PASS twice — through nine version bumps. Now: grand-total detection accepts every phrasing the portfolio uses and CHECK 2 emits an explicit `[NOTE] CHECK 2 DID NOT RUN` for the 13 SQVRs asserting no total, instead of contributing silence to a PASS (making it a FAIL was rejected — it would redden 13 providers for a sentence they never wrote). **The phrasing trap, do not "simplify" this:** NJ_NJCJIS writes `Total combos: 5 QIDMs / 8 combos`, so the obvious `Total combos:\s*(\d+)` captures the **QIDM** count and false-FAILs; the digit immediately PRECEDING "combos" wins, with `combos:\s*(\d+)` only as fallback. Never match a bare `(\d+) combos` — every SQVR carries per-entity section counts. Coverage 3 -> 7 providers compared (8 assertions); surfaced exactly one real finding, FL_FCIC 31-vs-30, flagged `[FLAG:sqvr-totals-denominator]` for FL's own next rebuild

==============================================================================
  audit_log_metadata_attribution.ps1
==============================================================================
**WHICH COMBO DOES THE WIRE SAY THIS IS? -- the log-stage direction that closes the feedback loop** (Rob 2026-09-02, during the CA_CLETS_OCATS v2.12 sweep: *"be sure the logs are matched to a query combo independently of the original metadata sweep used to build it. we don't want a deaf feedback loop."*). The two existing log gates each sit on one side of that loop and neither can answer it: **2i** attributes but replays the log's QUERY STRING through **OUR** combo array, so a wrong array is confirmed rather than caught; **6d** is genuinely metadata-driven but only asks SATISFACTION -- its matcher breaks on the FIRST satisfying combo and throws away *which one* (`$matched = $true; break`), so it can never say the wire belongs to a DIFFERENT combination than the log claims. This one computes the attribution from **the wire + the raw XML only**, then uses the JSON purely as a DICTIONARY (combo name -> its declared `set[]`, resolved through the QIDM attribute map) because the wire carries no keyRef to compare against. **AGREE** iff the filed combo's declared required set IS one of the metadata alternatives the wire satisfies; **DISAGREE** (blocking) iff the wire does not satisfy that set at all; **NO-LABEL** (blocking) iff the name matches no built combo -- *that was a NOTE in the first draft and is exactly how the LAW 2 mutation SURVIVED*, landing in NO-LABEL while the gate printed PASS. ⚠️ **THE COMPARISON AXIS IS THE REQUIRED SET, NOT `primaryFieldReference` -- the first draft used PF and produced 22 FALSE DISAGREEs across 4 providers**, the shape that means the probe is broken: a metadata combination carries ONE PF label across ALL its `<Choice>` alternatives (TX's `ArticleSingleQuery` has a single combination labelled `ArticleSerialNumber` whose branches are `[NCICNumber]` and `[ArticleSerialNumber, ArticleTypeCode]`, correctly split into two built combos), DH-suffixed pools compare unequal as strings, and some combinations declare no PF at all. Resolving `set[]` through the attribute map fixes the DH case for free -- no suffix hack. ⚠️ **`_strip_` TESTS ARE EXCLUDED AND COUNTED:** a strip test deliberately neutralises a field to prove RE-ROUTING, so its filename names the combo tested *against*, not the one that fired -- proven on NY_NYSPIN_EJUSTICE, whose ordinary OOS tests fill `RegistrationState="Georgia"` -> wire `<State>GA</State>` while both `_strip_` tests fill **"New York", NY's own home state**, and the wire correctly carries no State at all. Baseline 2026-09-02: **13 providers / 791 logs / AGREE 716 / DISAGREE 0 / NO-LABEL 0 / AMBIGUOUS 73 / STRIP-EXCLUDED 2**. AMBIGUOUS = the built combo declares a set that is a legitimate tightening of a metadata alternative (TX Boat adds `State`); that class is `audit_requirement_fidelity`'s, not re-litigated here. LAW 2 proven by copying a plate-wire log under a VIN combo's name -> KILLED, and re-proven after the `_strip_` exemption was added

==============================================================================
  audit_log_combo_attribution.ps1
==============================================================================
**LOG ATTRIBUTION GATE** -- did each saved log's NAMED combo actually fire? The wire XML carries no keyRef, so this was unverifiable and a green package could overstate coverage (17 of 417 logs were filed under combos that never ran, found 2026-07-29). Replays each log's recorded QUERY STRING (routing is existence-based, so field presence decides the winner) through the owning QIDM in array order, using the canonical `_sim_helpers` predicate. Scopes the QIDM by the log header's QUERY NAME, never bare keyRef (they collide across QIDMs -- BUILD_RULES 13). Stale logs on registered `dead-combo*` divergences report [NOTE]

==============================================================================
  audit_combo_reachability.ps1
==============================================================================
**DEAD-COMBO GATE** (fill-independent) -- the platform fires the FIRST matching combo, so combo A is unreachable if a B ordered before it matches whenever A does. Silent case: B's extra `set[]` fields are all form-prefilled (`initialValue`), so B always wins. Such a combo still validates, still counts toward coverage, and can carry a PASS log -- the wire XML has no keyRef, so a log named for A can't be distinguished from one where B fired. Counts only form `initialValue` as always-present; resolves EXISTS/NOT_EXISTS on prefilled fields; skips RMS cascades. `dead-combo*` accepted divergences report [NOTE] not [FAIL]. ⚠️ **Its "N combination(s) checked" is NOT a combo count — never cite it as one.** It reports what it COMPARED, which is systematically lower than the provider's combo total (HI_HCJDC_OFML 10 checked vs 12 combos; IL_LEADS_OFML 7 vs 9). For a combo total use `audit_test_coverage.ps1`'s `Total combos (CommSys): N`, which counts them from the emitted JSON. Reading the two as the same number produced three conflicting answers for HI in one session (16 / 12 / 10) and is what exposed the vacuous SQVR totals check

==============================================================================
  audit_prefill_shadow.ps1
==============================================================================
**WHICH PREFILL KILLED THE COMBO** -- BUILD_RULES 24 at the CAUSE, not the consequence. 24 has said since the 35-combos-across-6-providers incident that a form `initialValue` on any `set[]` field makes it always-present and hides every combo needing its absence; **nothing enforced it**. `audit_combo_reachability` reports the dead combo AFTER the fact and never says why, which makes it read as a design trade-off you can accept -- on AZ_AZDPS v3.7 exactly that happened: prefilling `ImageIndicator`, `Requestor` and `dexStateUserId` (three `set[]` fields in ONE version) collapsed `DQPN`->[NameLast,NameFirst]==`DQN`, `DQP`->[OperatorLicenseNumber]==`DQ`, `ACQB`->[RegistrationNumber]==`BQ`, `ACQBH`->[BoatHullIdNumber]==`BQH` -- four EXACT collisions no ordering can separate -- and the responses proposed were to delete or register the losers (Rob: *"we do not leave out queries because it is hard ... use ordering and recognize the shadows"*). The fix was to un-prefill the discriminators metadata already supplied. **THE RULE IS NOT "no prefill on a set[] field"**: for an ordered pair (A before B) it FAILs only when A shadows B on the VARIABLE sets (set[] minus prefilled) AND the subset relation does NOT already hold on the raw `set[]`s -- so a structural shadow stays reachability's, and a prefill present in EVERY combo's `set[]` cancels out of both sides and is spared (CA_CLETS `purposeCode`, AZ `dexStateUserId`). Honours mutually exclusive EXISTS/NOT_EXISTS gates. FAILs a zero-pair run. Baseline 2026-08-05: **20/20 clean, 645 ordered pairs compared**; proven to FAIL by re-injecting the ImageIndicator prefill (2 FAIL, naming both pairs and all three culprits)

==============================================================================
  audit_gate_efficacy.ps1
==============================================================================
**MUTATION TESTING FOR THE GATES** (LAW 2 -- a gate that cannot fail is not a gate). Injects each known defect CLASS into a throwaway replica and checks the owning gate actually FAILs. KILLED=its PASS is evidence; SURVIVED=that gate is blind, its PASS proves nothing for that class. Catalogue is hand-authored, so its score is bounded by what we thought of -- pair it with `fuzz_gate_efficacy.ps1`. ⚠️ **`[INVALID]` IS A FINDING, NOT A SKIP -- ENGINEERING_STANDARD 5 requires 0 INVALID as well as 0 SURVIVED, because a step that did not run is not a pass and a STALE MUTATION IS INDISTINGUISHABLE FROM A BLIND GATE.** Fixed 2026-09-02: `codetype-select-as-input` hunted three hardcoded fieldIds (`relatedHitSearchIndicator`/`ImageIndicator`) and threw when none existed -- which is the case on **ALL SIX CA providers**, none of which builds an `ImageIndicator` control (correctly -- it is absent from their metadata). Measured: **6 of 20 reported `[INVALID]` while each carries 5-6 perfectly valid `codeTypeCategory` FormSelects**, so `validate.ps1`'s codeTypeCategory branch had **never been efficacy-proven on a single CA provider**. Now falls back to `Get-CodeTypeSelectNode` -- selects on the PROPERTY the rule is about, so it self-extends to any future dropdown -- and prefers the historic fieldIds first so the 14 already-covered providers stay byte-identical. CA_SAN_LUIS_OBISPO 8/8+1 INVALID -> **9/9 / 0 SURVIVED / 0 INVALID**; CA_CLETS likewise 0 INVALID. **Two pre-existing rows on NJ_NJCJIS are NOT this change** (verified by re-running at HEAD with the edits stashed -- identical `12/13, SURVIVED 1, INVALID 1`): `nj-guardrail-wire-leak` SURVIVED on `audit_log_content`, and `vehiclemake-as-input` INVALID is the documented N/A (NJ builds no `VehicleMakeCode` field at all)

**`[N/A]` IS NOW A SEPARATE VERDICT FROM `[INVALID]` -- added 2026-09-09, and before it the bar was un-clearable noise.** `INVALID` carried two opposite meanings: **STALE** (the mutation used to create its defect and no longer can -- a real problem, since a stale mutation is indistinguishable from a blind gate) and **NOT-APPLICABLE** (this provider legitimately has no such construct, so there is nothing to mutate -- not a problem, and "fixing" it means BUILDING something the provider's own authority does not call for, i.e. the OVER-BUILD class). ENGINEERING_STANDARD 5 requires 0 INVALID, so with both in one bucket that bar was **unreachable** on any provider with a legitimate N/A -- precisely the un-clearable FAIL LAW 2b calls noise. A mutation now declares `NaIf={}` + `NaWhy`, evaluated BEFORE `Valid={}`; silence still reads as STALE, N/A is counted and printed in the totals **even at 0** (so "none" is distinguishable from "this build does not report them"), and only SURVIVED or INVALID(stale) exit non-zero.

**NJ_NJCJIS closed this way: `KILLED 12/12, SURVIVED 0, INVALID(stale) 0, N/A 2`** -- both of its long-standing INVALIDs were N/A, not stale. (1) `vehiclemake-as-input` -- NJ and HI build no `VehicleMakeCode` control at all. (2) `nj-guardrail-wire-leak` -- **UNHOSTABLE PORTFOLIO-WIDE, MEASURED not assumed.** A `-Path` mutation can only change the winner's POOL; the losing ids, the winner ids and the wire all come from the plan and the committed logs, which `-Path` does not touch. So a pool removal can only FAIL when a losing identifier is ON THE WIRE and exempted ONLY by the pool -- and a 20-provider sweep of every guardrail plan test found **ZERO** such cases (NJ Vehicle `RANDFULL` sends no VIN; NJ Person `FULLN` sends no Name). The earlier instruction "re-aim at Vehicle or Person" is therefore **impossible**, and adding a Boat guardrail test to NJ is still wrong (its devdoc permits `RegistrationNumber` on the hull query, so winner-only XML would FAIL on a correct build). ⚠️ **The pool exemption itself STAYS:** it guards against a FALSE FAIL when a provider legitimately rides an optional identifier along -- inert is not dead. What is no longer true is that any mutation proves that guard works.

**FULL 20-PROVIDER BASELINE, 2026-09-09 -- and the headline number is not the interesting one.**
`KILLED n/n · SURVIVED 0 · INVALID(stale) 0` on **all 20**, with N/A on 4 (HI 1, LA_LEMS 1, NJ 2,
OR 1). So the `0 SURVIVED / 0 INVALID` bar is met portfolio-wide. ⚠️ **BUT THE MUTATION COUNT IS
WILDLY UNEVEN, AND A CLEAN SCORE ON A THIN CATALOGUE IS NOT PROOF:** of 47 catalogued mutations,
**IL_LEADS_OFML has 12, TX_TLETS 10, NJ_NJCJIS 6, FL_FCIC 5, and AZ / CA_SAN_LUIS_OBISPO / HI /
NY / OR one each** — plus 9 GLOBAL. Measured mutations-run per provider: IL 20, TX 18, NY 16, FL 13,
NJ 12 … and **fifteen providers run 7-9**, essentially the globals alone. Those fifteen reach
"0 survived / 0 stale" cheaply because almost nothing was ever aimed at them. `build_phase1` step 6
now emits a COVERAGE shortcoming when ≤9 mutations ran, so the thinness is stated rather than
hidden behind a flattering ratio. **The next real work on this gate is aiming mutations at the
fifteen, not celebrating the 20/20.**

**TWO DEFECTS FOUND BY RUNNING THE SWEEP, both in the reporting path rather than in any gate:**

1. **`build_phase1` step 6 WAS BLIND TO STALE MUTATIONS.** It parsed only
   `KILLED (\d+) / (\d+)\s+SURVIVED (\d+)` and never read INVALID, so ENGINEERING_STANDARD 5's
   "0 INVALID as well as 0 SURVIVED" could not be enforced by the orchestrator that OWNS PHASE 1 --
   a mutation could rot, read `[INVALID] STALE` standalone, and PHASE 1 would print a clean "n/n
   killed" line. **A bar no orchestrator reads is not a bar.** Now parsed and reported separately
   from SURVIVED, because the two demand OPPOSITE actions: a survivor means FIX THE GATE, a stale
   mutation means FIX THE MUTATION. ⚠️ Both counts are **anchored to the totals line** -- a bare
   `N/A (\d+)` takes the FIRST match anywhere and an `[N/A]` reason line containing a number
   hijacks it (proven with a decoy: loose read `na=99` off a narrative line, anchored read `na=2`).

2. **THE HARNESS COULD ABORT MID-SWEEP AND THEN MIS-DESCRIBE ITSELF.** During the 20-provider run
   TX_TLETS died after 4 of its 18 mutations with `NativeCommandError` at `Run-Gate`, and it was
   **not reproducible** -- TX ran 18/18 clean immediately before and after. Cause: the script sets
   `$ErrorActionPreference='Stop'`, and **under PS 5.1 a native command that writes ANYTHING to
   stderr raises a terminating error**, so one transient line from a child gate kills the run. The
   damage is what it LOOKS like: no totals line, so `build_phase1` falls to its else branch and
   reports *"no mutation map for TX_TLETS -- its green gates are UNPROVEN"* on a provider with 18
   working mutations. Fixed by scoping `Continue` around the child invocation -- stderr from a child
   is DATA here, not an exception. **PROVEN ON 5.1, and the engine matters:** the same control under
   **pwsh 7 did NOT abort at all** (`completed, 77 chars`), so a proof run there would have been
   vacuous; on `powershell` 5.1 the before-case reports `ABORTED -- RemoteException` and the
   after-case completes while still seeing the child's `[FAIL]`. Same defect class as the Edge-stderr
   fix in `audit_extension_syntax` the same day.

**The regression check that matters is that N/A DISCRIMINATES rather than blanket-excusing:** CA_CLETS reports `N/A 0` because it HAS a `VehicleMakeCode` field, so the mutation runs and KILLS; HI and NJ report `N/A 1` because they genuinely build none. LAW 2 for the split itself was proven with a temporary injected control (`Valid={$false}`, no `NaIf`) -- it forced **exit 1**, confirming a stale mutation still blocks and that N/A did not swallow the stale path

==============================================================================
  fuzz_gate_efficacy.ps1
==============================================================================
**RANDOM mutation testing** -- what the hand-authored catalogue structurally cannot do. Mutation sites are ENUMERATED FROM THE JSON (set↔any, drop, over-permit from a sibling combo, drop-conditions, swap-order, prefill, Select→Input), aimed at nothing; the whole gate panel runs and the only question is whether ANY gate reacted. Survivors are CANDIDATES needing triage, not verdicts. `-Seed` makes runs reproducible. Wired into `build_phase1` step 6b

==============================================================================
  audit_log_inflation.ps1
==============================================================================
**COVERAGE-INFLATION ATTACKS** -- every other log gate asks "is what we sent correct?"; none asked "are these N logs actually N DISTINCT tests?". Four attacks: **A** clone (identical wire XML counted twice), **B** fingerprint drift (JSON rebuilt in place without a version bump, so the log is stale while its filename reads current), **C** orphan wire field (predates a rename), **D** degenerate guardrail (competing identifiers filled with the SAME value proves nothing). ⚠️ **ITS 2026-07-31 BASELINE OF "0/0/0/0 over 434 logs / 6 providers" WAS TWO KINDS OF FALSE, both fixed 2026-08-18.** (1) **Attack A COULD NOT FAIL.** Every wire carries a unique transaction id — as an `<Id>` ELEMENT *and* an `id="..."` ATTRIBUTE on `<api:Transaction>` — so no two logs ever hashed alike and `[A CLONE] none` was vacuous on every provider, every run, since the check was written. Both forms are now normalised out, and the key folds in the FILL-SET, because a clone is *same input AND same output*: a PASSING guardrail legitimately reproduces its base test's wire (that identity is the evidence), and keying on wire alone flagged 50 such pairs as defects. (2) **The default scope was a HARDCODED SIX**, so `AZ_AZDPS` and `IL_LEADS_OFML` — both tenant-verified — had never been examined at all; widening it found AZ **4** and IL **1**. It takes `-Providers` not `-Path`, so `audit_tool_portability` never covered it either.
