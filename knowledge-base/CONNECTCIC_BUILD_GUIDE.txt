STARTING A NEW JSON PROJECT
================================================================================

PROMPT TO START A BUILD FROM SCRATCH
-------------------------------------
"We are going to build [PROVIDER_NAME].json from scratch using [PROVIDER].XML as
the field and combination authority (MetaData wins over PDF when they disagree).
Use [PROVIDER].pdf as secondary reference for field descriptions and business context.
Use HIDLE.json as the structural template, and CA_ESUN.json and NY_NYSPIN_EJUSTICE
as reference for form layouts and field naming conventions. Use NY_NYSPIN_EJUSTICE
build scripts as the pattern reference for helpers and versioning.

Create the folder C:\Users\RobSgambellone\.local\bin\[PROVIDER_NAME]\ with the
standard structure: scripts/, docs/base/, docs/mc/, source/, phases/base/logs/,
phases/mc/logs/. Move source files (XML, PDF, HIDLE.json) to source/.
Create the build script at scripts/build_[provider].ps1 with -Version and -Phase
parameters (Phase default='base'). Create scripts/validate_[provider].ps1.
Create docs/[PROVIDER]_STATUS.txt and docs/[PROVIDER]_BUILD_NOTES.txt at docs/ root.
Run devdoc cross-check (PDF vs XML) and save to docs/base/DEVDOC_CROSSCHECK_*.txt.

Build [PROVIDER_NAME].json targeting [target system description]. Start at v1.0."

WHAT TO GATHER BEFORE STARTING
--------------------------------
Required:
  [PROVIDER].XML   -- sole source of truth for field names, sizes, keyRefs, combinations
  [PROVIDER].pdf   -- field classification (M/C/O), valid values, combination definitions
  HIDLE.json       -- structural template (bundle layout, rule handlers, RMS)

Reference (read-only, for patterns):
  CA_ESUN.json     -- single-card QUERYINPUTFORM layouts
  FL_FCIC.json     -- GunQuery sourceField naming, single-card multi-combination pattern
  NJ_NJCJIS.json   -- most complete ConnectCIC build to reference

PDF vs XML GAP CHECK  (required at standup -- before first build)
------------------------------------------------------------------
SCOPE RULE: Always compare the PDF section named "Basic Queries Supported" only.
Do not include entry, cancel, clear, WMP-I, wanted/missing, or any other
non-query transactions. This rule applies to both the gap report and the build.

Produce two output files in docs/:

  [PROVIDER]_PDF_XML_GAPS_SUMMARY.txt    -- Vendor-ready. Plain language, no internal
                                            notes or build decisions. Uses "DevDoc"
                                            for PDF references and "MetaData" for XML
                                            references throughout.
                                            Send to CommSys/vendor to resolve before building.

  [PROVIDER]_PDF_XML_INCONSISTENCIES.txt -- Internal detail. Full technical comparison,
                                            build decisions, summary table, live test
                                            priority list. Also scoped to Basic Queries only.

PROMPT TO RUN THE GAP CHECK
  "Read [PROVIDER].xml and [PROVIDER].pdf. In the PDF, find the section named
  'Basic Queries Supported' and extract only the transactions listed there.
  Compare those transactions against the XML. Identify:
    1. Transactions in the Basic Queries section that are not registered in the XML.
    2. Fields documented in the PDF but absent from the XML for those transactions.
    3. Fields where the PDF and XML disagree (size, required vs optional, present vs absent).
    4. Combination structure differences between PDF and XML.
    5. Any MessageKey conflicts (keyReferences shared across multiple transactions).

  Do not include entry, cancel, clear, WMP-I, wanted/missing, or any transaction
  outside the Basic Queries Supported section.

  Create two files in docs/:
    [PROVIDER]_PDF_XML_GAPS_SUMMARY.txt        -- simple numbered list, vendor-ready,
                                                  no internal notes or build decisions.
                                                  Use 'DevDoc' instead of 'PDF' and
                                                  'MetaData' instead of 'XML' throughout.
    [PROVIDER]_PDF_XML_INCONSISTENCIES.txt     -- full technical detail with build
                                                  decisions, field-by-field analysis,
                                                  summary table, and live test priority list.
                                                  Scoped to Basic Queries only."

WHAT TO DO WITH THE OUTPUT
  - Send [PROVIDER]_PDF_XML_GAPS_SUMMARY.txt to the vendor (CommSys or equivalent).
  - Use [PROVIDER]_PDF_XML_INCONSISTENCIES.txt to decide what to include vs exclude
    during the build. XML is the build authority; DevDoc-only fields are excluded by
    default unless confirmed working on a live connection.
  - Flag any missing transactions in LIMITATIONS.txt immediately.

SCOPE REMINDER FOR THE BUILD
  The JSON build itself is also scoped to Basic Queries Supported only.
  Do not build configurations for entry, cancel, clear, or non-query transactions
  unless explicitly requested.

KEY DECISIONS TO MAKE UP FRONT
--------------------------------
  1. State field name: check the XML -- NY uses "State", NJ uses "RegistrationState"
  2. Entity tab order: default=[Person,Vehicle,Firearm,...] vs CAD/FR=[Vehicle,Person,...]
  3. Per-entity form layout: single card (recommended) vs sections variant
  4. Which queries are in the XML? (Gun, Vehicle, DL, DH, Boat, Article, Wanted, Missing, etc.)
  5. Any queries requiring server-side registration first? (flag in LIMITATIONS.txt)
  6. Does this provider need split NJ/OOS entity tabs? (adds state field complexity -- see below)
  7. Person form architecture: 2-form (DL only) or 4-form (DL+DH+NCIC)?
     Check MetaData for: DriverHistoryQuery? WantedPersonQuery? MissingPersonQuery?
     Separate DL Name transaction (like NyNyspinDriverLicenseNameQuery)?
  8. Name field structure: does MetaData accept NameMiddle + NameSuffix?
     YES -> FormatStringRuleHandler arguments=@(' ',' ',' '), sourceField=4 fields
     NO  -> FormatStringRuleHandler arguments=@(' '), sourceField=@('NameFirst','NameLast')
  9. OPERATIONAL IDENTITY FIELDS: does the provider XML include BadgeNumber (or similar
     officer identity field) in any query transactions?
     YES -> decide before writing a single form field:
       VISIBLE   -- officer types badge on every query (Inp 'BadgeNumber')
       AUTO-FILL -- badge resolved from officer RMS profile (InpH 'dexStateUserId')
     Ask the end user / deployment team. Do NOT default to visible.
     Auto-fill uses CommsysGetDexStateUserIdRuleHandler (already in AUTH config by default).
     QIDM BadgeNumber attribute sourceField becomes @('dexStateUserId').
     All combination set/any refs change from 'BadgeNumber' to 'dexStateUserId'.
     See BUILD_CHECKLIST.txt OPERATIONAL IDENTITY FIELDS and FIELD_RULES.txt Section 5.
     Confirmed auto-fill pattern: AZ_AZDPS v1.1 (2026-04-20).

      [string]$Version = "1.0",

FORM FIELD DESIGN RULES
================================================================================

FIELD TYPE SELECTION
---------------------
  Text field (free entry)  -> FormInput   (fieldId, label, maxLength from XML)
  Dropdown (code list)     -> FormSelect  (fieldId, label, codeTypeCategory + codeTypeSource or attributeTypeId)
  Date field               -> FormDate    (fieldId, label)
  Y-only flag field        -> FormInput   (NOT FormSelect -- FormSelect exposes N/U which may be invalid)

DEFAULTS
---------
  State dropdowns (OOS)    -> codeTypeCategory = 'NJ_NIBRS_STATE'; codeTypeSource = 'NJ_NIBRS'
                              Sends 2-letter state code. Safe for outbound XML and RMS.
  State dropdowns (in-state)-> Use dual-field pattern (see STATE FIELD ARCHITECTURE below)
  Image (optional Y/N)     -> YES_NO_UNKNOWN/NCIC; initialValue varies by query
  Boolean flag (Y-only)    -> FormInput, no initialValue (blank = not sent, operator types Y)
  Yes/No field             -> YES_NO_UNKNOWN/NCIC (Y/N only; NIBRS adds Unknown as 3rd option)

  DO NOT use attributeTypeId='STATE' for any field that maps to outbound XML.
  attributeTypeId='STATE' sends an internal numeric ID, not a 2-letter code. See below.

IMAGEINDICATOR PATTERN  (3 requirements -- all must be met)
------------------------------------------------------------
  1. Attribute size=1 in QUERYINPUTDATAMAPPING
  2. initialValue set on the FormSelect (Y for person by default, N for vehicle)
  3. Field included in set[] or any[] of each combination that should send it
  If any of these three are missing, ImageIndicator will not appear in the outbound XML.

RANDOMREQUEST PATTERN
----------------------
  Use FormInput, maxLength from XML, no initialValue.
  Do NOT use FormSelect -- YES_NO_UNKNOWN exposes N/U which are not valid values.
  Blank = not sent (correct -- operator types Y when needed).

SEX / RACE
-----------
  SexCode  -> codeTypeCategory = 'NIBRS_SEX';  codeTypeSource = 'NIBRS'
              DO NOT use attributeTypeId='SEX' -- sends internal numeric ID to XML (confirmed bug NY v1.2)
  RaceCode -> codeTypeCategory = 'NIBRS_RACE'; codeTypeSource = 'NIBRS'
              DO NOT use attributeTypeId='RACE' -- sends internal numeric ID to XML (confirmed bug NY v1.12)
              NCIC gives empty dropdown for NIBRS_RACE -- must use NIBRS source.

ARTICLE TYPE
-------------
  ArticleTypeCode -> codeTypeCategory = 'NCIC_ARTICLE_TYPE'; codeTypeSource = 'CA_CLETS'
  (codeTypeSource 'NCIC' gives an empty dropdown -- must be CA_CLETS)

================================================================================
STATE FIELD ARCHITECTURE
================================================================================

BACKGROUND
-----------
  attributeTypeId='STATE' on any FormSelect (visible or hidden) causes the platform
  to send the internal numeric attribute ID (e.g., 69509884952 for NJ) instead of the
  2-letter state code. This is correct for RMS elastic search but wrong for outbound XML.

  RMS elastic search also requires:
    - fieldId='RegistrationState' with an internal attribute ID for VIN/OLN queries
    - fieldId='LicensePlateNumberIn' (NJ) or 'LicensePlateNumberOut' (OOS) for plate queries
    - Using fieldId='LicensePlateNumber' (generic) does NOT trigger RMS plate search

NJ IN-STATE FORMS  (resolved pattern -- v3.12/v3.13)
------------------------------------------------------
  Two hidden fields serve different consumers:

  Field 1: SelH  fieldId='RegistrationState'    attributeTypeId='STATE'  initialValue='NJ'
           Role: RMS elastic search reads this field by fieldId and receives the attribute ID.
           Rule: Do NOT add to QIDM. This field never reaches outbound XML.

  Field 2: InpH  fieldId='RegistrationStateNJ'  initialValue='NJ'
           Role: QIDM sourceField for StateNJ attribute. Sends literal 'NJ' to outbound XML.
           Rule: Add to QIDM with targetField='State' (or provider's state element name).

OOS FORMS
----------
  Field: Sel  fieldId='RegistrationStateOOS'
              codeTypeCategory='NJ_NIBRS_STATE'  codeTypeSource='NJ_NIBRS'
         Role: Visible dropdown. Sends 2-letter state code to outbound XML.
         Rule: No attributeTypeId -- does not interact with RMS attribute lookup.
              Add to QIDM with targetField='State'.

  Note: NJ_NIBRS_STATE is an NJ-specific code list.
        Other providers may need a different codeTypeCategory for their state dropdown.
        Always confirm which source populates the state dropdown for the target provider.

KEYREFERENCE UNIQUENESS WITH NJ+OOS IN SAME QIDM
--------------------------------------------------
  When NJ and OOS combinations share one QUERYINPUTDATAMAPPING, each combination
  must have a distinct keyReference. Platform rejects duplicate keyReferences with:
  "Duplicate key references found in query input data mapping"

  Resolution: suffix NJ combinations with _NJ
    RQ_NJ   -- Vehicle NJ plate
    RQN_NJ  -- Vehicle NJ VIN
    DQN_NJ  -- Person NJ OLN
  OOS combinations retain their original names (RQ, RQN, DQN, DQ, BQ, BQN).

RMS PLATE SEARCH FIELDIDS
--------------------------
  fieldId='LicensePlateNumber' (generic)  does NOT trigger RMS plate search.
  fieldId='LicensePlateNumberIn'          triggers RMS plate search on NJ in-state forms.
  fieldId='LicensePlateNumberOut'         triggers RMS plate search on OOS forms.
  These fieldIds come from HIDLE.json pattern. QIDM targetField remains 'LicensePlateNumber'.

DEAD END -- IgnoreUserValueRuleHandler
---------------------------------------
  Tested in NJ_NJCJIS v3.10. Does NOT substitute argument value when sourceField is populated.
  Cannot be used to hardcode a state value. Do not retry. Use InpH with initialValue instead.

================================================================================
QUERYINPUTDATAMAPPING DESIGN RULES
================================================================================

COMBINATION DEFINITIONS
------------------------
  Read combination rules from XML first, then PDF.
  Each combination needs: keyReference, set[], any[], primaryFieldReference, state

  set[] = required fields for this combination to be considered a match
  any[] = optional fields that are included in the request when present
  Both set[] and any[] must include all fields you want sent with this query.
  Fields NOT in set or any of the matched combination are NOT sent.

  Mandatory (M) fields from PDF/XML -> always in set[], not any[]
  Optional (O) fields -> in any[]
  Conditional (C) fields -> in set[] of the combination that requires them

COMBINATION ROUTING PRIORITY
------------------------------
  First combination in the array takes priority when its set[] fields are present.
  Second combination fires only when first combination's set[] is not satisfied.
  Order matters -- put the most specific combination first.

FIELD ISOLATION
----------------
  If you need field isolation per query path (no cross-contamination):
    Option A: Two separate QUERYINPUTDATAMAPPINGs with distinct attribute lists.
              Risk: LIMITATION #2 -- platform may not auto-switch. Test before committing.
    Option B: One QUERYINPUTDATAMAPPING, multiple combinations (recommended).
              set/any controls which combination fires. Extra fields from other paths
              will be sent (LIMITATION #1) but server typically ignores them.

WHEN SPLIT CONFIGS ARE FORCED
-------------------------------
  If the XML assigns the same keyReference to two combinations in one transaction,
  the platform will reject it ("Duplicate key references found in query input data mapping").
  In that case, split into one config per keyRef -- but test LIMITATION #2 (auto-switch).
  If LIMITATION #2 confirmed real: merge paths and use the same combination structure
  as FL_FCIC (single config, multiple combinations, set/any for routing).

MULTI-QUERY PERSON FORMS (DL + DH)
------------------------------------
  Two architectures depending on whether DL and DH share one form or separate forms.

  SCENARIO A: DL + DH on the SAME Person tab (FL_FCIC pattern)
  Apply BOTH patterns. Pattern 1 alone is insufficient -- see WARNING below.

  Pattern 1 -- autoSelect + queriesToDeselect (mutual exclusion between QIDMs)
    Add to each QIDM:
      autoSelect: true
      queriesToDeselect: ["<other query name>"]
    Effect: when DH fires, DL is auto-deselected; when DL fires, DH is auto-deselected.
    Prevents double-query submission when both QIDMs are active.
    WARNING: Pattern 1 alone deadlocks when DL and DH share OLN fieldId on the same form.
      Both QIDMs match simultaneously; mutual deselect produces undefined behavior.
      ALWAYS pair with Pattern 2 on a shared form.

  Pattern 2 -- DH-specific fieldId suffixes (mutual exclusion within the form)
    DH form fields use suffixed fieldIds: NameFirstDH, NameLastDH, BirthDateDH,
    SexCodeDH, OperatorLicenseNumberDH.
    DL form fields use standard fieldIds: NameFirst, NameLast, BirthDate, etc.
    DH QIDM combinations reference the DH-suffixed fieldIds in set[].
    DH QIDM attributes map DH sourceFields -> standard targetFields in outbound XML:
      sourceField=NameFirstDH  -> targetField=Name (combined with NameLastDH etc.)
      sourceField=BirthDateDH  -> targetField=BirthDate
      sourceField=SexCodeDH    -> targetField=SexCode
    Result: DL and DH set[] reference different sourceFields -- cannot co-fire.
  Source: FL_FCIC.json production pattern.

  SCENARIO B: DL + DH on SEPARATE QIFs (NY_NYSPIN_EJUSTICE v1.16 -- CONFIRMED)
  CONFIRMED (NY v1.15/v1.16 live tests, 2026-04-14):
    Platform uses a SHARED field-value pool for ALL Person QIDMs regardless of which
    QIF sub-tab is active. Separate sub-forms do NOT isolate QIDM evaluation.

    queriesToDeselect is INEFFECTIVE IN BOTH DIRECTIONS:
      DL queriesToDeselect did NOT prevent DH from co-firing (v1.15 test).
      DH queriesToDeselect did NOT prevent DL from co-firing (v1.16 T7a test).
      Platform fires all matching QIDMs simultaneously before deselect can intercept.
      See PLATFORM_LIMITATIONS.txt #26 and ANTI_PATTERNS.txt #16.

  CORRECT DESIGN (v1.16 -- apply to all future builds with separate-form DL+DH):
    - DO NOT add queriesToDeselect to DL QIDMs.
    - Keep queriesToDeselect on DH QIDM only (deselects both DL QIDMs; no functional
      isolation benefit but no harm; DH sub-form visually unchecks DL checkboxes after firing).
    - DLIC + DALL always co-fire when OLN is present -- this is CORRECT police workflow.
    - DGRP (Name path) does NOT co-fire with DALL (DH needs OLN; Name path has no OLN).
    - queryLabel naming: 'Driver License (OLN)', 'Driver License (Name)', 'Driver History'
      Distinguishes multiple Person checkboxes in the UI.

  FORMS (4 QIFs under targetEntity='Person'):
    ENTITY_Person_DL_[State]  label='Driver License - [State]'  OLN + Name/DOB cards; hidden state InpH
    ENTITY_Person_DL_OOS      label='Driver License - OOS'      OLN+State visible + Name/DOB cards
    ENTITY_Person_DH          label='Driver History'            OLN + State + DH-specific fields
                                                                 (NyNyspinTransactionName/PurposeCode/Requestor)
    ENTITY_Person_NCIC        label='Person - NCIC'             Name+DOB+Sex+Race; fires WINQ+MINQ

  IF TRUE ISOLATION IS NEEDED (DH must never fire from DL form):
    Add OperatorLicenseNumberDH to the DH form and DH QIDM set[].
    DH set[] field is absent from shared pool when DL form is active.
    Pair with autoSelect + queriesToDeselect (Scenario A full pattern).
    This has not been tested in production -- use only if co-fire is operationally unacceptable.

  SCENARIO C: DL only, no DH (NJ_NJCJIS pattern)
  Single merged DriverLicenseQuery QIDM. autoSelect=true. No queriesToDeselect.
  2-form person: [State] + Out of State.

  PERSON FORM ARCHITECTURE DECISION:
    No DH in MetaData?          -> Scenario C (NJ pattern)
    DH in MetaData?             -> Scenario A or B
    WINQ/MINQ in MetaData?      -> 4-form (Scenario B) -- add NCIC form for wanted/missing
    Check MetaData DH Name path -> separate transaction? If yes, build it. If no, not implementable.

TEST LOG FORMAT
----------------
  Create a .txt log file for each test run. Use new_test_log.ps1 to generate a stub:

  NJ:
    powershell.exe -ExecutionPolicy Bypass -File scripts\new_test_log.ps1 `
      -QueryType VEH -Combination RQ -Description "plate only" -Version 3.23 -Phase 03_vehicle

  NY:
    powershell.exe -ExecutionPolicy Bypass -File scripts\new_test_log.ps1 `
      -TestNum T4 -QueryType VehicleRegistration -Combination RVIN `
      -Description "OOS VIN+State" -Version 1.12 -Phase 03_vehicle -Form "Vehicle - OOS"

  Output filename patterns:
    NJ: [DATE]_[QueryType]_[Combination]_[Description]_v[Version].txt
    NY: [DATE]_[QueryType]_[TestNum]_[Combination]_v[Version].txt
    NY investigation: [DATE]_[QueryType]_[TestNum]_[Combination]_[Topic].txt  (manual)
    NY batch/phase:   [DATE]_[QueryType]_[TN]-[TN]_v[Version].txt            (manual)

  Include in every log:
    - Date, JSON version, query type, test description
    - Fields filled by operator (Form, Fill, Fires)
    - Field analysis table (field, value, SENT/NOT SENT, note)
    - Raw XML request (paste from browser dev tools -- F12 > Network > Payload)
    - RMS JSON request (NY logs also include this)
    - PASS/FAIL and explanation

  Save to: phases/[NN_phase]/logs/

SUBMITTING LOGS TO CLAUDE
--------------------------
  Paste the raw XML directly into the prompt. Include:
  - What you filled in
  - What you expected vs. what you see
  Example:
    "Here is the request log for [test name]:
     [paste XML]
     I filled [fields]. Expected [X], got [Y]."

STANDARD TEST SEQUENCE PER QUERY TYPE
---------------------------------------
  T1: Minimum required fields only (cleanest request)
  T2: Required + one optional field
  T3: Required + all optional fields
  T4: All fields filled (edge case -- confirms LIMITATION #1 behavior)
  T5: OOS variant if applicable (State != home state)

SPLIT CONFIG TEST SEQUENCE (LIMITATION #2)
-------------------------------------------
  If using two configs for one query (e.g. _OLN and _Name):
  T1: Cold start, path A (fill only path A fields)
  T2: Cold start, path B (fill only path B fields)
  T3: Warm switch A->B (after T2, clear path A, fill path B)
  T4: Warm switch B->A (after T3, clear path B, fill path A)

  If T3 fails: LIMITATION #2 confirmed. Merge to one config.
  If T1 fails: Platform never activates second config -- also need merge.
  If all pass: Split configs viable; field isolation achievable.

KNOWN PLATFORM LIMITATIONS (apply to all providers)
================================================================================

  See ConnectCIC-KB/knowledge-base/PLATFORM_LIMITATIONS.txt -- complete numbered list (#1-#26).
  See ConnectCIC-KB/knowledge-base/BUNDLE_ARCHITECTURE.txt -- bundle structure, AUTH/QMF/RMS patches.
  See NJ_NJCJIS/docs/NJ_NJCJIS_LIMITATIONS.txt for the most complete NJ-specific reference.
  See NY_NYSPIN_EJUSTICE/docs/NY_NYSPIN_EJUSTICE_LIMITATIONS.txt for NY-specific items.

  CRITICAL for every build:

  1. LIMITATION #1: set/any controls combination selection only -- not field sending.
     All populated attributes in the config are sent when any combination fires.
     Field isolation requires split configs (with LIMITATION #2 risk) or accepted
     cross-contamination. Server is typically tolerant of extra fields.

  2. LIMITATION #2: Platform evaluates only ONE QUERYINPUTDATAMAPPING per (targetEntity, query) pair.
     The first (or last-loaded) config is selected; all other configs for the same query are
     silently ignored -- regardless of which entity form is active or what set[] contains.
     Confirmed: NJ DQ Name path never fired after split (v2.6). NY VehicleRegistrationQuery
     OOS config never fired (v1.8-v1.10); form data confirmed plate populated, query still failed.

     Diagnostic trigger: form data confirms field IS populated (LicensePlateNumberOut="njtest")
     but query still does not fire. This proves the QIDM itself is never evaluated -- stop
     iterating set[] changes and move immediately to the merge decision below.

     Merge decision:
       Can merge  -- all keyReferences across both configs are distinct (no duplicate keyRefs).
                     NY Vehicle: _NY had RVEH+RCAR; _OOS had RVEH+RVIN.
                     After merge: RVEH+RCAR+RVIN -- all distinct. Fix: one merged QIDM (v1.11).
       Cannot merge -- a keyRef appears in both configs (duplicate would cause import error).
                     Options (try in order):
                     a) Separate MetaData transaction: check if provider XML defines a distinct
                        transaction for the second path with its own keyRef.
                        NY DL Name: NyNyspinDriverLicenseNameQuery (keyRef=DGRP). Different query
                        name = different (targetEntity, query) pair. LIMITATION #2 does not apply.
                     b) DH-suffixed fieldIds (FL_FCIC pattern): give second-path form fields unique
                        fieldIds (NameFirstDH, etc.). Each QIDM references only its own fieldIds
                        in set[]. Avoids LIMITATION #2 entirely without merging.
                     c) Not implementable: if neither (a) nor (b) applies, document and notify vendor.
                        NY DH Name: both DALL paths share keyRef=DALL; no separate DH Name
                        transaction exists. DH Name path (T8) is blocked pending vendor action.

     Always test T1-T4 (cold start + warm switch) before committing to split arch.

  3. Blank FormInput = not sent. Cleared FormSelect = not sent.
     Use initialValue for fields that should always have a default.

  4. FormSelect YES_NO_UNKNOWN exposes Y, N, U. U cannot be suppressed.
     For Y-only flag fields: use FormInput instead.

  5. Card.props.title is the only way to add instructional text. Plain text only.
     HTML tags appear verbatim.

  6. codeTypeSource for ArticleTypeCode must be CA_CLETS, not NCIC.

  7. attributeTypeId='STATE' sends internal numeric attribute ID, not 2-letter code.
     Only use on hidden SelH for RMS. Never map in QIDM for outbound XML.

  8. RMS elastic search fatals on VIN/OLN when RegistrationState receives plain text.
     Fix: dual-field approach (SelH for RMS + InpH for outbound XML). See above.

  9. fieldId='LicensePlateNumber' does not trigger RMS plate search.
     Use LicensePlateNumberIn (NJ) or LicensePlateNumberOut (OOS) instead.

  10. keyReference must be unique within a QUERYINPUTDATAMAPPING.
      Import error: "Duplicate key references found in query input data mapping."
      For NJ+OOS in same QIDM: suffix NJ combinations with _NJ.

  11. IgnoreUserValueRuleHandler does not override sourceField value when populated.
      Tested NJ v3.10. Dead end. Do not use for state field hardcoding.

  12. Query display summary shows internal attribute ID for hidden SelH state field.
      The summary widget always surfaces raw values of fields with attributeTypeId.
      SelH (attributeTypeId=STATE) cannot be removed from the form -- RMS requires it.
      Attempted fixes: field order swap, bundle order change, IgnoreUserValueRuleHandler -- all failed.
      Requires CommSys vendor support (summary aliasing or RMS accepting 2-letter codes).
      Functional impact: none. Outbound XML and RMS both work correctly.

  13. QUERYINPUTFORM in RMS bundle causes duplicate entity form cards.
      QUERYINPUTFORM belongs only in the ENTITIES bundle (provider=MARK43).

  14. YES_NO codeTypeCategory is not recognized -- use YES_NO_UNKNOWN.

  15. VehicleStolenQuery (and other unregistered transactions) cannot be built until
      CommSys registers the transaction in the server-side provider XML.
      Flag in LIMITATIONS.txt and gap summary at standup.
