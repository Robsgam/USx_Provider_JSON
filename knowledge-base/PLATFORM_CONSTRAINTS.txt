SECTION 1 -- QUERY ROUTING AND COMBINATION BEHAVIOR
================================================================================

LIMITATION #1: Attribute serialization controlled by CONDITIONS POOL, not just firing combo
  CORRECTED: TX_TLETS v3.2 T7+T8 (2026-05-26). Original claim and first correction both
    incomplete. Full behavior now understood.
  ORIGINAL (INCOMPLETE): "ALL populated attributes in the QIDM are sent regardless of
    set[]/any[]." True for QIDMs without conditions. NJ v2.1 had no conditions.
  ACTUAL BEHAVIOR: Platform builds a serialization pool from the UNION of set[]/any[]
    from all combos whose conditions match (or have no conditions). Then serializes
    populated fields from that pool. The combo that FIRES is determined by set[] matching,
    but serialization draws from the entire conditions-matched pool.
  PROOF (TX_TLETS v3.2):
    T7: Image=N ? DQNameImg conditions (EQUALS Y) FAIL ? Image/Reason/Email excluded
        from pool ? DQName catchall fires ? XML has only State, Sex, DOB, Name. PASS.
    T8: Image=Y ? DQNameImg conditions (EQUALS Y) PASS (but set[] fails, no Sex) ?
        Image/Reason/Email ADDED to pool ? QWName fires ? XML includes Image=Y,
        Reason=C even though they are NOT in QWName's set[]/any[]. PASS.
  KEY INSIGHT: Conditions filter the serialization pool. When conditions FAIL, those
    combos' unique fields are excluded even if form values exist. When conditions PASS,
    fields are included even if that combo doesn't fire (set[] not met).
  DESIGN IMPLICATION: Conditions routing can control attribute omission within a single
    QIDM. Put fields-to-omit ONLY in conditions-guarded combos' any[]. When conditions
    fail, those fields are excluded from XML. When conditions pass, they serialize.
    No need for separate QIDMs.
  COMPATIBILITY: QIDMs without conditions behave as originally documented ? all combos'
    fields form one pool, and all populated attributes serialize. LIMITATION #1 original
    claim is correct for the no-conditions case (e.g., NJ v2.1).

  CLARIFICATION (confirmed FL_FCIC 2026-05-05, CA_CLETS 2026-05-08):
    any[] is NOT a minimum-one-required gate. A combo fires when all set[] fields
    are populated, even if NO any[] field is populated. The any[] array controls
    which optional fields CAN serialize, not whether the combo matches.
    Tested: FL_FCIC FBQ+Hull combo (set=[BoatHullIdNumber],
    any=[Decal,Reg,TitleLien,ImageIndicator]) fired with only set[] filled.
    CA_CLETS NLTS.KQ.O (any=[registrationState]) fired with State blank.
    CA_CLETS IP.QA.S (any=[articleBrand,articleTypeCode]) fired with both blank.
    Server accepted all queries without error.

  OPERATIONAL CONCERN (flagged 2026-04-29):
    When priority routing selects one combo over another (e.g., RQ wins over RQN
    because both Plate and VIN are filled), the "losing" combo's SET fields still
    appear in the XML because they are populated QIDM attributes. Examples:
      - Plate+VIN filled: VehicleReg RQ fires but VIN is in the XML
      - Plate+VIN filled: VehicleStolen QVP fires but VIN is in the XML
      - OLN+Name+DOB filled: DQN fires but Name+DOB are in the XML
      - RegNum+HullId filled: QB fires but HullId is in the XML
    This is EXPECTED platform behavior and cannot be changed at the JSON level.
    Monitor provider responses for signs of rejection on extra fields.
    As of 2026-04-29, NJ CommSys tolerates the extra fields with no errors.

  MITIGATION -- PLATE-WINS GUARDRAIL (HI v3.6 2026-06-22):
    The "cannot be changed" claim above applies to simple combo ordering. It CAN
    be mitigated for the plate/VIN conflict using NOT_EXISTS conditions:
    Add { field: ['LicensePlateNumber'], operator: 'NOT_EXISTS' } to all VIN-path
    combos (RQV, QVV, M55S). When Plate is present, VIN combos exit the conditions
    pool entirely, so their fields (VehicleIdentificationNumber, VehicleMakeCode,
    VehicleYear) do NOT enter the union pool and are absent from the plate XML.
    LIVE-PROVEN HI v3.6: all-fields test ? only RQ fires; VIN absent from XML. Clean.
    FULL RULE: See BUILD_RULES.txt "VEHICLEREGISTRATIONQUERY PLATE-WINS GUARDRAIL".

LIMITATION #2: ONE QIDM per (targetEntity, query) pair
  CONFIRMED: NJ v2.6 (2026-04-08); NY v1.8-v1.10 (2026-04-13);
             NY v1.18b (2026-04-15)
  Behavior: When multiple QIDMs share the same targetEntity and query value, only
    one is evaluated. The others are silently ignored regardless of which entity
    form is active, what fields are populated, or whether autoSelect is true or false.
  Diagnostic trigger: Form data confirms field IS populated but query still does not
    fire. STOP iterating set[] changes -- the QIDM itself is never evaluated.
  Resolution: Merge into one QIDM (when all keyRefs are distinct), use a separate
    transaction, or use DH-suffix fieldIds. See BUILD_RULES.txt for patterns.

  DO NOT: Split QIDM configs without verifying this constraint first (AP #12)
    Creating two separate QIDMs for the same (targetEntity, query) and assuming
    both will fire depending on what the user fills in. Platform picks one QIDM
    per (targetEntity, query) pair. The second is silently ignored regardless of
    which form fields are populated.
    Correct approach: always run the LIMITATION #2 check (cold start T1 and T2 for
    each path) before committing to split architecture. Default to merged unless
    keyRefs are duplicated.
    Confirmed broken: NJ v2.6, NY v1.8-v1.10, NY v1.18b (FL_FCIC two-QIDM
    pattern, 2026-04-15 -- autoSelect=false does not bypass; second QIDM not
    surfaced, first QIDM autoSelect=true broken by presence of second QIDM
    targeting same query)

  DO NOT: Declare a query path not implementable without exhausting all QIDM
    options (AP #17)
    Seeing one blocker (LIMITATION #2) and concluding the path cannot be built
    without checking: (a) single QIDM with multiple combos + distinct keyRefs,
    (b) DH-suffix fieldIds, (c) existing reference builds (BoatQuery pattern).
    One QIDM with multiple combos is NOT blocked -- as long as each combination
    has a distinct keyReference (LIMITATION #21). BoatQuery in every NY/NJ build
    demonstrates this: one QIDM, four combinations (RVEH/RCAR/BVEH/BVIN).
    Check order before declaring not implementable:
      1. Can one QIDM cover both paths with multiple combos + distinct keyRefs?
      2. Can DH-suffix fieldIds give structural isolation?
      3. Does a reference build already demonstrate the pattern?
      4. Only after all three fail: declare not implementable.
    UPDATE (NY v1.19, 2026-04-15): DH Name path WAS blocked by duplicate DALL,
    but resolved by using invented distinct keyRefs (DALL + DALH) in single QIDM.
    Provider does not validate keyRef -- routes by field content.
    Confirmed working: DALL+DALH single QIDM (v1.19).

    SYNTHETIC KEYREF NAMING CONVENTION (applies to all providers):
    When metadata XML uses the same keyReference for multiple combos in a transaction,
    ConnectCIC requires a unique keyRef per combo. Invent a synthetic label by appending
    a suffix to the metadata keyRef. These synthetic keyRefs do NOT exist in the
    provider's metadata -- they are ConnectCIC-internal routing labels only.
    Standard suffixes:
      - DH Name path:   DALL -> DALH  (H = history/name path)
      - DH OOS:         DALL -> DALLOUT, DALH -> DALHOUT  (OUT = out-of-state)
      - DL Name path:   DLIC -> DLICN  (N = name path)
    Build scripts MUST include a comment on any synthetic keyRef explaining:
      "synthetic -- metadata uses [REAL_KEYREF] for both combos; platform requires
       unique keyRefs per QIDM (LIMITATION #21)"
    Confirmed working on NYSPIN: DLICN (NY v2.7, 2026-06-09 live test).

LIMITATION #21: Duplicate keyReference rejected at import
  CONFIRMED: NJ v3.12, NY v1.13
  Error: "Duplicate key references found in query input data mapping."
  Rule: Each combination within a single QIDM must have a distinct keyReference.
  Fix: Use invented distinct keyRef (e.g., DALL + DALH). Provider routes by field
    content in the XML, not by keyRef. keyRef is platform-internal only.
  Confirmed working: NY v1.19 (invented DALH accepted, both paths fire correctly).
  See also: AP #5 (anti-pattern: duplicate keyReference in one QIDM).

LIMITATION #3: First matching combination fires -- all populated fields sent
  CONFIRMED: NJ v2.0
  Behavior: First combination whose set[] fields are all present fires. Its any[]
    determines which optional fields are included in routing. All populated QIDM
    attributes are still sent (see #1).
  Impact: Put most-specific combination first in the array.

LIMITATION #4: attributeTypeId='STATE' sends internal numeric attribute ID
  CONFIRMED: NJ v3.x, NY v1.0
  Behavior: Any FormSelect with attributeTypeId='STATE' sends the platform's
    internal attribute ID (e.g., NJ=69509884952, NY=69509802469) instead of
    the 2-letter state code.
  Correct use: ONLY on visible Sel for RMS elastic search (fieldId=
    'RegistrationState'). Never map this field in a QIDM targetField for outbound
    XML without codeTypeProvider.
  Fix for outbound XML: codeTypeProvider='NCIC' on QIDM attribute enables
    reverse-lookup from attribute ID to 2-letter code. Fallback: InpH with
    initialValue.

  DO NOT: Use attributeTypeId='STATE' in a QIDM sourceField (AP #1)
    Mapping a SelH/Sel with attributeTypeId='STATE' to a QIDM attribute (i.e.,
    using fieldId='RegistrationState' as a QIDM sourceField). Platform serializes
    the internal numeric attribute ID into outbound XML instead of the 2-letter
    state code. Provider receives "69509884952" instead of "NY".
    Correct approach: Use InpH (hidden FormInput) with initialValue='NY'. Map
    that fieldId as the QIDM sourceField -> targetField='State'. Keep SelH
    'RegistrationState' (attributeTypeId=STATE) in the form for RMS only -- DO
    NOT include it in the QIDM.
    Confirmed broken: NJ, NY (multiple versions)

LIMITATION #5: RMS elastic search fatals on VIN/OLN when state is plain text
  CONFIRMED: NJ v3.11
  Behavior: RMS recognizes fieldId='RegistrationState' and expects an attribute
    ID. Sending plain text (e.g., 'NJ', 'NY') causes RMS to throw a fatal local
    error.
  Scope: VIN and OLN queries only. Plate-only queries do not trigger this.
  Fix: Use attributeTypeId='STATE' on form field (stores attr ID, not text).

LIMITATION #9: Blank FormInput = not sent; cleared FormSelect = not sent
  CONFIRMED: NJ v1.9

AP #2: attributeTypeId='SEX' WITHOUT codeTypeProvider='NIBRS'
  CONFIRMED broken (attributeTypeId alone): NY v1.2, NJ various versions
  CONFIRMED working (with codeTypeProvider=NIBRS): AZ_AZDPS,
    NJ_NJCJIS v3.25 (2026-04-17)
  What: Using attributeTypeId='SEX' on a SexCode FormSelect without also adding
    codeTypeProvider='NIBRS' on the form field AND the QIDM SexCode attribute.
  Why it fails: Form stores numeric attribute ID; QIDM without codeTypeProvider
    writes the raw ID into outbound XML. CommSys receives
    <SexCode>69509891711</SexCode>.
  Correct approach: attributeTypeId='SEX' + codeTypeProvider='NIBRS' on BOTH
    the form field AND the QIDM SexCode attribute. See FIELD_REFERENCE.txt Section 5.
  NOTE: codeTypeCategory=NIBRS_SEX satisfies CommSys only. It does NOT work for
    RMS sex filtering (useAttributeId=true cannot convert NIBRS code to attribute
    ID). Use the attributeTypeId + codeTypeProvider pattern when both CommSys and
    RMS are needed.

AP #4: IgnoreUserValueRuleHandler for state field hardcoding -- DEAD END
  CONFIRMED dead end: NJ v3.10

    argument, hoping to override the sourceField value with a hardcoded 'NJ'
    or 'NY'.
  Why it fails: Handler passes the raw sourceField value through unchanged
    when the field is populated. The argument is not substituted.
  Correct approach: InpH hidden FormInput with initialValue='NY'.

SECTION 3 -- MULTI-ENTITY AND SHARED FORM BEHAVIOR
================================================================================

LIMITATION #26: Shared field pool across Person QIDMs
  CONFIRMED: NY v1.15 live test (2026-04-14)
  Behavior: Platform evaluates ALL Person QIDMs from a single shared
    field-value pool, regardless of which sub-form (QIF sub-tab) is currently
    active. Separate QIF sub-forms do NOT isolate QIDM evaluation to the active
    form's fields only.
  Consequence: When OLN is entered on the DL form, the DH QIDM also matches.
    queriesToDeselect is ineffective in BOTH directions (confirmed NY v1.16
    T7a).
  Net behavior: DL + DH always co-fire whenever OLN is present = correct
    police workflow.
  True isolation requires: DH-suffix fieldIds (OperatorLicenseNumberDH on DH
    form).

  DO NOT: Assume separate QIF sub-forms isolate QIDM evaluation (AP #16)
    Placing DL and DH on separate QUERYINPUTFORM sub-tabs (distinct QIFs under
    the Person entity) and expecting the platform to evaluate each QIDM only
    when its own sub-form is active. CONFIRMED broken (NY v1.15 live test,
    2026-04-14). The platform evaluates ALL Person QIDMs from a single shared
    field-value pool regardless of which sub-form is active. Entering OLN on the
    DL sub-form causes the DH QIDM to also match, and vice versa.
    Correct approach -- option A (embrace co-fire): remove queriesToDeselect
    from DL QIDMs. DH fires as a co-query when OLN is entered (correct police
    workflow).
    Correct approach -- option B (true isolation): add OperatorLicenseNumberDH
    to the DH form and DH QIDM set[]. DH set[] field is absent from the shared
    pool when only DL form fields are populated.
    Applied: NY v1.17 uses Option B. NY v1.16 used Option A.
    Confirmed broken: NY v1.15 separate-form architecture with mutual
    queriesToDeselect.

LIMITATION #28: Entity-split breaks codeTypeProvider reverse-lookup
  SERVER-SIDE -- no config fix available
  CONFIRMED: FL_FCIC v2.0, v2.3, v2.4 (2026-04-20 through 2026-04-21).
    3 tests, all failed.
  Control: FL_FCIC v2.2 single-QIF WORKS on same instance.
  Behavior: When multiple QIFs target the same entity, codeTypeProvider
    reverse-lookup on QIDM attributes fails. The QIDM sends raw attribute ID
    instead of resolved code.
  Root cause: Shared field pool (see #26). Inactive QIF's empty value
    interferes with reverse-lookup on active QIF's populated value.
  Design constraint: To use codeTypeProvider reverse-lookup, each entity must
    have exactly ONE QIF. Multi-card layouts within a single QIF are unaffected.
  Full investigation: FL_FCIC_entity_split_investigation.zip

LIMITATION #29: Attention field overridden by platform with user session data
  CONFIRMED -- SERVER-SIDE
  Confirmed: FL_FCIC KQ (DriverHistoryQuery) 2026-04-23
  Behavior: User types a value in Attention field, but platform substitutes
    logged-in user's name (LASTNAME FIRSTINITIAL) in outbound XML <Attention>
    element. Override happens AFTER form submit and BEFORE XML generation.
  Resolution (SUPERSEDES earlier guidance): per the VISIBLE-FIRST MANDATE
    (BUILD_RULES.txt Section 14), Attention is built as a VISIBLE FormInput
    by default -- the officer keeps control and form load/submit is faster
    (confirmed FL_FCIC v4.0). The platform may still override the value
    server-side; that is acceptable. The hidden auto-populate workaround
    (CommsysGetLastNameFirstNameInitialRuleHandler, CA_eSUN/LA_LEMS legacy
    pattern) is NOT the default and must NOT be added without explicit user
    approval. verify_build.ps1 CHECK 8 WARNs on the hidden-handler case.
    EARLIER NOTE ("Do NOT add visible FormInput for Attention") is OBSOLETE.
  Open: Whether the server-side override applies to all providers or only
    FL_FCIC; whether it applies to all queries or only DriverHistoryQuery.

AP #14: queriesToDeselect without DH-suffix fieldIds deadlocks
  CONFIRMED broken: NY v1.15 (2026-04-14), NY v1.16 T7a (2026-04-14)
  What: Adding queriesToDeselect to DL and DH QIDMs but not using DH-suffix
    fieldIds, when both QIDMs reference the same OperatorLicenseNumber fieldId
    in their set[].
  Why it fails: When the officer enters an OLN, BOTH QIDMs match
    simultaneously. DL tries to deselect DH and DH tries to deselect DL.
    Mutual deselect deadlocks -- result is undefined (neither fires, or
    unpredictable firing order).
  Correct approach on a SHARED form: Always pair queriesToDeselect with
    DH-suffix fieldIds. Give DH form field OperatorLicenseNumberDH (different
    fieldId). DH QIDM set[] references OperatorLicenseNumberDH. DL QIDM set[]
    references OperatorLicenseNumber. They cannot match simultaneously.
    Source: FL_FCIC.json.
  On SEPARATE forms (distinct QIFs): SAME PROBLEM CONFIRMED (NY v1.15 live
    test, 2026-04-14). Platform uses a shared field-value pool for ALL Person
    QIDMs regardless of active sub-form (see LIMITATION #26). Mutual
    queriesToDeselect deadlocks even when DL and DH are on separate QIF sub-tabs.
  Resolution (v1.16): Remove queriesToDeselect from DL QIDMs. Embrace
    DLIC+DALL co-fire as correct workflow (comprehensive OLN search). If true
    isolation needed: DH-suffix fieldIds.

LIMITATION #23: Unregistered transactions cannot be built
  Behavior: QIDM cannot target a transaction type that the CommSys server has
    not registered. No import error, but query will never fire.
  Check at standup: Confirm all target transactions are in the provider XML
    metadata.
  Examples: NJ VehicleStolenQuery (registered late), NY WINQ/MINQ (no
    transaction XML).

--------------------------------------------------------------------------------

AP #5: Duplicate keyReference in one QIDM
  CONFIRMED broken: NY v1.13 (duplicate DLIC, 2026-04-14);
    NY v1.18a (duplicate DALL, 2026-04-15)
  What: Creating a single QIDM with two or more combinations that both use
    the same keyReference (e.g., two combinations both with
    keyReference='DLIC').
  Why it fails: Platform rejects the import with:
    "Duplicate key references found in query input data mapping"
  Correct approach: Use DISTINCT keyRefs for the two combinations. keyRef is
    a platform-internal identifier only -- the provider does NOT receive or
    validate the keyRef. Provider routes by field content in the XML.
    Invented keyRefs (e.g., DALL + DALH) are valid as long as they are unique
    within the QIDM.
    CONFIRMED: NY v1.19 (2026-04-15) -- DALL (OLN path) + DALH (Name path)
    in single QIDM. Import accepted; both paths fire correctly;
    autoSelect=true works.

AP #9: QUERYINPUTFORM in RMS bundle duplicates forms
  CONFIRMED broken: NJ (multiple versions)
  What: Adding a QUERYINPUTFORM to the RMS bundle (or any bundle other than
    ENTITIES).
  Why it fails: Causes each entity form card to render twice in the UI.
  Correct approach: QUERYINPUTFORM belongs ONLY in the ENTITIES bundle
    (provider=MARK43).

--------------------------------------------------------------------------------

AP #10: Merging QIDMs with shared keyReference
  CONFIRMED broken: NY v1.13
  What: Attempting to resolve LIMITATION #2 by combining two split QIDMs into
    one when those QIDMs have combinations with the same keyReference.
  Why it fails: The merge itself causes import error #5 above (duplicate
    keyRef).
  Correct approach: Use separate transaction or DH-suffix pattern. If keyRefs
    conflict, invent distinct keyRefs (see AP #5).

LIMITATION #30: initialValue on State changes combo routing (in-state -> OOS)
  CONFIRMED -- by design (#1 + #3 interaction)
  Confirmed: NY_NYSPIN_EJUSTICE MC 2026-04-24
  Behavior: Setting initialValue (e.g., 'NY') on State dropdown causes State
    to always be populated. OOS combo (which includes State in set[]) fires
    instead of in-state combo.
  Example: Without initialValue, VIN only -> RCAR fires (in-state).
           With initialValue='NY', VIN + State(NY) -> RVIN fires (OOS).
  Workaround: Use card title hint ("Leave blank for NY queries").
  Safe to use initialValue: When provider has no separate in-state keyRef
    (e.g., NJ).
  Do NOT use initialValue: When provider has separate in-state vs OOS combos
    (e.g., NY).

--------------------------------------------------------------------------------

LIMITATION #31: initialValue fields not counted for set[] combo evaluation
  CONFIRMED: NJ v2.6 (VehicleStolenQuery/VehicleRegistrationQuery 2026-04-10)
  Behavior: Platform combo evaluator ignores initialValue defaults on
    FormSelect/FormInput when evaluating set[] requirements. Only fields the
    user actively enters or changes are counted as "populated." Fields with
    initialValue (PlateType=PC, RandomRequest=N, ImageIndicator=Y/N) must go
    in any[], not set[].
  Impact: QIDM combinations must not include defaulted-only fields in set[].
  SCOPE REFINEMENT (CA_CLETS 2026-05-08): CaRequestPurposeCode with
    initialValue='C' IS counted for set[] evaluation. All CA_CLETS combos
    include caRequestPurposeCode in set[] and fire correctly with the default.
    LIMITATION #31 may only apply to attributeTypeId-based fields (STATE) or
    autoSelect-involved QIDMs, not regular FormInput/FormSelect defaults.
    Further testing needed to confirm the precise scope boundary.

--------------------------------------------------------------------------------

LIMITATION #32: autoSelect=true triggers on initialValue in any[] fields
  CONFIRMED: FL_FCIC v4.2 (2026-05-19)
  Behavior: autoSelect=true lights the QIDM checkbox when ANY attribute's
    sourceField has a value, including initialValue defaults -- even if that
    field is in any[], not set[]. This means a DH QIDM with registrationStateDH
    initialValue='FL' auto-lights the DH checkbox on page load, causing DH to
    co-fire with DL queries and producing CommSys errors.
  Impact: DH-suffix fields with initialValue cannot coexist with autoSelect=true
    on the same QIDM. Either drop the initialValue or remove the field from
    the QIDM entirely.
  Workaround: Remove initialValue from DH State field. Use label text to guide
    officers (e.g., "State (required for Driver History)"). registrationStateDH
    stays in any[] so State is sent when officer selects it.
  Related: LIMITATION #30 (State initialValue changes routing),
    LIMITATION #31 (initialValue not counted for set[])

LIMITATION #33: RMS Person cannot receive DH State due to field isolation
  CONFIRMED: FL_FCIC v4.3 (2026-05-19)
  Behavior: RMS Person QIDM reads registrationState (DL card). DH card uses
    registrationStateDH (DH-suffix for isolation). RMS cannot reference both
    fields to the same targetField (duplicate targetField = error). When DL
    State is blank (in-state FDQ), RMS Person search has no state filter.
  Impact: In-state Person queries do not include state in the RMS elastic search.
    OOS queries (DQ with registrationState populated) do include state in RMS.
  Workaround: Pending Cringer platform fix -- defaults[] with proper attribute
    UUID handling would allow injecting home state into RMS without a form field.
    Cannot rename fields (CAD auto-populate depends on registrationState).
  Related: LIMITATION #5 (RMS fatals on plain text state)

AP #18: Removing RMS sex without also removing SexCodeOOS from combinations
  CONFIRMED broken: NY_NYSPIN_EJUSTICE v1.0 (2026-04-20)
  CONFIRMED working: NY_NYSPIN_EJUSTICE v1.1 (2026-04-20)
  What: When removing sex from the RMS Person QIDM, only filtering 'SexCode'
    from combination any[] while leaving 'SexCodeOOS' in OOS combinations.
  Why it fails: The RMS Person QIDM has TWO sex attributes:
    'sex'    -> sourceField=SexCode,    targetField=sexAttrId  (in-state)
    'sexOOS' -> sourceField=SexCodeOOS, targetField=sexAttrId  (OOS)

    the sexOOS attribute but leaving 'SexCodeOOS' in any[] causes import error:
    "Missing attributes found in query input data mapping: [sexcodeoos]"

    attributes, AND remove BOTH 'SexCode' AND 'SexCodeOOS' from all combination
    any[]/set[] arrays. PowerShell pattern:
      $rmsPersonQidm.attributes = @($rmsPersonQidm.attributes |
        Where-Object { $_.targetField -ne 'sexAttrId' })
      foreach ($combo in $rmsPersonQidm.combinations) {
        $combo.requirements.any = @($combo.requirements.any |
          Where-Object { $_ -ne 'SexCode' -and $_ -ne 'SexCodeOOS' })
        $combo.requirements.set = @($combo.requirements.set |
          Where-Object { $_ -ne 'SexCode' -and $_ -ne 'SexCodeOOS' })
      }

AP #23: autoSelect conflicts on single-form entities

  What: Using arguments = @(' ',' ',' ') (3 separators) with only 2

LIMITATION #36: Metadata Choice-set ? OOS combo path not implemented
  CONFIRMED: NY_NYSPIN_EJUSTICE v2.1 (2026-06-08) -- DH OOS combos missing
  Behavior: Metadata XML can define combinations with a Choice structure:
    <Requirements><Set><Choice><Set>..minimal..</Set><Set>..+OOS fields..</Set></Choice></Set></Requirements>
    The first (shorter) Set is the in-state path; the second adds PurposeCode,
    Requestor, State for OOS queries. Implementing only the in-state path (the
    common case) means OOS DH queries silently go out without required OOS fields,
    producing errors or wrong routing at the CommSys endpoint.
  Detection: audit_metadata.ps1 CHECK 4b ("Choice-Set Option Coverage") flags this.
  Fix: Build a second OOS combo for each Choice path. The OOS combo puts the extra
    fields (PurposeCode, requestorDH, registrationState) in set[], ensuring the
    combo only fires when all OOS fields are present. Ordering: OOS combo first
    (more set[] fields = higher priority), in-state combo as fallback.
  Canonical example -- NY DH (4 combos):
    DALHOUT set[birthDateDH, nameLastDH, nameFirstDH, sexCodeDH, purposeCodeDH, requestorDH, registrationState]
    DALH    set[birthDateDH, nameLastDH, nameFirstDH, sexCodeDH]
    DALLOUT set[operatorLicenseNumberDH, purposeCodeDH, requestorDH, registrationState]
    DALL    set[operatorLicenseNumberDH]
  Scope: Check all providers with DriverHistoryQuery + OOS capability. Also check
    other queries with Choice structure in metadata XML.
  Related: LIMITATION #35 (OOS State misroutes CAD) -- add NOT_EQUALS conditions
    on DALHOUT/DALLOUT if the provider has a home-state CAD risk.

  *** DECISION RULE -- <Any> vs <Choice>-extended-<Set> (added 2026-06-08) ***
  The metadata expresses the in-state/OOS distinction in TWO different ways. They
  require DIFFERENT JSON treatment. Read the XML structure, do not guess:

  (A) State (and OOS fields) appear inside <Any> of the combination:
        <Set><Field reference="OperatorLicenseNumber"/><Any><Field reference="State"/></Any></Set>
      -> Build ONE combo with State in any[]. The metadata says State is OPTIONAL.
         Example: NY DriverLicenseQuery (DLIC, DLICN) -- State in any[] is CORRECT.
         Do NOT invent an OOS combo. This is not a gap.

  (B) State (and OOS fields) appear inside a second <Set> under a <Choice>:
        <Choice><Set>minimal</Set><Set>...,State (all required)</Set></Choice>
      -> Build a DEDICATED OOS combo with the non-defaulted discriminator (State)
         in set[]. Keep DEFAULTED fields (PlateType=PC, PlateYear=$currentYear) in
         any[] -- per LIMITATION #31 defaulted fields cannot gate combo firing, so
         they must NOT go in set[].
         Examples: NY VehicleReg plate (RVEH in-state / RVEHOUT set[plate,State] OOS),
         NY VehicleReg VIN (RCAR / RVIN set[VIN,State]), NY DH (DALL/DALLOUT, DALH/DALHOUT).

  WHY: a <Choice> extended Set means those fields are REQUIRED TOGETHER for the OOS
  query. Demoting State to any[] lets an officer submit an incomplete OOS query and
  removes the form-level enforcement the metadata intends. CHECK 4b emits a [NOTE]
  when a Choice OOS option needs State but no combo (sharing that primaryFieldReference)
  has State in set[].

  CONFIRMED EXTENSIONS:
    NY DH OOS combos added v2.2 (2026-06-08).
    NY VehicleReg RVEHOUT (plate OOS) added v2.3 (2026-06-08) -- swept after the DH
    fix revealed the plate Choice had the same pattern. Lesson: when one Choice-set
    gap is found, sweep EVERY <Choice> in that provider's metadata before declaring done.

LIMITATION #35: OOS combos with home state in set[] misroute CAD queries
  CONFIRMED: CA_CLETS v2.3 (2026-05-21), NJ_NJCJIS v3.2 (2026-05-15)
  Behavior: When a provider has separate in-state vs OOS (out-of-state) combos
    and State is in set[] on OOS combos, CAD auto-populating the home state
    causes the OOS combo to fire instead of the in-state combo.
  Example: CA_CLETS has IA.QV (in-state, no State in set[]) and NLTS.RQ.P
    (OOS, State in set[]). CAD sends registrationState=CA. NLTS.RQ.P fires
    (OOS/Nlets routing) instead of IA.QV (in-state/DMV routing).
  Fix: Add NOT_EQUALS condition on all OOS combos with home state in set[]:
    conditions = @([PSCustomObject]@{
        field = @('State'); operator = 'NOT_EQUALS'; value = @('<HOME_STATE>')
    })
    This prevents OOS combos from firing when CAD sends the home state.
    The in-state combo (without State in set[]) fires as the correct fallback.
  Scope: Affects any provider with separate in-state/OOS keyRef groups where
    State appears in OOS set[]. Currently confirmed: all CA providers (NLTS
    prefix = OOS). Check NJ, TX, and any provider with State-based routing.
  AUDIT: Grep for combos with State or registrationState in set[] and verify
    they have NOT_EQUALS conditions if an in-state equivalent exists.

LIMITATION #40: THE WIRE IS A UNION ACROSS EVERY MATCHING COMBINATION, NOT THE
  FIRING COMBINATION'S FIELD LIST.
  STATUS: LIVE-PROVEN providers/FL_FCIC/logs/Boat/FL_FCIC_v7.23_FBQDecalNumber_af_BoatHullIdNumber.txt
  Control (must carry NEITHER field): providers/FL_FCIC/logs/Boat/FL_FCIC_v7.23_FBQDecalNumber.txt
  Quantified 2026-08-12: 38/38 Boat logs predicted correctly, 0 mispredicted, 37 conditions evaluated.

  A field reaches the CommSys request when the officer's fill satisfies ANY built combination
  that defines it -- NOT only the combination that actually fires. Removing a field from the
  firing combination's set[]/any[] therefore does NOT guarantee it stops transmitting.

  THE PROOF, and why it is not ambiguous. FL_FCIC v7.23 BoatQuery, fill = decalNumber + hull
  (+ the form-prefilled relatedHitSearchIndicator=Y and ImageIndicator=Y):
    wire = BoatHullIdNumber, DecalNumber, Id, ImageIndicator, MessageType,
           RelatedHitSearchIndicator, Requestor
    - DecalNumber is in NO QB combination, so the FIRING combo is unambiguously FBQ{Decal};
      audit_log_combo_attribution independently agrees (110/110 across the sweep).
    - FBQ{Decal}'s any[] at v7.23 is [BoatHullIdNumber, titleLienInformation,
      RegistrationNumber]. It defines NEITHER ImageIndicator NOR RelatedHitSearchIndicator.
    - Both nevertheless ride, because the same fill ALSO satisfies QB{BoatHullIdNumber}
      (set[Hull, relatedHitSearchIndicator], condition relatedHitSearchIndicator EXISTS),
      and QB defines both.
  The control case settles it: fill = decalNumber alone, or decalNumber + titleLienInformation,
  matches no QB combination, and those wires carry NEITHER field -- even though the form still
  holds ImageIndicator=Y. So it is not "the form value is always sent"; it is match-driven.

  CONSEQUENCES:
  1. A per-COMBINATION over-permit is not necessarily a wire defect, and removing the field from
     the firing combo is not necessarily a fix. Ask instead: does ANY matching combination define
     it? FL_FCIC v7.23 removed ImageIndicator from all four FBQ combos (both authorities agree it
     does not belong there -- metadata FBQ <Any> and devdoc items 1-4 list it nowhere) and 5 of 8
     FBQ wires still carry it, because those 5 fills also match a QB combination.
  2. audit_requirement_fidelity's OVER-PERMITTED check models the firing combination only, so it
     cannot express this. Its $formOnly whitelist (ImageIndicator, RegistrationState) may well be
     an empirical workaround for exactly this behaviour rather than an oversight -- do not remove
     that whitelist without re-reading this entry first.
  3. Identifier-priority guardrails still work, because they change WHICH combos MATCH (a
     NOT_EXISTS condition makes the loser stop matching), not merely which one is ordered first.
     That is why the Hull>Reg NOT_EXISTS gates de-bleed correctly while an any[] removal does not.

  NOT YET ESTABLISHED: whether this generalises beyond BoatQuery/FL_FCIC. Discriminating test --
  on any provider, fill a combination whose siblings define an extra optional it does not, and
  check whether the sibling's field rides. Until run, treat #40 as proven for FL_FCIC BoatQuery
  and STRONGLY INDICATED elsewhere.

LIMITATION #43: `requirements.defaults[]` ONLY FILLS AN EMPTY FIELD -- IT NEVER
                OVERRIDES A VALUE THE OFFICER TYPED. So a combo default cannot
                NORMALISE or FORCE a value, and cannot collapse many codes to one.
================================================================================
  STATUS: LIVE-PROVEN docs/evidence/2026-09-15_TRANSLATE_TEST_captures_XOUT_XIN.json
  (measured 2026-09-15 on practice-robsgambellone, dept 68908334972; 3 captures in that file,

  docs/evidence/2026-09-15_TRANSLATE_TEST_capture_XIN_first.json, transaction

  RIG: tools/build_translate_test.ps1 -> providers/TRANSLATE_TEST.json

  WHAT WAS ASKED. Rob, 2026-09-15, on NY_NYSPIN_EJUSTICE: NY uses CUSTOM NUMERIC in-state
  plate types and NCIC alpha types out-of-state, and "we would have mulitple ny nistate
  plate types used on the form tranlasted down to 1 ncic code  we would have this many to
  one assoication". The cheapest candidate mechanism was a combo default: put
  defaults[]={LicensePlateTypeCode: PC} on the out-of-state combination and let it
  overwrite whichever NY code the officer picked. That would have made many-to-one FREE.

  THE MEASUREMENT. Two combinations on one throwaway form, gated exactly like NY's real
  RVEH/RVEHOUT seam (RegistrationState NOT_EXISTS vs State required):
    XOUT  set[Plate, RegistrationState, LicensePlateTypeCode, LicensePlateYear]
          defaults[] LicensePlateTypeCode = PC
    XIN   set[Plate]  any[LicensePlateTypeCode]  cond RegistrationState NOT_EXISTS
  Officer typed LicensePlateTypeCode = 16 and filled State = Georgia + Year = 2020, so

    <LicensePlateYear>2020</LicensePlateYear><State>GA</State>
    <LicensePlateTypeCode>16</LicensePlateTypeCode><LicensePlateNumber>TEST</LicensePlateNumber>
  The default said PC. THE WIRE SAID 16. Two further captures with State blank fired XIN
  and also carried 16 verbatim.

  TWO CONSEQUENCES, AND THE FIRST IS REASSURING:
  (a) EVERY combo default shipped across the portfolio is SAFE -- it cannot clobber what an
      officer typed. That property was assumed and had never been measured. It is why the
      CAD-default convention (CAD ignores form initialValue, so combo defaults carry the
      value) does not silently overwrite a real operator entry.
  (b) A combo default is NOT a normaliser. Do not reach for defaults[] to force a code, to
      collapse a set of values onto one, or to "correct" an operator's choice. It will
      silently do nothing whenever the field is non-empty -- i.e. exactly in the case you
      were designing for.

  WHY NO GATE CAUGHT THIS EITHER WAY. `audit_wiring_closure` class E (INERT DEFAULT) checks
  only that a default's field is REACHABLE (present in that combination's set[]/any[]); no
  gate has ever asked what a default DOES to a value already present. The question was
  therefore unanswerable from the repo and had to be measured on a tenant.

  FREE-TEXT PASSTHROUGH, PROVEN IN THE SAME CAPTURES: a FormInput's typed value reaches the
  wire verbatim (16 -> <LicensePlateTypeCode>16</LicensePlateTypeCode>, three times). So a
  provider CAN transmit a code for which no platform code table exists -- relevant wherever
  a state's code set is not provisioned (contrast LIMITATION #39, where a FormSelect bound
  to an unprovisioned table renders EMPTY).

  STILL OPEN -- NOT tested by this rig: attribute-level `codeTypeProvider` DISAGREEING with
  its form control. The rig declared it but the second attribute's targetField was never
  placed in a combination's set[]/any[], so it was never in the serialization pool and no
  tag was emitted. Absence there is a RIG DEFECT, not a platform result.

    PROVEN -- the handler runs on the request path and substitutes the mapped value.
    PROVEN -- the emitted value is UPPERCASED (GEORGIA, NEW YORK). Favourable: an NCIC-style target
              code is uppercase anyway.
    NOT PROVEN -- a MANY-TO-ONE table (16/17/18 -> PC). The mechanism supports it by construction

              The dependency is PROVISIONING, not capability.

    provision an attribute table shaped   CODE = the state's own code (16, 17, 18)
                                          DISPLAY VALUE = the target code (PC)
    then put this handler on that field's REQUEST attribute. The officer picks from the state's
    list; the wire carries the mapped code. Several state codes mapping to one target code is
    exactly the many-to-one association that was asked for.
  ⚠️ The output is the DISPLAY VALUE, so the table must be built "backwards" from how a display
  table is normally read -- the human-readable column has to hold the code you want transmitted.

    * codeTypeProvider on an attribute is NOT a translator -- it is the switch that makes the
      platform emit the CODE instead of the internal numeric row id. validate.ps1 AP #1 enforces it

      as inert when tested for translation: it was doing its real job.
    * LIMITATION #43 (combo defaults only fill an empty field) still stands -- unaffected.

  Until one of those is answered, do NOT record a numeric cap as platform fact. What is measured is
  narrow and solid: THIS sixth entity, correctly formed, did not render.

  WHY IT COST A BUILD: `validate`, `verify_build`, `render_layout` and `audit_wiring_closure` all
  read the JSON and all passed -- the form is internally consistent, its fields are wired, its QIDM
  is reachable. NOTHING IN THE REPO KNOWS WHICH ENTITIES THE PLATFORM WILL RENDER, so a sixth one
  is indistinguishable from a correct build until a human looks at the page. That is LAW 1 (the
  form comes first) meeting the limit of static checking.

  SCOPE -- READ THIS BEFORE DRAWING A CONCLUSION FROM THE ABOVE. This limitation is about the
  targetEntity **VALUE** being unrecognised. It is NOT a cap on the number of tabs, and the first
  version of this entry wrongly implied that it was. **SEE CAPABILITY #47: MORE THAN FIVE TABS ARE
  AVAILABLE TODAY** -- tabs are keyed by QUERYINPUTFORM, not by entity, so a transaction that is
  not about one of the five subjects CAN have its own separate tab by reusing a known entity value.
  Everything this entry originally concluded ("it must become a CARD on one of the five", "move
  WantedPersonQuery onto its own entity is not available") was WRONG and has been deleted rather
  than softened. Rob drove the correction twice: "there has to be a way to have more than 5" and
  then "are you sure you are testing this correctly  i feel like 5 is arbitraty". He was right
  both times.

  The stale-client-cache alternative is ELIMINATED: the probe imports rendered their control tabs
  on the same page in the same session, so the client was reading fresh configuration.

CAPABILITY #47 (NOT a limitation): TABS ARE KEYED BY QUERYINPUTFORM, NOT BY ENTITY --
  SO MORE THAN FIVE TABS ARE AVAILABLE TODAY, AND ANY TRANSACTION CAN HAVE ITS OWN.
  STATUS: LIVE-PROVEN docs/evidence/ENTITY_PROBE_RESULT_2026-09-16.txt -- measured on usx-sc-sled (73046844870) via
  `build_entity_probe.ps1 -DuplicateEntityTest` -> `ENTITY_PROBE_DUP.json`.

  THE MEASUREMENT. Eight QUERYINPUTFORMs were declared: the five known entities, plus THREE MORE
  that all target `Person` with distinct `name` and `label` values --
      ENTITY_PersonAlpha   / label 'Person Alpha (dup-entity probe)'
      ENTITY_PersonBravo   / label 'Person Bravo (dup-entity probe)'
      ENTITY_PersonCharlie / label 'Person Charlie (dup-entity probe)'
  `order.default` listed `Person` FOUR times, deliberately un-deduplicated.
  RESULT, Rob reading the rendered page: **"8 tabs showing"**. All eight forms became tabs.

  SO THE RENDER UNIT IS THE FORM. A QUERYINPUTFORM gets a tab; `targetEntity` says what KIND of
  record that form searches for, not how many tabs exist. Reusing a known entity value across
  several forms is legal and each form is its own tab.

  WHY THIS WAS NOT FOUND EARLIER, and it is a pure blind spot rather than a hard problem:
  21 of 21 providers ship EXACTLY ONE QIF PER ENTITY. Nobody had ever declared two, so the
  repo had 21 identical data points and zero information about the alternative. Surveying our own
  builds could not have found this (ENGINEERING_STANDARD 4.5 -- practice is not spec), and 66
  DEPLOYED tenant configs could not either, because they are all built the same way.

  ⚠️ IT DOES NOT CONTRADICT LIMITATION #46 -- the two answer different questions:
      #46  an UNRECOGNISED targetEntity VALUE renders nothing. Eight candidate names were tested
           in one import (Organization, Location, Incident, Property, Case, Address, Message,
           AdministrativeMessage) and ALL EIGHT failed. That still holds.
      #47  the NUMBER of tabs is not bounded by the entity set, because tabs are per-FORM.
  Together: you may have as many tabs as you like; each one must declare an entity the platform
  recognises.

  ⚠️ TWO PRE-EXISTING LIMITATIONS GOVERN THIS AND BOTH WERE ALREADY IN THIS FILE. I wrote "the
  field pool is not yet measured" here and that was WRONG -- it is measured and root-caused:
    LIMITATION #26  the field pool IS SHARED across QIFs on the same entity
    LIMITATION #28  therefore a SECOND QIF on an entity BREAKS codeTypeProvider reverse-lookup
                    for that entity -- CONFIRMED on FL_FCIC v2.0/v2.3/v2.4, three tests, with a
                    single-QIF control (v2.2) that worked on the same instance. Its stated design
                    constraint: "To use codeTypeProvider reverse-lookup, each entity must have
                    exactly ONE QIF."
  So the repo ALREADY KNEW multi-QIF entities were possible -- #28 is a limitation ABOUT them --
  and this capability is better described as REDISCOVERED than discovered. The lesson is mine: I
  surveyed builds and deployed configs for evidence and did not grep the constraints file for the
  mechanism, which is the check CLAUDE.md's Source Authority table exists to force.

  CONSEQUENCE FOR PICKING THE HOST ENTITY -- this is the real design rule:
    - a second QIF must go on an entity with NO codeTypeProvider control, or #28 breaks that
      entity's reverse-lookup. SC_SLED v1.2's first attempt used Person and the VALIDATOR FAILED
      IT, naming SexCodeDR -- all three of SC_SLED's codeTypeProvider controls are on Person.
      It was rehosted on Article (no codeTypeProvider, smallest pool: 1 card / 2 fields / 1 combo).
    - GIVE THE NEW TAB'S CONTROLS UNIQUE FIELD IDS. Because #26 makes the pool shared and
      LIMITATION #1 makes the wire a union across every matching combination, unique ids are what
      stop a fill on the host entity's tab from satisfying or over-sending into the new one.
      SC_SLED v1.2 uses an AM suffix, the same device DriverHistory uses with DH.

  ⚠️ ALSO UNMEASURED: whether `label` drives the tab CAPTION. Eight tabs appeared and the three
  duplicates carried distinct labels, so they were distinguishable -- but which property the
  caption comes from was not read back. Verify before relying on a specific caption.

  CONSEQUENCE: a transaction that is not about one of the five subjects -- SC_SLED's
  AdministrativeMessage is the live case -- can have its OWN TAB, which is what Rob asked for
  ("i want it compeltely seperated"). It does not have to be a card bolted onto Vehicle, and
  WantedPersonQuery CAN be moved off Person onto a tab of its own.

LIMITATION #48: THERE IS NO MULTI-LINE / TEXTAREA FORM CONTROL. A LONG FREE-TEXT
  FIELD IS A SINGLE-LINE `FormInput` AND THAT IS THE MOST THE JSON CAN EXPRESS.
  CONFIRMED 2026-09-17 by FOUR independent sources (Rob: "on admi can we make the
  text line multirow like a box for text" -- SC_SLED's AdministrativeMessage carries
  a 501-character message in a one-line box, which is a fair thing to want fixed).

  WHAT THE FORM RENDERER IS: the QIF renderer is called **FORGE** (Craft.js based)
  and serves JMS, RMS, CAD and FR. Mobile/OnScene uses a SECOND, DIFFERENT renderer
  called **m43Forms**, which is Form.io based -- that is the `m43Forms` key sitting
  beside `departmentBundle` in every tenant export. Form.io HAS a textarea; FORGE
  IS THE ONE OUR JSON DRIVES AND IT DOES NOT. Do not conflate them.

  THE FOUR SOURCES, weakest to strongest:
   1. OUR 21 BUILDS -- 9 component types, and a `FormInput` has only ever carried
      fieldId / label / maxLength / initialValue. (`probe_control_types.ps1`)
   2. 66 TENANT CONFIGS PULLED OFF THE PLATFORM, INCLUDING NOT-OUR-BUILD ones
      authored by other engineers -- 7,414 control nodes, the same five field
      component types (FormInput, FormSelect, FormDate, FormCheckbox,
      FormRadioGroup), 19 distinct props, NO multiline/rows/height prop anywhere.
      This is the source that makes it a statement about the PLATFORM rather than
      about our habits.
   3. Confluence "Forge -> M43Forms Migration Guide" (SEARCH/6944981063) §3
      Component Mapping enumerates the Forge `type.resolvedName` values it converts:
      Card, Row, FormInput, FormDate, FormSelect (two paths), FormCheckbox, and
      Root/Form/Page as scaffolding. No textarea. ⚠️ READ ITS OWN CAVEAT: the page
      states the script "only covers the Forge component types and props that are in
      use today", so this is a USAGE CENSUS like #1 and #2, not a registry dump.
   4. Confluence "Federated Search JSON Configuration Capabilities" (RND/6397788223)
      -- THE CAPABILITY DOCUMENT, and the strongest source because it is written as
      supported-vs-unsupported rather than as an inventory of current use. It lists
      field props for "FormInput, FormSelect, FormDate", has an explicit "Not
      Supported in Field Props" section, and frames every unsupported item under
      "Unsupported Features (Require Frontend Code)". No multiline, no rows, no
      height, and no textarea component. ⚠️ Last modified 2026-02-27, so it is ~7
      months old -- old enough that a NEW component could exist un-documented, which
      is why this entry is a LIMITATION on the JSON surface and not a claim about
      Forge's source.

  CONSEQUENCE: a multi-row message box is a PRODUCT ASK (frontend code / Jira),
  not a configuration change. Anything the capability doc lists as unsupported is
  explicitly "Requires Frontend Code" -- that is the route, not a cleverer JSON.
  ⚠️ DO NOT INVENT A `resolvedName`. An unknown component name renders NOTHING and
  says nothing -- the retired `Convert-UsxCasing` whole-tree recase is the precedent
  (it collapsed Craft.js `nodes` and left only tab names showing). The most the
  proven vocabulary allows for a long field is a full-width row (`['12']`) with the
  metadata `maxLength`, which is what SC_SLED already ships.
