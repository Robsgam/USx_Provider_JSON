CONNECTCIC BUILD RULES -- PROVIDER JSON STRUCTURE
====================================================
How to structure a provider JSON from scratch.
Last updated: 2026-06-09
Source: NJ_NJCJIS (v2.3), NY_NYSPIN_EJUSTICE (v1.1), AZ_AZDPS (v2.0),
        FL_FCIC (v3.0), HI_HCJDC_OFML (v1.1), TX_TLETS (v2.1),
        LA_LEMS (v2.0), CA_CLETS (v1.5)

See also:
  RULE_HANDLERS.txt     -- Handler signatures, arguments, usage patterns
  FIELD_REFERENCE.txt   -- Field code-type pairings, attributeTypeId rules
  QIDM_REFERENCE.txt    -- QIDM combination rules, merge/split decisions
  IMPORT_ERRORS.txt     -- Import error messages and fixes

================================================================================
0. PROVIDER NAMING AND FOLDER SETUP
================================================================================

  NAMING RULE: Provider folder name MUST match the metadata XML filename
  (minus the .xml extension). This is the canonical name for the provider.

  Example:
    XML file:  CA_SAN_LUIS_OBISPO.xml  ->  folder: providers/CA_SAN_LUIS_OBISPO/
    XML file:  NM_NMLETS_OFML.xml      ->  folder: providers/NM_NMLETS_OFML/
    XML file:  MD_METERS.xml           ->  folder: providers/MD_METERS/

  WHY: Mismatched names require renaming the folder, all doc files, all
  references in CLAUDE.md, README.txt, new_test_log.ps1, and every internal
  doc file. This was learned when CA_SAN_LOUIS_OBISPO and NM_NMLETS had to
  be renamed to match their XML filenames (CA_SAN_LUIS_OBISPO and
  NM_NMLETS_OFML). Rename propagation touches 10+ files per provider.

  VERIFICATION: Before creating a provider folder, open the metadata XML and
  confirm the filename. Use that exact name (case-sensitive) for the folder.

  RENAME PROPAGATION CHECKLIST (if a rename is ever needed):
    [ ] git mv the provider folder
    [ ] Rename all docs: STATUS.txt, BUILD_NOTES.txt, SQVR.txt
    [ ] Update doc file contents (provider name references)
    [ ] Update JSON_INVENTORY.md
    [ ] Update CLAUDE.md provider table
    [ ] Update knowledge-base/README.txt provider list
    [ ] Update tools/new_test_log.ps1 knownPaths hash
    [ ] Update any build scripts referencing the old name
    [ ] Grep full repo for the old name to catch stragglers

  ONE JSON IN ROOT RULE:
    Exactly one JSON file in the provider root folder at all times.
    - MC active:   <PROVIDER>_MC.json in root, BASE in phases/base/
    - MC archived:  <PROVIDER>_BASE.json in root
    NEVER both BASE and MC in root simultaneously. enforce.ps1 checks this.
    Build scripts must output to the correct location.

  SOURCE FOLDER SETUP (before any build):
    [ ] Copy metadata XML to source/<PROVIDER>.xml
    [ ] Copy devdoc PDF to source/<PROVIDER>.pdf
    [ ] Run extract_queries.ps1 on the XML to map query landscape:
        powershell.exe -ExecutionPolicy Bypass -File tools/extract_queries.ps1
          -XmlPath source/<PROVIDER>.xml -OutFile docs/<PROVIDER>_SQVR.txt

  DEVDOC TEXT EXTRACTION:
    [ ] Convert PDF to text for searchable reference:
        pdftotext "source/<PROVIDER>.pdf" "source/<PROVIDER>_DEVDOC.txt"
    [ ] Review "Basic Queries Supported" section -- this is the ONLY authority
        for WHICH queries to build. Metadata existence alone does NOT authorize
        building a query.

1. 3-BUNDLE STRUCTURE
================================================================================

  Every provider JSON contains exactly 3 bundles in this order:

  1. ENTITIES BUNDLE     name='ENTITIES', provider='MARK43'
     Contains all QUERYINPUTFORM configurations (entity input forms):
       - One QIF per entity sub-form (Vehicle-NY, Vehicle-OOS, Person-DL-NY, etc.)
       - Also contains the entity display order array.
     Rule: QUERYINPUTFORM belongs ONLY here. Never in the provider or RMS bundle.
       Adding a QIF to any other bundle causes duplicate entity form cards in the
       UI (LIMITATION #22).
     ENTITIES MUST BE FIRST. Confirmed AZ v2.0: forms do not render when ENTITIES
       is not the first bundle in the array.

  2. PROVIDER BUNDLE     name=[PROVIDER_NAME], provider=[PROVIDER_NAME]
     Contains all provider-specific configurations:
       - AUTHENTICATION (1)
       - QUERYRESULTDATAMAPPING (1)
       - QUERYMESSAGEFORMAT (1)
       - QUERYINPUTDATAMAPPING (1 per query/path -- most of the work)

  3. RMS BUNDLE          name='RMS', provider='RMS'
     Contains RMS-specific QIDMs for local record matching.
     Built from KB specs by tools/_build_rms_bundle.ps1.
     See Section 4 for RMS design decisions and per-provider flags.

  Top-level JSON structure:
    {
      "bundles": [ <entities_bundle>, <provider_bundle>, <rms_bundle> ]
    }

  Bundle-level properties (required on each bundle):
    configurations   array of config objects
    description      human-readable string (e.g., "Provider configuration for
                       AZ_AZDPS v1.0")
    name             bundle name
    type             'BUNDLE'   *** REQUIRED -- if omitted, platform silently
                       ignores the bundle. ***
                       Both the CommSys provider bundle AND the ENTITIES bundle
                       require this. Confirmed failure mode: AZ_AZDPS v2.1/v2.2
                       (forms did not render).
    provider         provider name (or 'MARK43' for ENTITIES, 'RMS' for RMS
                       bundle)

  BUNDLE ORDER: ENTITIES bundle must be first.
    Confirmed: AZ v2.0 -- forms do not render when ENTITIES is not first.
    Order: 1=ENTITIES (provider=MARK43), 2=PROVIDER, 3=RMS

  BUNDLE TYPE: Every bundle must have type='BUNDLE'.
    Confirmed: AZ v1.0. Missing type causes import rejection.

  LIMITATION #22: QUERYINPUTFORM in RMS bundle causes duplicate entity cards
    Confirmed: NJ, NY
    Rule: QUERYINPUTFORM belongs ONLY in the ENTITIES bundle (provider=MARK43).
    Adding it to any other bundle renders each form twice.

================================================================================
2. ENTITIES BUNDLE
================================================================================

  The ENTITIES bundle contains all QIFs and the entity display order.
  It is the FIRST bundle in the JSON.

  Bundle-level properties:
    name             'ENTITIES'
    type             'BUNDLE'
    provider         'MARK43'
    description      'Entity input form configurations'
    configurations   array of QUERYINPUTFORM objects
    order            entity display order object (see below)

  Each QUERYINPUTFORM targets one entity (Vehicle, Person, Boat, Firearm,
  Article). Multiple QIFs can target the same entity (e.g., Vehicle-NY and
  Vehicle-OOS). Platform groups all QIFs sharing a targetEntity into one
  tab/display group.

  Required QIF properties:
    type          'QUERYINPUTFORM'
    name          unique name (e.g., 'ENTITY_Vehicle_NY')
    label         display label (e.g., 'Vehicle - NY')
    targetEntity  entity name ('Vehicle','Person','Boat','Firearm','Article')
    provider      'MARK43'
    layout        object with default, CAD_DISPATCH, FIRST_RESPONDER variants

  Entity display order -- MUST be a nested object, NOT a flat array:
    WRONG:  "order": ["Vehicle","Person","Firearm","Article","Boat"]
    RIGHT:  "order": { "default": [...], "CAD_DISPATCH": [...],
                        "FIRST_RESPONDER": [...] }

    order: {
      default:          ['Person','Vehicle','Firearm','Article','Boat']
      CAD_DISPATCH:     ['Vehicle','Person','Firearm','Article','Boat']
      FIRST_RESPONDER:  ['Vehicle','Person','Firearm','Article','Boat']
    }

  Values MUST be targetEntity values. Not entity names, not config names,
  not entity labels. Confirmed: NJ, NY, AZ. Any other value type produces
  incorrect/alphabetical sort.
  Failure mode: flat array causes entity ordering failure; forms may not render.
    Confirmed: AZ_AZDPS v2.2 (2026-04-20). Fixed in v2.3 / v1.0 Phase 1.

  FIRST_RESPONDER layout key:
    Included in all three layout variants of each QIF.
    Whether FIRST_RESPONDER is actually recognized as a distinct rendering
    context by the platform is UNCONFIRMED as of 2026-04-14 (NY STATUS.txt).
    Include it in all builds (same as CAD_DISPATCH) -- functionally harmless.

================================================================================
3. PROVIDER BUNDLE CONFIGS
================================================================================

  The provider bundle contains four config types. Each has a required structure.
  Handler signatures and arguments are documented in RULE_HANDLERS.txt.

  ---- 3A. AUTHENTICATION CONFIG ----

  One per provider bundle. Handles login/credential authentication.

  Required properties:
    type                        'AUTHENTICATION'
    name                        [PROVIDER_NAME]
    description                 'Authentication configuration for [PROVIDER]'
    handlerFunction             'CommsysOriAuthenticationHandler'
    provider                    [PROVIDER_NAME]
    providerType                'Commsys'
    signInRequired              false
    deviceRegistrationOptional  false

  Standard attributes:
    ORI       size=12  sourceField=['ORI']          targetField='ORI'
    Mnemonic  size=25  sourceField=['mnemonic']     targetField='Mnemonic'
    UserName  rule=CommsysGetDexStateUserIdRuleHandler
              sourceField=['dexStateUserId']        targetField='UserName'

  Combination:
    requirements: set=['ORI','Mnemonic']  any=['dexStateUserId']

  ---- 3B. QUERYMESSAGEFORMAT CONFIG ----

  One per provider bundle. Defines the XML message wrapper structure.
  This config is IDENTICAL across providers -- copy as-is, change name and
  provider only.

  Required properties:
    type                  'QUERYMESSAGEFORMAT'
    name                  '[PROVIDER_NAME]_QueryMessageFormat'
    description           'Configuration for Query format'
    handlerFunction       'CommsysWsiOutgoingMessageHandler'
    provider              [PROVIDER_NAME]
    authenticationParent  'LawEnforcementTransaction'
    payloadParent         'LawEnforcementTransaction'

  No attributes or combinations. This config is structural only.

  ---- 3C. QUERYRESULTDATAMAPPING CONFIG ----

  One per provider bundle. Defines how provider XML responses are mapped to
  the ConnectCIC result display.

  Standard approach: built by Build-ProviderQrdm in _build_provider_helpers.ps1.
  The CommSys QRDM uses generic field mappings. Name and provider are set
  automatically from the -ProviderName parameter.

  When to validate: after first successful query returns data (not "No
  Returns"). Compare QRDM mapping field names against actual XML element
  names in the response. Update any mismatched field names. This is
  provider-specific work.

  ---- 3D. QUERYINPUTDATAMAPPING CONFIGS ----

  One per query/path. This is the bulk of the provider bundle work.
  Each QIDM uses handlerFunction='CommsysTransactionRequestHandler'.
  Full QIDM architecture, combination rules, and merge/split decisions
  are documented in QIDM_REFERENCE.txt.

4. RMS BUNDLE -- DESIGN DECISIONS
================================================================================

  The RMS bundle is built from KB specs by tools/_build_rms_bundle.ps1.
  No external template. The module encodes all design decisions below as
  code. Per-provider variations are controlled by flags (-KeepSsn, -SkipRace).

  DECISION 1 -- Vehicle: LicensePlateYear in licensePlateIn any[]
  -----------------------------------------------------------------------
    The standard RMS Vehicle QIDM includes LicensePlateYear in the
      licensePlateIn any[] combination. On instances without elastic mapping
      for this field, the combination may reject or misbehave.
    _build_rms_bundle.ps1 includes it by default.
    AZ_AZDPS: confirmed no elastic mapping — build script removes it.
    NJ, NY: LicensePlateYear kept (elastic mapping exists).

  DECISION 2 -- Vehicle: RegistrationState in licensePlateIn any[]
  ------------------------------------------------------------------
    The RMS Vehicle QIDM licensePlateIn combination includes
      RegistrationState in any[]. The hidden SelH 'RegistrationState'
      is populated and the RMS combination uses it for state filtering.
    _build_rms_bundle.ps1 includes it by default.
    Confirmed: NY v1.4, NJ v1.2, AZ v1.0.

  DECISION 3 -- Vehicle: licensePlateOutAndState combination
  ------------------------------------------------------------------
    The RMS Vehicle QIDM has a licensePlateOutAndState combination
      with set=['LicensePlateNumberOut','RegistrationStateOut']. When OOS
      plate uses licensePlateNumber instead of LicensePlateNumberOut, this
      combination can never fire.
    _build_rms_bundle.ps1 includes it by default. Providers that use
      single-field plate pattern remove it in their build scripts.
    Does NOT apply to: NJ (NJ uses LicensePlateNumberOut on OOS forms).
    Confirmed: NY v1.4.

  DECISION 4 -- Person: registrationStateAttrId (ALWAYS included)
  ----------------------------------------------------------------
    The RMS Person QIDM includes a registrationState attribute. Without
      this, person searches (OLN, Name) fire without a state filter in
      the RMS elastic query.
    _build_rms_bundle.ps1 always includes:
      name='registrationState', sourceField=['RegistrationState'],
      targetField='registrationStateAttrId', useAttributeId=true
      Add 'RegistrationState' to ALL person combination any[] arrays.
    IMPORTANT: registrationStateAttrId is a SINGULAR string (no
      ArrayWrapper). This differs from Vehicle which uses
      registrationStateAttrIds (array + ArrayWrapper).
    Applies to: all providers (always apply).
    Confirmed: NJ_NJCJIS v1.2 (2026-04-20) --
      registrationStateAttrId:"69509884952" (string).
    autoSelect=true: add to all RMS QIDMs so they fire automatically.
    Confirmed: AZ_AZDPS v1.0, NJ_NJCJIS v1.7, NY_NYSPIN_EJUSTICE v1.1.

  DECISION 5 -- Person: Sex attribute handling (INSTANCE-SPECIFIC)
  -----------------------------------------------------------------
    The RMS Person QIDM includes sex (sexAttrId) and sexOOS attributes
    with useAttributeId=true. Whether to keep or remove depends on the
    instance.

    KEEP (NIBRS reverse-lookup confirmed -- instance supports attr ID ->
      M/F/U):
      Form uses attributeTypeId=SEX + codeTypeProvider=NIBRS.
      Form stores numeric attr ID. CommSys QIDM codeTypeProvider=NIBRS
        converts to M/F/U.
      RMS useAttributeId=true passes attr ID as-is.
        sexAttrId:"69509891711" (string) CORRECT.
      DO NOT add AttributeArrayWrapperRuleHandler.
      DO NOT remove sex from RMS QIDM.
      CONFIRMED: NJ_NJCJIS, AZ_AZDPS, FL_FCIC (single-QIF only).
      NOTE: Prior "FL reverse-lookup broken" was wrong (2026-04-20). Actual
        failure was duplicate targetField from entity-split design. FL works
        with single Person QIF. See PROVIDER_CONSTRAINTS.txt FL-9.

    REMOVE (only when entity-split creates duplicate targetField):
      When duplicate Person QIFs cause two QIDM attrs with same targetField,
      reverse-lookup breaks. Form must use codeTypeCategory=NIBRS_SEX instead.
      useAttributeId=true + string "M" -> wraps in array ->
        sexAttrId:[69509891711] -> RMS 400 error.
      Fix: remove BOTH sex attributes from RMS QIDM attributes[] AND remove
        'SexCode' AND 'SexCodeOOS' from ALL combination any[]/set[] arrays.
      Pattern: filter by targetField='sexAttrId' (catches both 'sex' and
        'sexOOS' attributes).
      REQUIRED: NY_NYSPIN_EJUSTICE (uses entity-split design).
      UNCONFIRMED: any new instance -- test before assuming keep or remove.
      See PLATFORM_CONSTRAINTS.txt AP #18 for both-attr removal detail.

  DECISION 6 -- RMS CLEANUP: Remove unused fields (per-provider)
  ----------------------------------------------------------------
    The base RMS template in _build_rms_bundle.ps1 contains fields for all
    possible providers. Most providers only use a subset. Dead fields (no
    matching form fieldId) add JSON bloat and their combos never fire.
    Build scripts remove unused attrs/combos after calling Build-RmsBundle.

    Vehicle -- remove these attrs:
      LicensePlateNumberOut     (OOS dual-field plate pattern -- not used
                                  with NCIC single-field)
      RegistrationStateOut      (same)
      OwnerFirstName            (no owner search on form)
      OwnerLastName             (same)
    Vehicle -- remove these combos:
      licensePlateOutAndState   (references LicensePlateNumberOut +
                                  RegistrationStateOut)
      OwnerFirstAndLastName     (references OwnerFirstName + OwnerLastName)
    Vehicle -- clean any[] in remaining combos:
      Remove LicensePlateNumberOut, RegistrationStateOut, OwnerFirstName,
        OwnerLastName

    Person -- remove these attrs:
      socialSecurityNumber      (no SSN field on form)
      licenseNumberOOS          (no OOS-suffixed fieldIds on form)
      firstNameOOS              (same)
      lastNameOOS               (same)
      dateOfBirthOOS            (same)
      sexOOS                    (same)
    Person -- remove these combos:
      firstNameLastNameSocialSecurityNumber
        (references SocialSecurityNumber)
      driversLicenseNumberOOS
        (references OOS fieldIds)
      firstNameLastNameDriversLicenseNumberOOS
        (same)
      firstNameLastNameDateOfBirthOOS
        (same)
      firstNameLastNameOOS
        (same)

    Result: Vehicle goes from 10 attrs/4 combos to 6 attrs/2 combos.
            Person goes from 13 attrs/9 combos to 7 attrs/4 combos.
    Applies to: NJ, NY (confirmed 2026-04-24). Apply to all new providers.
    Exception: if a provider DOES use OOS-suffixed fieldIds (e.g., FL_FCIC
      DH-suffix), keep the OOS attrs/combos that match those fieldIds.

  Summary of AZ_AZDPS patches (as reference):
    PATCH 1: LicensePlateYear removed from Vehicle QIDM licensePlateIn any[]
    PATCH 2: RegistrationState added to Vehicle QIDM licensePlateIn any[]
    PATCH 3: RegistrationStateOut removed from licensePlateOutAndState set[]
    PATCH 4: registrationStateAttrId + RegistrationState added to all Person
               combos
    PATCH 5 (KEEP): sex retained in RMS (NIBRS confirmed AZ);
               autoSelect=true applied

  RMS POOL ISOLATION -- KNOWN OVER-SEND, FIX DESIGNED BUT GATED (2026-06-12):
    OBSERVED (FL v4.8 live, USx Tenant): full DL card -> RMS elastic query sent
    dlNumber + lastName + firstName + dateOfBirth + sexAttrId. Cause: RMS QIDMs
    follow the same union-pool serialization model as CommSys (LIMITATION #1) --
    all four Person combos' set[] are satisfied simultaneously, none have
    conditions, so the pool is the union of every combo's fields. The handler
    is not broken; the config has no pool isolation. Risk (UNVERIFIED): if the
    elastic search ANDs criteria, full-card searches over-constrain and can
    miss records an OLN-only search would find.

    FIX DESIGN (mirror CommSys FL v4.8 pattern, in _build_rms_bundle.ps1):
      1. driversLicenseNumber       set [operatorLicenseNumber]; any []
      2. firstNameLastNameDateOfBirth  set [first,last,dob];
         any [race,sex,state]; conditions [ field:["licenseNumber"], NOT_EXISTS ]
      3. firstNameLastName          set [first,last]; any [race,sex,state];
         same NOT_EXISTS condition
      Drop firstNameLastNameDriversLicenseNumber (unreachable under OLN-first).
      KeepSsn providers (AZ, TN): same treatment for the SSN combo at their rebuild.
      Effect: OLN filled -> dlNumber-only elastic query; name searches unchanged.
      Propagates to all 19 providers on rebuild (shared module).

    DO NOT APPLY UNTIL BOTH GATES CLEAR:
      G1 (impact): live RMS test with a record whose OLN matches but name
          differs -- compare OLN-only vs full-card results. If elastic ORs
          criteria there is no harm and the fix may be unnecessary.
      G2 (mechanism): conditions are live-proven ONLY on
          CommsysTransactionRequestHandler. Zero RmsRestPayloadHandler combos
          portfolio-wide use conditions -- verify the RMS handler honors them
          (or ask platform team) before relying on this fix.

5. QIF LAYOUT STRUCTURE
================================================================================

  All three layout variants required: default, CAD_DISPATCH, FIRST_RESPONDER.
  CAD_DISPATCH: same as default with CONTEXT_INFO_CARD (CAD unit + event
    dropdowns) prepended.
  FIRST_RESPONDER: same as CAD_DISPATCH.

  Node hierarchy:
    ROOT -> FORM_ROOT (Form, hidePageItems=true, layout='page')
         -> ROOT_PAGE (Page, title='Page 1')
         -> CARD_xxx (Card, optional title)
            -> ROW_xxx (Row, templateColumns=[...])
               -> FIELD_xxx (FormInput / FormSelect / FormDate / etc.)

  Multi-card layout: one card per query path (OLN card, Name/DOB card, etc.)
  BuildMultiCardLayout helper builds this automatically from cardDefs array.

  templateColumns: array of strings representing grid column widths.
    Single field: ['12']   (full width)
    Two fields:   ['6','6']  (equal width)
    Three fields: ['4','4','4'] or ['3','3','6'] (asymmetric)
    Four fields:  ['3','3','3','3']

6. BUILD MODEL -- SINGLE JSON, MULTI-CARD FROM START
================================================================================

  ONE BUILD SCRIPT → ONE JSON per provider. Always multi-card. No separate
  BASE/MC variants. The build script handles both QIDM definition and
  multi-card layout in a single pass.

  Output: <PROVIDER>.json (no _BASE or _MC suffix).
  Reports: docs/ (no docs/base/ or docs/mc/ subdirectories).

  HISTORY: Originally builds produced a BASE (single-card proof of concept)
  and then an MC (multi-card). In practice, BASE encouraged skipping queries
  and doubled maintenance (two scripts, two JSONs, two report directories
  per provider). All QIDMs are identical between BASE and MC; only the layout
  differs. Multi-card is the standard build model.
  Merged 2026-05-21 for NJ, FL, CA_CLETS. Other providers merge on rebuild.

  BUILD DISCIPLINE (still applies -- just one JSON now):

  Step 1: QIDM confirmation (single card mentally, multi-card in layout).
    Build all QIDMs and combinations first. Every field on the form, every
    combo requirement mapped. Run test_commsys.ps1 to verify all combos
    fire. Do NOT declare any query "MC expansion candidate" -- build 100%
    coverage from the start.

  Step 2: Layout refinement.
    Entities with 2+ distinct search paths get one card per path.
    QIDM does NOT change -- layout only.
    Retest only affected entities.

    Which entities benefit from multi-card:
      PROMOTE:  Any entity where two paths use mutually exclusive required
                fields (Plate vs VIN, OLN vs Name+DOB). Multi-card prevents
                accidental dual-population and gives operators clear search
                path navigation.
      SKIP:     Entities with one required field set (Firearm: Serial only;
                Article: Serial+Type). No structural search path separation
                to offer.

    Card titles: use ALL CAPS (platform renders plain text only).
      Good: 'DRIVER LICENSE - LICENSE NUMBER', 'VEHICLE SEARCH - PLATE'
      Bad:  'OLN search', 'Search by plate'

    RegistrationState on multi-card forms:
      If state is needed on multiple cards (e.g. Person OLN card + Name
      card), put RegistrationState on both cards. Same fieldId -- shared
      field pool keeps them in sync. Operator sets state once; it carries to
      all cards.

  Step 3: Split entity (multiple QIFs per targetEntity -- most providers
    never need this).
    Only when multi-card reveals a genuine state model conflict: two search
    paths require fundamentally different hidden state fields that cannot
    coexist in one QIF.

    Use SPLIT ENTITY when:
      - In-state path needs SelH+InpH (dual-field); OOS path needs visible
          RegistrationStateOOS.
      - Paths are logically different enough to be navigated as separate
          sub-tabs.
    Use MULTI-CARD (stay in Step 2) when:
      - Paths share a common state model (NCIC pattern covers both).
      - Paths are logically grouped under one query type.

  WHY QIDM-FIRST (lessons from NJ v1.0--v1.6 and NY v1.0--v1.10):
    NJ built multi-card and split-entity before QIDM combinations were
    confirmed. When OOS state failed it was impossible to isolate: was it
    the QIDM, the layout, or the state model? Re-investigating took
    multiple phases and dead ends.
    NY added multi-card during standup. Same confusion.
    Confirm all QIDMs first. Every failure before layout changes is
    unambiguously a QIDM or combination problem -- not a form layout
    problem.

  Decision reference for Person forms:
    DL only (NJ pattern): one QIF, two cards (OLN + Name)
    DL + DH (AZ/FL pattern): single QIF with all paths on one card, then
      split cards
    DL + DH + WINQ/MINQ (AZ pattern): all on single Person QIF; cross-fire
      prevented by distinct required fields (RaceCode in ACQW set[], Age in
      ACQM set[], DH-suffix fieldIds)
    DL + DH (separate QIFs, NY pre-2026-04-20 pattern): CONFIRMED layout
      complexity causes QIDM isolation issues (LIMITATION #26 shared field
      pool). Prefer single QIF.

7. STATE FIELD PATTERNS
================================================================================

  Two confirmed patterns for state handling. Choose based on instance support.
  ALWAYS test NCIC pattern on first import (ST-1: in-state query) before
  relying on it. If CommSys <State> element is absent on ST-1, fall back to
  dual-field pattern (Section 7b).

  Field-level code-type config details are in FIELD_REFERENCE.txt. This
  section covers the structural layout patterns only.

  ---- 7A. NCIC STATE PATTERN (preferred when supported) ----

  CONFIRMED: NJ_NJCJIS (2026-04-20), AZ_AZDPS (2026-04-20), NY (confirmed).
  UNCONFIRMED: FL, HI, TX, LA, CA -- test before using.

  Single visible Sel 'RegistrationState':
    type: FormSelect
    props: { fieldId: 'RegistrationState', attributeTypeId: 'STATE',
             initialValue: '<state>' }
    visible: true (operator selects any state including OOS)

  CommSys QIDM State attribute:
    { name: 'State', sourceField: ['RegistrationState'],
      targetField: 'State', codeTypeProvider: 'NCIC', size: 2 }
    NCIC reverse-lookup: stored attr ID -> 2-letter state code for outbound
      XML.

  CommSys combination any[]:
    'RegistrationState'  (form fieldId, not attribute name 'State')

  RMS QIDM (standard from _build_rms_bundle.ps1 -- no changes needed):
    useAttributeId=true + AttributeArrayWrapperRuleHandler
    Sends registrationStateAttrIds:[<dynamic attr id>] for any selected
      state.

  RESULT: One field. Operator selects once. CommSys receives
    <State>XX</State> and RMS receives registrationStateAttrIds:[<attr id>]
    for any state including OOS.
  No hidden fields. No dual-field architecture needed.

  INSTANCE TEST: Run in-state plate query first. If <State>XX</State>
    present -> NCIC confirmed. If absent -> codeTypeProvider=NCIC not
    registered for state on this instance. Fall back to Section 7b.

  ---- 7B. DUAL-FIELD STATE PATTERN (fallback when NCIC not supported) ----

  Use when NCIC state pattern is not confirmed on the target instance.
  Two hidden fields -- both in the form layout, both hidden=true:

  FIELD 1: SelH 'RegistrationState'
    type: FormSelect
    hidden: true
    props: { fieldId: 'RegistrationState', attributeTypeId: 'STATE',
             initialValue: 'NY' }
    Purpose: RMS reads fieldId='RegistrationState' and gets the attribute
      ID for state filtering.
    Rule: DO NOT add to QIDM. Must not reach outbound XML.

  FIELD 2: InpH 'RegistrationStateNY' (or 'RegistrationStateNJ', etc.)
    type: FormInput
    hidden: true
    props: { fieldId: 'RegistrationStateNY', initialValue: 'NY' }
    Purpose: QIDM sourceField -> targetField='State'. Sends literal 'NY'
      to outbound XML.
    Rule: Add to QIDM as an attribute with targetField='State'.

  DO NOT use attributeTypeId='STATE' on a field that is mapped in the QIDM.
  DO NOT use InpH for the RMS field -- RMS needs attributeTypeId=STATE to
    recognize the value.
  LIMITATION: OOS state not achievable for RMS with this pattern. See

================================================================================
11. MULTI-CARD LAYOUT RULES
================================================================================

  Multi-card is the standard build model.
  Multi-card isolates routing fields onto a separate OPTIONS card so officers
  cannot accidentally trigger the wrong query type.

  CORE PRINCIPLE:
    Routing fields (State, Stolen Search, etc.) go on an OPTIONS card.
    All search fields go on a single SEARCH card.
    The OPTIONS card is a SEPARATE card the officer must deliberately visit.

  DUPLICATE FIELDID ACROSS CARDS = INTERNAL SERVER ERROR (ISE):
    The same fieldId CANNOT appear on multiple cards within one entity.
    If two combos share a field, that field goes on ONE card only.
    Use the shared OPTIONS card pattern for fields in any[] of multiple combos.

  CARD STRUCTURE PER ENTITY (standard pattern):
    2-card layout: OPTIONS card + SEARCH card
    - OPTIONS: routing toggles (State, Stolen Search) + shared any[] (Image)
    - SEARCH: all primary search fields (Plate, VIN, Hull, Name, etc.)
    This is the tightest layout that still isolates routing.

    More cards only if the entity has fundamentally different search paths
    that would confuse officers when visible together. Most entities work
    with 2 cards.

  "LEAVE BLANK FOR [STATE]" LABEL RULE:
    On MC, "State (leave blank for [STATE])" is the standard label for
    ALL State fields that serve in-state vs OOS routing. This includes:

    - Vehicle Options card State: blank = FRQ (in-state), filled = RQ (OOS)
    - Boat Options card State: blank = FBQ (in-state), filled = BQ (OOS)
    - Person DL card State: blank = FDQ (in-state), filled = DQ (OOS)

    BOAT NAME/DOB EXCEPTION: Boat BQ name/DOB combos have State in set[],
    meaning State is REQUIRED even for in-state name searches (State=FL).
    Unlike Vehicle/Person, there is no in-state boat name query without State.
    Boat State label must add this exception: "leave blank for FL, required
    for name/DOB". FL_FCIC v4.1 confirmed during T18 testing.
    Check each provider's boat combos — if name/DOB requires State, add
    the exception to the label. Vehicle/Person do NOT need this because
    FRQ/FDQ name combos exist without State.

    This is safe on MC because DH uses its own registrationStateDH field
    (DH-suffix pattern). DL State does NOT affect DH queries.

    CONSISTENCY RULE: If one entity has the hint, ALL entities with
    in-state vs OOS routing must have it. Officers expect uniform labeling.
    FL_FCIC v4.1 confirmed: inconsistent labels confused the workflow.

  OPTIONS CARD TITLE:
    Use "Options" as the card title. Keep it simple and generic.
    The "leave blank for [STATE]" hint belongs on the FIELD LABEL, not the card title.
    Card titles describe the card's purpose; field-level instructions stay on field labels.
    ASCII only (LIMITATION #11). FL_FCIC v4.1 confirmed: verbose card titles cluttered the UI.

  WHICH FIELDS GO ON OPTIONS VS SEARCH:
    OPTIONS card fields:
    - registrationState (State) -- routes in-state vs OOS combos
    - relatedHitSearchIndicator (Stolen Search) -- routes FBQ vs QB (Boat)
    - imageIndicator (Image) -- shared any[] across all combos
    - Any field that appears in any[] of MULTIPLE combo types

    SEARCH card fields:
    - All primary identifiers (Plate, VIN, Hull, RegNum, Decal, etc.)
    - All secondary fields (PlateType, PlateYear, Make, Year, etc.)
    - Name fields (Last, First, DOB) for name-based combos
    - NCIC lookup fields (CG#, NCIC#, PCN)

  PERSON IS DIFFERENT:
    Person uses DH-suffix fieldIds instead of an OPTIONS card.
    DL card: OLN, State, Image, Name, DOB, Sex, Suffix
    DH card: OLN_DH, StateDH, PurposeCode, Name_DH, DOB_DH, Sex_DH, Attention
    queriesToDeselect isolates DL from DH (one-directional: DH deselects DL).

  QIDMS ARE INDEPENDENT OF LAYOUT:
    All QIDM combinations, attributes, and keyReferences are defined
    independently of the card structure. Layout changes do not affect QIDMs.

  CONFIRMED PROVIDERS USING THIS PATTERN:
    FL_FCIC v4.1: Vehicle(2 cards), Person(2 cards), Boat(2 cards)
    CA_eSUN v1.5: Vehicle(4 cards), Person(2 cards)
    OH_LEADS v1.3: Vehicle(6 cards), Person(2 cards)
    TX_TLETS v2.5: Vehicle(3 cards), Person(2 cards)
    HI_HCJDC_OFML v1.6: Vehicle(3 cards), Person(2 cards)

  DEVDOC-ORDER COMBOS + ROUTING CONDITIONS (standard as of FL v4.7, 2026-06-12):
    USER DIRECTIVE: combo array order follows the devdoc "Possible Combinations"
    listing order in EVERY QIDM. Devdocs list in-state combos first, so under
    first-match evaluation the in-state combos must carry routing conditions or
    later OOS/stolen combos become unreachable:
      - In-state (FRQ/FBQ/FDQ-style) combos: conditions State NOT_EXISTS
      - Stolen-toggle counterparts (FBQ Hull/Reg vs QB): additionally
        RelatedHitSearchIndicator NOT_EQUALS Y
      - Name combos in OLN+Name families: OperatorLicenseNumber NOT_EXISTS
        (the over-send fix: a fired combo serializes the union pool of all
        condition-matched combos -- LIMITATION #1 -- so failing the Name combos'
        conditions when OLN is filled removes Name/DOB/Sex from the XML)
    Conditions both route firing AND filter the serialization pool. NOT_EXISTS
    pool-filtering is now LIVE-PROVEN on two tenants (FL v4.8 + HI v3.4 T4/T5).
    Validator G-16 understands this: it only flags an earlier UNCONDITIONED combo
    whose set[] is a subset of a later combo's set[] (true shadowing).
    WIRE FORMAT IS MANDATORY: conditions nested in requirements; field = the FORM
    sourceField / fieldId (NOT the attribute name -- CORRECTED 2026-06-22, HI v3.4
    T5; an attribute-name field whose sourceField differs is silently INERT);
    value arrays (QIDM_REFERENCE Section 2a). Combo-level conditions are silently
    ignored (FL v4.7 live failure 2026-06-12).

    DEFAULTED-FIELD SUBSET-SHADOWING (HI VehicleRegistrationQuery, 2026-06-22):
    a combo whose set[] contains a DEFAULTED form field (e.g. vehicleTypeCode
    initialValue=1) plus a shared primary (LicensePlateNumber) is ALWAYS satisfied
    once the primary is filled -- the defaulted field is never blank. So it sits in
    the union pool permanently and bleeds its fields (VehicleTypeCode) into any
    co-satisfied OOS combo's XML. Fixes: (a) order the more-specific OOS combo first
    AND (b) give the defaulted-field combo an existence-only condition on the OOS
    discriminator's sourceField (M55L: LicensePlateTypeCode NOT_EXISTS; M55S:
    RegistrationState NOT_EXISTS) so it LEAVES the pool when the OOS combo applies.
    For routing purposes, a combo's EFFECTIVE required fields = set[] minus any
    field that has an initialValue. Validator flags when an earlier combo's effective
    set is a subset of a later one's (it will shadow it). Do NOT put the OOS
    discriminator in the defaulted combo's any[] -- it can never serialize there and
    it breaks the test conductor (HI v3.3 T16: RegistrationState in M55S any[] +
    NOT_EXISTS condition contradicted; removed v3.4).

  IDENTIFIER-PRIORITY GUARDRAIL (generalized HI v3.6 plate-wins + FL DL OLN-priority):

    PRINCIPLE: Within ONE QIDM, when two combos represent different search identifiers
    an officer can fill at the same time, the platform serializes the UNION of every
    satisfied combo's set[]+any[] (LIMITATION #1) -- not just the first match. To keep
    the higher-priority identifier's query clean, gate the lower-priority combos out of
    the union pool with a NOT_EXISTS condition on the higher-priority identifier's
    sourceField. Standard priority order:
      - Vehicle: Plate > VIN  -> every VIN-path combo gets <plate> NOT_EXISTS
      - Person : OLN  > Name  -> every Name-path combo gets <oln>   NOT_EXISTS
    NOT_EXISTS-only (existence test). NEVER a value-comparison condition (poisoned-array;
    those are silently inert -- QIDM_REFERENCE Sec 2a).

    CASING: conditions[].field = the provider's actual form sourceField token (FIELD =
    SOURCEFIELD rule). PascalCase providers (NJ/FL/HI) use ['LicensePlateNumber'] /
    ['OperatorLicenseNumber']; camelCase providers (TX/CA_CLETS/NY/AZ) use
    ['licensePlateNumber'] / ['operatorLicenseNumber']. Verify the token before editing.

  --- VEHICLE half (Plate > VIN) -- HI v3.6 plate-wins ---

  serialize. It is harmless but redundant on the live platform, and it actively BREAKS the test
  conductor (run_test_matrix Build-MinimalData pulls any[] fields into the minimal test data,
  which then trips the NOT_EXISTS and the combo falsely fails to fire). TX v3.12
  QBRegistrationNumber hit this: boatHullIdNumber was in both its any[] and its NOT_EXISTS

  scrub the gated field from that combo's any[]. ***

12. CAD DEFAULTS -- COMBINATION-LEVEL DEFAULT VALUES
================================================================================

  CAD dispatch does NOT apply QIF form initialValues. When CAD sends a query,
  only the fields CAD explicitly populates are present. Fields with form
  initialValues (ImageIndicator=N, RandomRequest=N, PlateType=PC, etc.) are
  absent from CAD-dispatched XML unless the QIDM combo has a defaults[] entry.

  RULE: Every field that meets ALL of these conditions needs a combo default:
    1. The field is in any[] (optional, not in set[])
    2. The corresponding form field has an initialValue
    3. The provider expects a value (field appears in XML spec)

  SYNTAX (inside requirements alongside set/any):
    defaults = @(
        [PSCustomObject]@{ field = 'ImageIndicator'; value = 'N' }
        [PSCustomObject]@{ field = 'RandomRequest';  value = 'N' }
    )

  In JSON output:
    "requirements": {
      "set": ["licensePlateNumber"],
      "any": ["randomRequest", "imageIndicator"],
      "defaults": [
        { "field": "RandomRequest", "value": "N" },
        { "field": "ImageIndicator", "value": "N" }
      ]
    }

  FIELD NAME: defaults[].field uses the QIDM attribute name (PascalCase
  targetField), NOT the sourceField (camelCase). This matches the server's
  attribute-level injection point.

  VALUE: The literal string value the server injects. Must match what the
  provider expects (e.g., 'N' for ImageIndicator, 'PC' for PlateType).

  STATE DEFAULTS:
    When a provider has State in any[] with a form initialValue (e.g., 'NJ'),

14. VISIBLE-FIRST MANDATE  (MAJOR DIRECTIVE)
================================================================================

  RULE: Every officer-facing query field MUST be built as a VISIBLE form field
  (hidden=false) by default. Do NOT hide a field, and do NOT auto-populate a
  field via a rule handler in place of a visible input, WITHOUT explicit user
  approval or live-test evidence that the platform requires it.

  ATTENTION FIELD -- EXCEPTION TO THE RULE (automated, by directive 2026-06-22):
    The Attention field is the ONE standing exception. Wherever Attention is
    part of a query, it MUST be auto-populated via the
    CommsysGetLastNameFirstNameInitialRuleHandler rule handler (no visible form
    field). This is the approved STANDARD, not a per-provider exception.
      QIDM attribute:
        name='Attention'; size=30; sourceField=['Attention'];
        targetField='Attention';
        rule={ function='CommsysGetLastNameFirstNameInitialRuleHandler' }
    The handler derives "LASTNAME F" (last name + first initial) from the
    query's name and serves as a response-correlation tag. Scope it to ONLY the
    query whose metadata lists Attention (e.g. DriverHistoryQuery); never attach
    it to queries whose metadata does not include Attention.
    SECURITY: the auto-derived value is name-sourced, so the outbound request
    XML MUST be properly escaped -- verify with an injection test (a name
    containing < & " ' ]]> must not break or inject into the XML).

  HISTORY / WHY THE REVERSAL: An earlier policy (FL_FCIC v3.9) exposed Attention
  as a visible field, attributing a form load/submit slowdown to the handler.
  That attribution is now doubted -- the slowdown was likely not handler-related,
  and WNG has since posted a platform performance fix that makes any residual
  degradation negligible. Per user directive (2026-06-22) the automated handler
  is restored as the standard; form-load performance is re-verified during HI
  live testing. The general visible-first rule still governs ALL OTHER fields.

  HOW TO APPLY (all fields EXCEPT Attention):
    - Build query fields as Inp (FormInput) / Sel (FormSelect) / Dt (FormDate),
      hidden=false. Use the field's natural fieldId.
    - Do NOT reach for InpH/SelH (hidden helpers) or an auto-populate rule
      handler as a first move. If you believe another field should be hidden or
      auto-filled, STOP and get user approval first, or wait for live-test
      evidence that the visible field breaks something.

  APPROVED EXCEPTIONS (fields that may be hidden / auto-populated without
  case-by-case approval -- documented platform requirements or standing
  directives, not conveniences):
    1. Attention -- auto-populated via CommsysGetLastNameFirstNameInitialRuleHandler
       wherever Attention is part of a query (standing directive 2026-06-22; see
       above). This is the standard, not a violation.
    2. RMS dual-field State -- SelH 'RegistrationState' (RMS) + InpH outbound
       state field -- ONLY when the NCIC single-visible-State pattern is
       unavailable for the provider. See Section 7. Prefer the single visible
       RegistrationState (NCIC) pattern, which has NO hidden fields.
    3. dexStateUserId -- auto-populated from the officer's RMS profile (AUTH).
    4. CAD / First-Responder dispatch context fields (CadUnit, CadEvent,
       LinkToEvent) -- injected by the CAD_DISPATCH / FIRST_RESPONDER variants.

  REQUIRED ATTENTION (CCH) -- EXEMPT: the automated handler is for OPTIONAL
  Attention only (DriverHistory-style, metadata any[]). Where Attention is
  REQUIRED (metadata set[], e.g. the CCH Criminal History query family), the
  officer must supply the routing value, so a VISIBLE field is correct and the
  name-derived handler is NOT applied. (TX_TLETS_CCH is the standing example;
  it is out of scope for the optional-Attention conversion.)

  ENFORCEMENT: verify_build.ps1 CHECK 8 ("Visible-First Mandate") scans every
  build. It WARNs on any hidden form field not on the whitelist above, AND on an
  OPTIONAL Attention attribute that LACKS the handler (the manual/visible case to
  convert). An Attention attribute WITH the handler is conforming (Info); a
  REQUIRED Attention (in a combo set[]) is exempt (Info). The check is
  non-blocking (WARN, not FAIL) so it does not break legacy providers mid-flight,
  but every WARN must be resolved before a build is declared DONE (0 WARN target).

  ATTENTION CONFORMANCE STATUS (automated handler = conforming):
    CONFORMING (handler present): HI_HCJDC_OFML, LA_LEMS, CA_eSUN, CA_VENTURA,
      OH_LEADS, TN_TIES.
    TO CONVERT (manual visible field -> automated handler): FL_FCIC, TX_TLETS.

15. SYNTHETIC KEYREF DOCUMENTATION (MANDATORY)
================================================================================

  RULE: Every QIDM in a build script that has more than one combo MUST include
  a LIMITATION comment block immediately before the $...Query = [PSCustomObject]@{
  line. This is mandatory on every new build and on every rebuild.

  WHY: ConnectCIC requires unique keyRefs per QIDM (LIMITATION #21). Provider
  metadata XML often uses the same keyReference for multiple transactions. Build
  scripts invent synthetic keyRef labels (e.g., DLICN, DALH, KQName) to satisfy
  the platform constraint. Without documentation, these invented names appear to be
  real provider transaction codes and cause confusion during debugging, auditing,
  and operator training. NY_NYSPIN testing found DLICN with no explanation --
  this standard was created 2026-06-09 to prevent recurrence.

  STANDARD COMMENT BLOCK FORMAT (insert before every $...Query definition
  whose QIDM has >1 combo):

    # PLATFORM CONSTRAINT: ConnectCIC requires unique keyRefs per QIDM (LIMITATION #21).
    # Metadata uses keyRef '<BASE>' for all <N> combos; synthetic labels (<LIST>) are
    # invented for platform routing only. NOT real <PROVIDER> transaction codes.
    # See PLATFORM_CONSTRAINTS.txt -- synthetic keyRef naming convention.

  For OOS-split combos (LIMITATION #36 Choice OOS rule), use instead:
    # PLATFORM CONSTRAINT: <KEYREF> is a synthetic keyRef (NOT a real <PROVIDER> code).
    # Metadata uses a Choice combo with State in extended-Set; LIMITATION #36 requires a
    # dedicated OOS combo with State in set[]. <IN_STATE_KEYREF> stays in-state only.
    # See PLATFORM_CONSTRAINTS.txt -- Choice OOS rule (LIMITATION #36).

  SYNTHETIC KEYREF NAMING CONVENTIONS (from PLATFORM_CONSTRAINTS.txt):
    - DH Name path:   DALL → DALH   (H = history/name path)
    - DH OOS:         DALL → DALLOUT, DALH → DALHOUT  (OUT = out-of-state)
    - DL Name path:   DLIC → DLICN  (N = name path)
    - FL/TX pattern:  Base_FieldName (e.g., KQName, FRQLicensePlateNumber)
    - CA pattern:     Base.suffix  (e.g., NLTS.DQ.N, IR.QVC.O)
    - NJ VehReg:      RQ_RAND, RQN_RAND  (_RAND = RandomRequest=Y routing split)

  ENFORCEMENT: verify_build.ps1 CHECK 9 ("Synthetic keyRef Documentation")
  WARNs on any multi-combo QIDM that lacks a LIMITATION #21/#36 comment within
  40 lines of the first keyReference in the build script. 0 WARN is required
  before declaring any build DONE.

  STATUS (2026-06-09): NJ, FL, CA_CLETS, TX, NY all CLEAN (CHECK 9 PASS).

16. ADDING AN OVERLAPPING QUERY FAMILY (SUFFIX-ISOLATION)
================================================================================

  When you add a NEW family of queries to an entity that ALREADY has cards
  (e.g., CCH criminal-history queries onto the Person form that already hosts
  DL/DH/OPTIONS), the new queries almost always reuse field NAMES that the
  existing cards use (Name, BirthDate, SexCode, RaceCode, ImageIndicator,
  State, etc.). A fieldId may appear on only ONE card per entity QIF --
  duplicate fieldId across cards = Internal Server Error (AP: no_duplicate_fieldid).

  RULE -- SUFFIX-ISOLATION (generalizes the DH-suffix pattern):
    Give EVERY form field of the new family a family suffix on the fieldId /
    sourceField (e.g. nameLastCCH, birthDateCCH, sexCodeCCH, imageIndicatorCCH).
    Keep the XML-facing targetField as the metadata name (BirthDate, Name, ...).
    This guarantees zero collision with the existing cards. Put the new family
    on its own card(s); a shared "<FAMILY> OPTIONS" card holds the fields used
    by nearly every combo (the OPTIONS pattern).

  AUTOSELECT FOR OPT-IN / RESTRICTED FAMILIES:
    Set autoSelect=false on the new family's QIDMs and expose each as a named
    checkbox via queryLabel = the transaction. The officer explicitly picks the
    query. This prevents co-fire with the base autoSelect queries and removes
    any need to share/reuse base fields (reuse couples inputs and risks co-fire;
    full isolation is cleaner -- confirmed TX_TLETS_CCH 2026-06-09).

  CHOICE SPLITS: a metadata <Choice> of multiple <Set>s (e.g. CCH QH name path
  with SSN-or-Misc, QWI with DOB|Misc|SSN) becomes one combo PER inner <Set>,
  each with a synthetic keyRef (QH.NAME.SSN, QH.NAME.MISC, QWI.DOB, ...) and the
  Section 15 LIMITATION #21/#36 comment.

  ADDING NEW queryLabels (MANDATORY pair-update):
    A new query family needs new queryLabel values. You MUST add them in BOTH:
      1. tools/verify_build.ps1  -> $validLabels array
      2. CLAUDE.md  -> "### queryLabel Standard" table
    audit_repo.ps1 CATEGORY 3 fails unless the two match exactly. queryLabels
    MAY contain parentheses (e.g. "CCH Criminal History (QH)") -- the
    Get-ValidLabels parser is paren-safe as of 2026-06-09.

  NEW-PROVIDER ONBOARDING FRICTION (new_provider.ps1):
    The scaffolder emits a legacy BASE+MC stub pair and stub docs. For the
    single-JSON model: delete the build_*_mc.ps1 stub, and populate the three
    stub docs so repo audit passes -- JSON_INVENTORY.md must NOT contain
    "(no builds yet)" and must cite the version; STATUS.txt must carry the
    validator score (NNP/0F) not "Not built"; SQVR.txt must mention the version.
    sync_version_docs does not fully de-stub a brand-new provider.

17. HYPOTHESIS QUARANTINE + ITERATE-PHASE GATE (gap-proofing)
================================================================================

  WHY: builds were always hard-gated (validate/verify_build), but the
  test->change->iterate phase was prose-trusted. Two failure modes recurred:
  (1) a provider carried stale [CONFIRMED] markers / untested combos / missing
  XML / a stale TEST_MATRIX yet still "passed" and got called done; (2) an
  unverified platform HYPOTHESIS was written into the KB + both simulators as
  "live-proven" before the confirming test ran (the FL v4.7->v5.0 churn). Both
  are now tool-enforced.

  RULE A -- CLAIM STATUS CONVENTION (enforced by tools/verify_claims.ps1):
    Every platform-behavior assertion in knowledge-base/*.txt and in the
    simulators (test_commsys.ps1, run_test_matrix.ps1) carries a status line:
      STATUS: LIVE-PROVEN <test-log path>            -- confirmed by a COMMITTED log
      STATUS: HYPOTHESIS <named discriminating test>  -- not yet proven
    * LIVE-PROVEN MUST cite a path that exists (archived logs under
      tests/_archive_pre_v*/ count -- they are committed evidence).
    * A HYPOTHESIS MUST NOT be encoded in a simulator as fact. Simulate it only
      as an explicit assumption, and do not write the verdict to KB until the
      discriminating test log is committed.
    verify_claims.ps1 also flags any concrete test-log path citation that no
    longer resolves (e.g. a log moved to _archive on a reset).

  RULE B -- ITERATE-PHASE GATE (tools/audit_test_coverage.ps1 -Gate):
    Per provider, the gate computes one verdict:
      CLOSED                -- every combo [CONFIRMED]-with-XML or [APPROVED SKIP];
                               TEST_MATRIX combo count == JSON; version aligned.
      INCOMPLETE-consistent -- combos still [PENDING], no contradiction (a fresh,
                               not-yet-tested build -- legitimate, but NOT done).
      INCONSISTENT          -- blocks: stale [CONFIRMED] vs tests/.test_version,
                               more [CONFIRMED] markers than XML-bearing logs, or
                               TEST_MATRIX combo count != JSON combo count.

  Both run as enforce.ps1 PHASE 6 (blocking). "DONE" = CLOSED + claims verified.
  TEST_MATRIX is regenerated automatically by reset_test_package.ps1 on every
  rebuild so its combo count never drifts from the JSON.
  See TESTING_REQUIREMENTS.txt Section 11 GATES 4-5, QIDM_REFERENCE.txt Sec 2a.

18. CONDITIONAL-REQUIRED FIELD PATTERN (devdoc "must be filled if X=Y")
================================================================================

  PROBLEM: Devdoc says field A is required when field X=Y (e.g. EmailAddress required
  when ImageIndicator=Y). Value-comparison conditions are inert (poisoned-array rule --
  QIDM_REFERENCE.txt Sec 2a), so you cannot enforce "required if X=Y" via conditions[].

  SOLUTION: Image-variant combo split.

  Design rules:
  1. Create TWO combos per routing path: an "Image" variant and a "plain" variant.
  2. Image variant: put the dependent field (X, e.g. imageIndicator) AND any co-required
     fields (e.g. reasonCode) in any[] ONLY. Put the conditionally-required field (A,
     e.g. emailAddress) in set[]. This combo fires only when A is present.
  3. Plain variant: OMIT X, A, and co-required fields entirely from both set[] and any[].
     This combo fires when A is absent. By union-exclusion semantics (QIDM_REFERENCE.txt
     Sec 1d), X is excluded from the XML because it appears only in the non-matching
     Image variant. Field X therefore CANNOT serialize without A.
  4. Combo ordering: Image variant FIRST (more set[] fields = more specific).
  5. Toggle field must be a typed FormInput with no initialValue. Do NOT use an
     initialValue field as the toggle (LIMITATION #31 -- initialValue not counted for
     set[] matching). For Email/Image, emailAddress (typed FormInput) is correct;
     imageIndicator (initialValue=Y) is NOT.
  6. defaults[]: $imgDefsDH on Image variants (inject Image=Y, Reason=C, State=TX);
     $noImgDefsDH on plain variants (inject only Purpose=C, State=TX).

  RESULT: X=Y (e.g. Image=Y) can serialize ONLY when A (Email) is present. No-photo
  (A absent) fires freely. CAD path fires the plain combo (no email source available).

  PRECEDENT: TX_TLETS v3.8 DriverHistoryQuery (KQNameImg/KQName/KQOLNImg/KQOLN).
             LA_LEMS DP/DQ (ImageIndicator in set[] of DP vs any[] of DQ -- same split
             with imageIndicator as the toggle; LA_LEMS is not constrained by Lim #31
             because its imageIndicator field has no initialValue).

  PORTFOLIO NOTE: Other providers with DH may have the same devdoc constraint. Check
  at each provider's rebuild -- do not mass-sweep (one-provider-at-a-time rule).

19. BUILD REPRODUCIBILITY CONTRACT
================================================================================

  CONTRACT: a provider's committed <PROVIDER>.json MUST equal what its build script
  produces from current inputs (KB + shared modules). The build is the source of
  truth; the committed JSON is a cached artifact of it.

  TWO DISTINCT FAILURE MODES (audit_reproducible.ps1 separates them):
    - NON-DETERMINISTIC: two fresh builds (same moment, same inputs) differ.
      That is a BUILD BUG -- fix it. The build must not depend on anything that
      varies run-to-run.
    - STALE: builds are deterministic, but the committed JSON differs from a fresh
      build. The commit predates a KB / shared-module change. Not a bug -- rebuild
      that provider to bring it current (one-provider-at-a-time).

  INTENTIONALLY VARIANT FIELDS (normalized out of the reproducibility compare; do
  NOT treat their drift as non-determinism):
    - top-level "version" (stamped by Write-ProviderJson from build-script $Version).
    - PlateYear / LicensePlateYear initialValue = current year (Get-Date). This
      makes a raw build reproducible only WITHIN a calendar year. audit_reproducible
      normalizes it; if you ever need cross-year byte-stability, pin the year
      instead of deriving it. (No other Get-Date value reaches JSON content -- dates
      appear only in the phase-archive FILENAME.)

  DETERMINISM REQUIREMENTS already in place: [ordered] dicts everywhere (stable
  key order), ConvertTo-Json -Depth 100, UTF-8 no-BOM. Do not introduce Get-Random,
  unordered hashtables, or time/now-derived JSON content.

  KEEPING A REBUILD = a real version bump: bump build-script $Version, add a
  BUILD_NOTES entry (CHANGED/REASON), reset_test_package, sync_version_docs +
  CLAUDE.md row, build_report, enforce green. (feedback: full-rebuild-audit,
  rebuild-restarts-testing, bump-build-script-version.)

  GATE: audit_reproducible.ps1 -Path <json>  (or enforce.ps1 -Reproducible; opt-in
  because it re-runs the build twice per provider). Build to scratch via the
  $env:REPRO_OUTPATH hook in Write-ProviderJson -- never compare by overwriting the
  committed file.

  PRECEDENT (2026-06-24): NJ_NJCJIS v4.5 reproduced byte-identical; FL_FCIC v6.5 and
  HI_HCJDC_OFML v4.1 were DETERMINISTIC-but-STALE (predated the version field + the
  VehicleMakeName QRDM fix) -> rebuilt to v6.6 / v4.2.
