BoatQuery | BQ | Attention | devdoc-optional-unreachable | THE FIRING VARIANT DOES NOT DEFINE Attention, so wiring it would OVER-PERMIT -- but the ALTERNATIVE DISPOSITION is recorded here because it is a real design question, not a closed one. Devdoc BoatQuery #2 is "(mand) RegistrationNumber, Attention [opt State]". LA metadata offers FOUR boat variants and they split the two optionals between them: QB{RegistrationNumber} = Set[RegistrationNumber] Any[Attention] and BQ{RegistrationNumber} = Set[RegistrationNumber] Any[State]; likewise for hull. This build implements BQ{reg} (State) for the registration search and QB{hull} (Attention) for the hull search. So a registration search cannot transmit Attention, and adding it to BQ any[] would emit a field that transaction does not define. THE TWO REG VARIANTS ARE ROUTING-INDISTINGUISHABLE -- both are Set[RegistrationNumber] and differ only in their optionals, and optionals cannot discriminate because routing tests field PRESENCE against set[] plus conditions -- so BOTH cannot be built; whichever is ordered first takes every fill. That is a routing IMPOSSIBILITY, not a preference. THE OPEN QUESTION, FLAGGED NOT DECIDED: the devdoc marks Attention MANDATORY and State merely optional on this item, so implementing QB{reg} instead of BQ{reg} would transmit the MANDATORY field and lose only an OPTIONAL one -- strictly better devdoc conformance. That is a deliberate design swap on a provider with a standing hold (COMMSYS ASKS ARE ON HOLD, Rob 2026-08-18; LA devdoc-vs-metadata inversions are recorded, not owed), so it is not being made unilaterally.
