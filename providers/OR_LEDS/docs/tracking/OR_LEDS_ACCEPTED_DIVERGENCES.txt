# SUPPRESSION-SCOPE: direction-aware
#   Opted in 2026-08-01. Without this marker a registry row suppresses EVERY check for its
#   (query, keyRef, field) triple regardless of what the recorded decision actually said -- so a row
#   granting "this field may ride in any[]" also silences the OPPOSITE defect (a field wrongly
#   promoted INTO set[]), and the gate goes mute somewhere it was never granted.
#   Narrowing is STRICTER and CAN turn a provider red by un-silencing a real finding. That is the
#   point: if it does, investigate the finding -- do NOT remove the marker.
#   Measured before/after opting in; result recorded in the commit.
# OR_LEDS ACCEPTED METADATA DIVERGENCES
# Read by tools/audit_metadata.ps1 (CHECK 4 / 4d). Each non-comment line records a
# set/any divergence that is intentional and correct, so the gate treats it as [NOTE] not [FAIL].
# Format (pipe-delimited): query | keyRef | field | rule | reason | source | date

BoatQuery | BQ.H | RegistrationNumber | devdoc-optional-unreachable | Firing variant BQ{BoatHullIdNumber} = Set[BoatHullIdNumber] Any[State] -- RegistrationNumber is NOT defined on it. It is the Set KEY of the SIBLING variant BQ{RegistrationNumber}, which the separate BQ.R combo implements. So a hull search that also carries a registration number correctly does not transmit it; adding it to BQ.H any[] would OVER-PERMIT a field this variant does not define, and would also blur the Hull>Reg identifier priority. | metadata-vs-devdoc | 2026-08-01
DriverLicenseQuery | DQ.N | Name | devdoc-optional-unreachable | Devdoc DriverLicenseQuery #1 "BirthDate, Name, [SexCode]" and #3 "BirthDate, Name, State, [SexCode, ImageIndicator]" both BRACKET SexCode as optional, but THIS provider's metadata DQ{Name} is Set[BirthDate, Name, SexCode] Any[ImageIndicator, State] -- SexCode is MANDATORY there, and DQ{Name} is the ONLY name variant (its lone sibling is DQ{OperatorLicenseNumber}), so there is no looser alternative to fall through to. METADATA IS FIELD-AUTHORITY, devdoc is QUERY-authority (KB rule B4). CONTEXT: SexCode was PROMOTED from any[] to set[] at v2.1 precisely BECAUSE metadata makes it mandatory -- with it in any[] the combination could FIRE WITHOUT IT and emit a request the metadata calls invalid (an UNDER-REQUIRED wire defect, the class gate 6d catches on a live log while 6c and 2i cannot see it at all). These NO-COMBO-FIRES findings are the KNOWN AND ACCEPTED CONSEQUENCE of that correct fix, not a regression: a devdoc-legal Name+DOB fill without Sex now matches nothing, which is exactly right, because metadata says such a request is incomplete. Reverting the promotion to satisfy this gate would trade an honest no-fire for a silently invalid wire request. Consequence stated plainly: a name-based licence search on this provider requires Sex. Verified against the raw XML Requirements 2026-08-01. | metadata-vs-devdoc | 2026-08-01

VehicleRegistrationQuery | RQ.V | VehicleMakeCode | devdoc-optional-unreachable | NOT BUILDABLE -- this provider OWN metadata does not define these fields on the firing variant. Devdoc VehicleRegistrationQuery combination #2 is "(In) VehicleIdentificationNumber, [VehicleMakeCode, VehicleYear]", so the devdoc DOES list both as optionals on the VIN search. But read from the raw XML <Requirements> per <Combination>, the sanctioned exception: OR_LEDS VehicleRegistrationQuery has exactly TWO variants -- RQ{LicensePlateNumber} = Set[LicensePlateNumber] Any[LicensePlateTypeCode, LicensePlateYear, State], and RQ{VehicleIdentificationNumber} = Set[VehicleIdentificationNumber] Any[State]. NEITHER defines VehicleMakeCode or VehicleYear, in Set or in Any. Searched EVERY transaction in the XML, not just VehicleRegistrationQuery: those two fields appear ONLY on Wanted-Person transactions (QLW, QW, and the PEWantedPerson Entry/Modify/Supplemental family EW/ET/SW/RW/MW/MT/MWXW/XN/EN) -- a different product surface, and none of it is the vehicle registration query. So keeping them would OVER-PERMIT: transmit two fields this transaction does not define. This is the structural devdoc-vs-metadata scoping mismatch the flat devdoc optional list cannot express, and metadata is FIELD authority (Rob 2026-08-18: "meta data wins over dev doc built to the spec"). REMOVED AT v2.4 IN FULL, not just from any[]: the two QIDM attributes went too (else ORPHAN attributes, wiring class B) and both form controls went with ROW_VEH_VIN_2 (else DEAD CONTROLS, wiring class A -- officer input silently discarded, which is worse than not offering the field).
