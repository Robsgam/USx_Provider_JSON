SEXCODE DUAL-VALUE CONFLICT -- Root Cause Analysis and Open Issue
  Date: 2026-04-09
  Status: UNRESOLVED -- pending decision on resolution approach

  ================================================================================
  BACKGROUND
  ================================================================================

  SexCode must satisfy two consumers simultaneously:

    1. FL_FCIC outbound query (DriverLicenseQuery, DriverHistoryQuery)
       Expects: code value -- "M", "F", or "U"
       XML spec: <Field name="SexCode" type="Alphabetic" maxLength="1"/>

    2. RMS Person Search query
       Expects: internal attribute ID (e.g. 69510840620)
       Elastic payload target field: "sexAttrId"
       Attribute config: useAttributeId: true

  These two requirements are mutually exclusive with a single form field.
  A field value that satisfies FL FCIC ("M") causes RMS to fail, and vice versa.

  ================================================================================
  HOW THIS EMERGED
  ================================================================================

  FL_FCIC_BASE (pre-entity-split):
    Form field:      attributeTypeId: SEX           -> sends attribute ID
    FL FCIC mapping: codeTypeProvider: NIBRS         -> INTENDED to convert to code value
    RMS mapping:     useAttributeId: true            -> works (receives attribute ID)

    Status: RMS worked. FL FCIC SexCode was BROKEN (attribute ID sent to outbound
    query) but was never tested/confirmed before entity split work began.

  Entity split (Changes 7-19):
    codeTypeProvider: NIBRS was dropped from FL FCIC mapping SexCode attributes.
    Form field remained attributeTypeId: SEX.
    FL FCIC SexCode continued to send attribute ID (latent bug now more visible).
    RMS continued to work.

  Change 32 (2026-04-09):
    Added codeTypeProvider: NIBRS back to FL FCIC mapping SexCode attributes.
    Form still used attributeTypeId: SEX.
    Result: codeTypeProvider did NOT convert the attribute ID to code value.
    Confirmed: codeTypeProvider in the mapping attribute cannot resolve a platform
    SEX attribute ID to a NIBRS code value -- the two ID spaces do not overlap.

  Change 33 (2026-04-09):
    Changed form field from attributeTypeId: SEX to codeTypeSource: NIBRS /
    codeTypeCategory: SEX (then iterated through NIBRS_SEX in subsequent commits).
    Result: FL FCIC now receives code value "M" -- FL FCIC fixed.
    New problem: RMS mapping (useAttributeId: true) now receives "M" instead of
    attribute ID -- RMS Person Search query begins failing.

  Additional tests (2026-04-09):
    Tried attributeTypeId: SEX + codeTypeProvider: NIBRS on the form field itself
    (HIDLE.json pattern). Result: did not resolve FL FCIC -- still sent attribute ID.
    NOTE: See HIDLE.json investigation below -- this conclusion may need to be
    revisited. The test may have been reverted before live validation was completed.

  Current state (codeTypeSource: NIBRS / codeTypeCategory: NIBRS_SEX on form):
    FL FCIC: receives code value -- WORKING
    RMS:     receives "M" for sexAttrId -- FAILING

  ================================================================================
  RMS COMBINATION SCOPE
  ================================================================================

  SexCode appears in requirements.ANY (optional) in ALL RMS Person Search
  combinations -- never in requirements.SET. Combinations confirmed:
    firstNameLastName, firstNameLastNameDateOfBirth, firstNameLastNameDriversLicenseNumber,
    driversLicenseNumber (and OOS/DH equivalents).
  SexCode is sent to RMS whenever the user fills in sex -- causing failure.
  If SexCode field is absent/empty, the RMS query succeeds.

  ================================================================================
  REVERSE LOOKUP INVESTIGATION -- CONFIRMED NOT AVAILABLE
  ================================================================================

  Investigated whether the RMS mapping attribute could perform a reverse lookup
  (code value "M" -> attribute ID) to eliminate the need for a dual-field approach.

  Findings (2026-04-09):
    Examined all provider JSONs: FL_FCIC.json, TX_TLETS.JSON, HIDLE.json, SDSO_USX.json,
    NJ_NJCJIS.json. Every single implementation uses identical config for sexAttrId:
      {"name": "sex", "sourceField": ["SexCode"], "targetField": "sexAttrId", "useAttributeId": true}

    The ONLY properties ever used on RMS mapping attributes across all providers are:
      name, rule, size, sourceField, targetField, useAttributeId
    No codeTypeProvider, codeTypeCategory, codeTypeSource, or any reverse conversion
    mechanism appears in any RMS mapping attribute in any provider JSON.

  Conclusion: No reverse lookup mechanism exists in the platform as currently used.
    There is no mapping-level way to convert a code value ("M") to an attribute ID
    for RMS. useAttributeId: true universally requires attribute IDs as input.
    A middle ground between Option A and Option B does not exist.

  ================================================================================
  RESOLUTION OPTIONS
  ================================================================================

  OPTION A -- Remove SexCode from RMS requirements.any (quick fix)
    Remove SexCode/SexCodeOOS/SexCodeDH from requirements.any in all RMS combinations.
    Remove sex/sexOOS/sexDH attributes from RMS Person Search query.
    Result: RMS queries work; sex is never sent as an RMS filter.
    Trade-off: Minor loss of RMS search precision (sex no longer narrows results).
    Recommended if sex filtering in RMS is considered non-critical.

  OPTION B -- Dual-field approach (full fix, same pattern as dual-state NJ_NJCJIS)
    Add a second sex field per person entity form:
      SexCode        codeTypeSource: NIBRS / codeTypeCategory: NIBRS_SEX
                     -> sends code value "M" -> used by FL FCIC mapping
      SexCodeRMS     attributeTypeId: SEX
                     -> sends attribute ID   -> used by RMS mapping
    Update RMS combinations: replace SexCode with SexCodeRMS in requirements.any.
    Update RMS sex attributes: sourceField -> SexCodeRMS.
    Trade-off: User must fill in two sex fields per person form (poor UX).
    Recommended if full RMS sex filtering must be preserved.

  ================================================================================
  DECISION -- 2026-04-09
  ================================================================================
  DEFERRED -- accepted as a known platform limitation of the ConnectCIC JSON
  configuration layer. No workaround exists without unacceptable trade-offs
  (broken RMS filtering or dual-field UX). Current state retained: NIBRS/NIBRS_SEX
  on form fields (FL FCIC XML receives correct code value; RMS sexAttrId receives
  code value instead of attribute ID and is expected to fail on sex filter).
  No further action planned unless a platform-side fix becomes available.
