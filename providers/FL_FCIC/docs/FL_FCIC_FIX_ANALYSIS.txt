LIMITATION #2: Platform evaluates ONE QIDM per (targetEntity, query) pair.
FL currently has multiple QIDMs per entity. Only the first fires; the rest
are silently ignored. All search paths must be merged into single QIDMs
with distinct keyReferences per combo.

Required merges:

  VEHICLE (4 QIDMs -> 1)
    Merge: VehicleRegistrationQuery + VehicleVINQuery
           + VehicleDecalQuery + VehicleTitleLienQuery
    Result: 1 QIDM with combos for Registration, VIN, Decal, TitleLien
    Each combo gets a distinct keyReference (e.g. RQ, QV, DECAL, TITLE)

  PERSON (4 QIDMs -> 2)
    DL: Merge FL_FCIC_DriverLicenseOLN + FL_FCIC_DriverLicenseQuery -> 1 QIDM
    DH: Merge FL_FCIC_DriverHistoryQuery + FL_FCIC_DriverHistoryOLN -> 1 QIDM
    DH QIDM uses DH-suffix fieldIds (already in place from v2.2)

  BOAT (7 QIDMs -> 1)
    Merge: BoatQuery + BoatHullQuery + BoatDecalQuery + BoatTitleLienQuery
           + BoatCoastGuardQuery + BoatNCICQuery + BoatProcessControlQuery
    Result: 1 QIDM with 7+ combos (Registration, Hull, Decal, TitleLien,
            CoastGuard, NCIC, ProcessControl)

  FIREARM (3 QIDMs -> 1)
    Merge: GunQuery + GunNCICQuery + GunProcessControlQuery
    Result: 1 QIDM with combos for Serial, NCIC, ProcessControl

  ARTICLE (4 QIDMs -> 1)
    Merge: ArticleSingleQuery + ArticleOwnerQuery
           + ArticleNCICQuery + ArticleProcessControlQuery
    Result: 1 QIDM with combos for Serial, Owner, NCIC, ProcessControl

Approach for each merge:
  - Union all unique attributes from the split QIDMs into one attribute list
  - Consolidate all combos with distinct keyReferences
  - Order combos by specificity (most set[] fields first)
  - Reference: NJ_NJCJIS and NY_NYSPIN_EJUSTICE use this single-QIDM pattern

  DO NOT ATTEMPT — CONFIRMED BROKEN

LIMITATION #28: Entity-split (multiple QIFs per entity) is NOT implementable.
Three approaches tested 2026-04-20 to 2026-04-21, ALL produce broken XML:
  v2.0: Different fieldIds (SexCode + SexCodeOOS) -> numeric ID in XML
  v2.3: Same fieldIds across QIFs -> numeric ID in XML
  v2.4: Mixed storage strategies -> numeric ID in XML

Root cause: Platform collects fields from ALL QIFs targeting same entity
into shared pool. Inactive QIF's empty value breaks reverse-lookup.

The v2.2 single-QIF-per-entity design is the ONLY working approach.
