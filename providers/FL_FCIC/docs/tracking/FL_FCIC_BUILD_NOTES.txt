PHASE 4 -- FIRST IMPORT ERROR: DUPLICATE KEYREFERENCE
================================================================================

IMPORT ERROR RECEIVED
  {"error":"Internal Server Error","details":[{"name":"Internal Server Error",
  "value":"Failed to import bundle: FL_FCIC_VehicleRegistrationQuery with error:
  Invalid Bundle configurations: [Duplicate key references found in query input
  data mapping.]"}]}

ROOT CAUSE
  The platform requires that each keyReference value appears AT MOST ONCE within
  a single QUERYINPUTDATAMAPPING's combinations array.

  The initial build had multiple combinations sharing the same keyReference in
  one mapping:
    - VehicleRegistrationQuery: FRQ appeared 3 times (Plate, VIN, Decal)
    - DriverLicenseQuery: FDQ appeared twice (OLN, Name)
    - DriverHistoryQuery: KQ appeared twice (Name, OLN)
    - BoatQuery: FBQ appeared twice (RegNumber, HullId)

FIX APPLIED
  Split each mapping with duplicate keyReferences into separate mappings --
  one mapping per primary search path. Multiple DIFFERENT keyReferences in
  one mapping ARE allowed (e.g., FDQ+QW in the same mapping is fine).

  Result: FL_FCIC bundle grew from 9 to 14 configurations:
    FL_FCIC_VehicleRegistrationQuery  FRQ  (Plate)
    FL_FCIC_VehicleVINQuery           FRQ  (VIN)
    FL_FCIC_VehicleDecalQuery         FRQ  (Decal)
    FL_FCIC_DriverLicenseOLN          FDQ  (OLN)
    FL_FCIC_DriverLicenseQuery        FDQ + QW  (Name -- different keys, OK)
    FL_FCIC_DriverHistoryQuery        KQ   (Name)
    FL_FCIC_DriverHistoryOLN          KQ   (OLN)
    FL_FCIC_BoatQuery                 FBQ  (RegNumber)
    FL_FCIC_BoatHullQuery             FBQ  (HullId)

USER CONSTRAINT
  "Do not use any other json in an attempt to fix" -- fix was applied purely
  from the build script using FL_FCIC.xml and HIDLE.json only.

IMPORT RESULT: Success after split.

PHASE 9 -- DRIVER LICENSE / DRIVER HISTORY MUTUAL EXCLUSION (v1.3 → v1.4)
================================================================================

HOW THIS WAS DISCOVERED
  After v1.3 was built, a question was raised: when the Driver History checkbox
  lights, can it automatically deselect Driver License? The initial assessment
  was that no such mechanism existed in the QUERYINPUTDATAMAPPING schema.

  However, while investigating whether the DriverHistoryQuery handler function
  (CommsysTransactionRequestHandler) was correct, HIDLE.json was inspected for
  comparison. Hawaii has both a DriverLicenseQuery and a DriverHistoryQuery
  mapping. Both use two fields not present in any of our FL_FCIC driver mappings:

    autoSelect         -- controls whether a combination self-selects when lit
    queriesToDeselect  -- lists query types to force-deselect when this one selects

  HIDLE.json pattern (confirmed source of truth):
    HI_HCJDC_DriverLicenseQuery:  autoSelect=true,  queriesToDeselect=["DriverHistoryQuery"]
    HI_HCJDC_DriverHistoryQuery:  autoSelect=false, queriesToDeselect=["DriverLicenseQuery"]

  This pattern fully enforces mutual exclusion and directly addresses the issue
  raised in v1.3: Driver History deselects Driver License when selected, and
  vice versa.

WHY autoSelect DIFFERS BETWEEN THE TWO QUERY TYPES
  Driver License (autoSelect=true): A DL query is the default behavior when a
  user enters person search fields. It should fire without requiring extra
  operator action. Auto-selecting the combination when fields are populated
  reflects the expected default workflow.

  Driver History (autoSelect=false): KQ is an intentional, Florida-specific
  query requiring PurposeCode and Attention -- fields with legal/policy
  significance. The operator must consciously activate the KQ combination.
  Requiring a manual click reinforces that this is a deliberate choice.

STATE OF FL_FCIC MAPPINGS BEFORE v1.4
  FL_FCIC_DriverLicenseOLN:    autoSelect=true (present), no queriesToDeselect
  FL_FCIC_DriverLicenseQuery:  no autoSelect, no queriesToDeselect
  FL_FCIC_DriverHistoryQuery:  no autoSelect, no queriesToDeselect
  FL_FCIC_DriverHistoryOLN:    no autoSelect, no queriesToDeselect

CHANGES MADE

  FL_FCIC_DriverLicenseOLN  (FDQ/DQ/QW + OLN):
    autoSelect = true              (already present -- no change)
    queriesToDeselect = ["DriverHistoryQuery"]   (added)

  FL_FCIC_DriverLicenseQuery  (FDQ/QW/DQ + Name):
    autoSelect = true              (added)
    queriesToDeselect = ["DriverHistoryQuery"]   (added)

  FL_FCIC_DriverHistoryQuery  (KQ + Name):
    autoSelect = false             (added)
    queriesToDeselect = ["DriverLicenseQuery"]   (added)

  FL_FCIC_DriverHistoryOLN  (KQ + OLN):
    autoSelect = false             (added)
    queriesToDeselect = ["DriverLicenseQuery"]   (added)

POWERSHELL NOTE
  queriesToDeselect is a single-element array. To prevent PowerShell's
  ConvertTo-Json from collapsing it to a plain string, it is typed explicitly:
    queriesToDeselect = [string[]]@('DriverHistoryQuery')
  This ensures the JSON output is ["DriverHistoryQuery"], not "DriverHistoryQuery".

LESSON LEARNED
  When using HIDLE.json as a template, inspect ALL fields on each configuration
  type -- not just the ones already present in the configurations being built.
  autoSelect and queriesToDeselect were present in HIDLE.json's driver mappings
  from the start but were not carried forward because the initial build focused
  on attributes, combinations, and routing keys. A full field comparison between
  HIDLE and each FL_FCIC mapping type should be done before declaring a mapping
  complete.

NO OTHER CHANGES
  No form fields, attributes, combinations, or other mappings changed.
  Total configuration count remains 25 (FL_FCIC) + 5 (ENTITIES) + 6 (RMS) = 36.

v2.6  2026-04-22  ATTENTION FIELD FIX -- match CA_eSUN / LA_LEMS pattern
================================================================================

ROOT CAUSE IDENTIFIED (2026-04-22):
  FL_FCIC had Attention as a visible FormInput with Attention in set[] on both
  DriverHistory QIDMs. Because set[] requires all fields to be populated before
  the combination fires, the platform auto-filled the Attention field with the
  officer's "LASTNAME F" (CommsysGetLastNameFirstNameInitialRuleHandler behavior)
  so the combination could fire. This produced correct output but through an
  implicit platform mechanism rather than explicit configuration.

  Confirmed by comparing CommSys XML logs:
    HIDLE/HI: Attention in any[] + user types value -> sends user value
    FL_FCIC:  Attention in set[] + no form entry   -> platform auto-fills "HALLOF G"
    LA_LEMS: Attention in any[] + handler on attr + no form field -> sends "LASTNAME F"

CORRECT PATTERN (CA_eSUN, LA_LEMS):
  - CommsysGetLastNameFirstNameInitialRuleHandler on the Attention QIDM attribute
  - No Attention FormInput on the form (handler reads from user session, not form)
  - Attention in any[] (optional -- fires automatically via handler)
