  *** 4K WOULD HAVE SHIPPED DEAD WITHOUT THE PREFILL REMOVAL, AND THAT IS BUILD_RULES 24. ***
  LicensePlateTypeCode was prefilled 'PC'. With that prefill, 4K's set[] collapses to an
  always-present [Plate] and collides EXACTLY with `4` -- and an exact collision is the one thing
  ordering CANNOT separate (the AZ_AZDPS DQPN/DQP case, where prefilling three set[] fields killed
  four combos). So a "built" 4K would have been a combo that looks present and can never fire, which
  is strictly worse than not building it. Removing the form prefill makes LicensePlateTypeCode a real
  DISCRIMINATOR: plate alone -> `4`, plate+type -> 4K, plate+year+state -> RQ.P.
  CAD IS NOT AFFECTED: combo defaults[] still supply PC on 4K and RQ.P, and defaults[] do not
  participate in ROUTING (audit_combo_reachability counts only form initialValue as always-present).
  The cost is that an officer now picks Plate Type when they want the 4K path -- which is exactly what
  "LicensePlateTypeCode is MANDATORY on 4K" means. audit_cross_provider does NOT gate a PC default, so
  this deviates from no enforced convention.

  BUSINESSINDICATOR IS DELIBERATELY NOT PREFILLED, for the same reason in the other direction: it is
  the ONLY discriminator between VC and VP. Prefilling it would make VC always match and kill the
  plain owner-name search. Built as a Y/N Select (YES_NO_UNKNOWN|NCIC) because the metadata types it
  Alphabetic with NO enumeration and no size -- a Select constrains the input where free text would
  not, and "Indicator" reads Y/N. If CLETS rejects Y/N, that is the value to change, not the routing.

v2.5  2026-08-18  RQ.P: LicensePlateYear was OPTIONAL where the metadata MANDATES it
  CHANGED: RQ.P `LicensePlateYear` moved from `any[]` into `set[]`, so its combination now reads
    set[caRequestPurposeCode, LicensePlateNumber, LicensePlateYear, RegistrationState].
    Nothing else moved: the CAD `defaults[]` twin (LicensePlateTypeCode='PC', LicensePlateYear=
    <current year>) and the registered RegistrationState promotion are unchanged.
  REASON: audit_requirement_fidelity reported
    "VehicleRegistrationQuery / RQ -> built 'RQ.P' UNDER-REQUIRED: LicensePlateYear (built any[])",
    the severity-1 class -- a combination that can fire WITHOUT a field its metadata variant makes
    mandatory sends a request the metadata calls INVALID.
    READ FROM THE RAW XML <Requirements> PER <Combination>, the sanctioned exception:
      RQ{LicensePlateNumber} = Set[CaRequestPurposeCode, LicensePlateNumber, LicensePlateYear]
                               Any[State, LicensePlateTypeCode]
    So Year is MANDATORY on the RQ plate path and State is merely OPTIONAL -- we had it exactly
    inverted (State in set[], Year in any[]). The State half is DELIBERATE and already registered
    ("OOS plate combo requires State; EXISTS-gated", 2026-07-23); only the Year half was a defect.
    NOT REGISTERABLE: a demoted-to-any row is only honest when a LOOSER metadata variant permits the
    field's absence, and RQ has no second plate variant. A plate-only search is legal under `4` and
    `QV{plate}`, but those are DIFFERENT keyRefs on a different transaction -- they cannot license an
    incomplete RQ.

  *** IT WAS INERT IN PRACTICE, AND I NEARLY REPORTED THE WRONG REASON FOR FIXING IT. *** My first
  read was "CAD ignores form initialValue, so a CAD-originated OOS plate query would send RQ with no
  year". That premise was FALSE and reading the build script refuted it in one line: RQ.P already
  carries `defaults[] LicensePlateYear = $currentYear`, so CAD is covered too. Between the form
  prefill ('2026') and that defaults twin, LicensePlateYear was ALWAYS present from either origin --
  the request was never actually invalid.
  SO WHY FIX IT AT ALL: because the guarantee was INCIDENTAL, and set[] makes it STRUCTURAL. The two
  failure modes are not equivalent. With Year in any[], removing the prefill later would make RQ.P
  fire and send an INVALID request -- silent, no gate would see it, because the wire looks well-formed.
  With Year in set[], removing the prefill makes RQ.P simply stop matching, and the fill falls to `4`:
  the wrong query, but a VALID one, and reachability would say so. Prefer the failure mode a gate can
  detect. Cost of doing it now: zero -- never imported, no current-version logs.

  MEASURED, and the numbers moved in a way worth explaining rather than hiding:
    UNDER-REQUIRED 1 -> 0. Branches compared held at 23 (no coverage traded away).
    Reachability 18 checked, ALL REACHABLE. audit_prefill_shadow 36 ordered pairs, 0 FAIL -- so
    adding a PREFILLED field to a set[] shadowed nothing here (BUILD_RULES 24 does not bite: no
    combination requires LicensePlateYear to be ABSENT).
    OVER-PERMITTED 6 -> 7 and "registered" 6 -> 5, which looks like a regression and is not one:

  ONE PRE-EXISTING FINDING THIS EXPOSED -- OPEN, NOT FIXED HERE, NEEDS A RULING:

    vehicleYear], but by its OWN authority metadata `4` has an **EMPTY <Any>** and `QV{plate}` defines
