TN_TIES ACCEPTED DIVERGENCES
============================
Provider: TN_TIES   Version: v2.0 (galvanized 2026-07-23)

These are intentional, reviewed departures from a literal 1:1 metadata->JSON mapping.
None are metadata violations (audit_metadata = 167 PASS / 0 FAIL / 0 WARN; CHECK 4d
"no fields over-promoted from metadata any[] to set[]"). Recorded here for audit trail.

--------------------------------------------------------------------------------
1. DROPPED FORM-IDENTICAL SHADOW COMBOS (28 metadata combos -> 22 built)
--------------------------------------------------------------------------------
TN's VehicleRegistrationQuery and DriverLicenseQuery metadata carry multiple keyRefs
whose form-facing requirements (set[] + any[]) are IDENTICAL -- they differ only in the
backend keyRef the server routes to. The platform fires the first matching combo, so a
second combo with an identical form signature can never be reached and cannot be
distinguished by any officer-visible input. There is no existence-only field that tells
them apart (value-comparison conditions are banned -- poisoned-array rule, validate G-31).
Per the OCATS / MD_METERS precedent ("server routes by keyRef; dropped form-identical
dups"), the redundant twin in each pair is dropped:

  VehicleRegistrationQuery:  *** WHICH TWIN IS KEPT WAS INVERTED AT v2.4 -- see the note below ***
    RV01  (in-state plate,  set[LicensePlateNumber])            == RQ01 (in-state plate)  -> DROPPED (KEPT RQ01)
    QV    {LicensePlateNumber}                                  == RQ01                   -> DROPPED (mined)
    RV03  (in-state VIN,    set[VehicleIdentificationNumber])   == RQ03 (in-state VIN)    -> DROPPED (KEPT RQ03)
    QV    {VehicleIdentificationNumber}                         == RQ03                   -> DROPPED (mined)
    QV    {DealerLicensePlateNumber}                            == RQ05 (dealer)          -> DROPPED (mined)
    RV    (OOS plate, set[Plate,Year,Type,State])               == RQ.P (OOS plate)       -> DROPPED (kept RQ.P)

  v2.4 CORRECTION -- THE PAIRS ARE UNCHANGED, THE NAMES WE KEEP ARE REVERSED. Through v2.3 these
  rows read "RQ01 == QV.P -> DROPPED (kept QV.P)", i.e. the surviving combos were named after the
  NCIC transactions QV.P / QV.V / QV.D. Two reasons that was the wrong way round:
    1. `QV` (with QA, QB, QG, QW) is a DATA-MINED transaction -- the devdoc says so on its own line:
       "Data-Mined Transactions: NCIC (QA, QB, QG, QV, QW) and DMV (Person and Vehicle) Tags returned
       from Data mining". A mined transaction is one TIES runs off our single request and returns
       tags for. It is not a query we send, so naming an OUTGOING combo after it invited exactly the
       wrong reading.
    2. It DID invite it. A note claiming in-state TN plate searches "reach NCIC not TIES/DMV" was
       carried in FOUR places and filed as needing Rob's ruling. It was impossible: THE KEYREF NEVER
       REACHES THE WIRE (a request carries <MessageType>VehicleRegistrationQuery</MessageType> plus
       the FIELDS, nothing else), so QV.P and RQ01 emitted BYTE-IDENTICAL bytes. Closed 2026-08-24;
       `tools\audit_data_mined.ps1` now states both facts at build time (build_phase1 step 5b).
  The kept combos now carry the metadata names for the paths they implement -- RQ01 (devdoc #1 in-state
  plate), RQ03 (devdoc #3 VIN), RQ05 (devdoc #4 dealer) -- and the mined QV twins are recorded as
  dropped alongside the RV/RV01/RV03 twins they always sat with. ZERO wire impact either way.

  DriverLicenseQuery:
    DQ02  (in-state Name, set[Name,BirthDate,SexCode])          == QWA (no-state Name)    -> DROPPED (kept QWA)

Net effect: no loss of officer-reachable query capability -- every distinct form signature
still fires. "Leave blank for TN" (no State) selects the in-state combos (RQ01 plate, RQ03 VIN,
QWA name); entering a State selects the ones that additionally REQUIRE and TRANSMIT State
(RQ.P / RQ.V / DQ.*). This mirrors NM_NMLETS_OFML / MD_METERS.

*** THE SENTENCE ABOVE USED TO SAY the blank-State paths "route to the NCIC national keyRefs",
and that phrasing was itself the misconception, corrected 2026-08-24. *** A keyRef does not route
anything: THE KEYREF NEVER REACHES THE WIRE. A request carries
<MessageType>VehicleRegistrationQuery</MessageType> plus the FIELDS, and that is the entire
identification. What the officer's State choice actually does is select WHICH FIELD SET is sent --
State-absent sends the plate alone (devdoc #1, in-state), State-present sends
plate+type+year+State (devdoc #2, out-of-state). The destination is TIES's business, decided from
the fields and from InquiryTypeIndicator (default 3 = registration AND hotfiles), with the NCIC
side returned by DATA MINING. Any statement of the form "keyRef X goes to system Y" in this file
or any other is wrong by construction; see tools\audit_data_mined.ps1.

2. Attention auto-handler feeder (DriverHistoryQuery)
--------------------------------------------------------------------------------
DH metadata marks Attention (Name of Requestor) Mandatory on the KQ combos. It carries a
CommsysGetLastNameFirstNameInitialRuleHandler, so it is auto-populated -- not officer-typed.
Implemented with the eSUN/AZ feeder pattern: a hidden InpH 'attention' (initialValue='X')
on the DH-OLN card, 'attention' in each KQ any[], and combo defaults Attention='X' so the
handler output serializes. This is the only hidden field in the provider (Visible-First
Mandate otherwise satisfied -- all DH-suffix fields are visible on their own DH cards).
