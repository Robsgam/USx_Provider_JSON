# --- AM : AdministrativeMessage -- EXACTLY 501 CHARACTERS (v1.11) ------------------------------
# set[FreeText]. ROB'S CALL 2026-09-17: "you can enter 501 chars". This REPLACES the short value
# that used to sit here, whose comment argued a short string "is enough to prove the tag transmits
# and a 501-char filler would make the captured log unreadable for no gain". That reasoning was
# right for proving the TAG and wrong for the question v1.11 raises, because v1.11 changed this
# control from FormInput to FormTextarea (CAPABILITY #48) and maxLength enforcement is UNMEASURED
# on a textarea. It is honoured on FormInput and relied on portfolio-wide, so a silent loss of the
# cap is a real regression risk -- and 501 is the metadata maximum (<Field name="FreeText"
# type="Alphanumeric" maxLength="501">), so this is a LEGAL boundary value, not an abuse case.
#
# WHAT A FULL-LENGTH FILL PROVES: that a 501-character message survives the control, the form state
# and the serializer intact -- i.e. nothing truncates at some lower limit nobody documented.
#
# âš ï¸ WHAT IT CANNOT PROVE, AND THIS IS WHY THE READABILITY OBJECTION LOSES: the driver assigns
# .value programmatically (driver.js setVal), and HTML maxLength constrains USER input only --
# typing and pasting. So no driver fill, at any length, can show whether an OFFICER is capped.
# That needs a human pasting >501 characters by hand. Two different questions; this covers one.
#
# THE SENTINELS ARE THE DESIGN, not decoration. 'USX501START-' ... '-END501USX' means truncation is
# visible at a glance in the captured wire instead of needing a character count, and the END
# sentinel arriving intact is positive proof nothing was cut. The digit filler makes any partial
# loss countable. This keeps the log auditable, which was the old comment's legitimate concern.

# --- AM : DestinationCode / DestinationCode2..5 -- DELIBERATELY NOT MAPPED, NEEDS ROB'S CALL ------
# emit_test_plan WARNs 5x: "Article AM any[]: 'DestinationCodeN' has no test value". That WARN is
# CORRECT SIGNAL and is being LEFT IN PLACE rather than silenced with a guess.
#
# WHY. Every other override in this file is a synthetic string that goes into a SEARCH. An
# AdministrativeMessage is not a search -- it DELIVERS free text to the ORI(s) named in these
# fields, into a queue a human at that agency reads. So inventing a 9-character ORI-shaped value
# does not make a test value; it picks a recipient. Guess wrong and we have sent an unsolicited
# message to a real South Carolina agency under the tenant's ORI, which no gate can undo.
#
# The SELF-ADDRESSED option (send it to the originating agency, so the message lands back in our
# own queue) is the obviously safe one, and it cannot be written here: `Build-Auth` takes the ORI
# from the TENANT at runtime, so the build does not know the string. It would have to be read off
# usx-sc-sled after the import and pasted in.
#
# CONSEQUENCE, stated rather than hidden: the AM combination has a plan test for set[FreeText] and
# will be driven, but its five any[] optionals will NOT be, so nothing proves those tags transmit.
# That is a real coverage hole in the AM entity and it is the only one in this provider.
