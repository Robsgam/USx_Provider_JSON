BoatQuery | QBN | RegistrationNumber | devdoc-optional-unreachable | GENUINE DEVDOC-vs-METADATA CONFLICT, and the FL precedent does NOT transfer. Devdoc BoatQuery #1 is 'BoatHullIdNumber [ImageIndicator, RegistrationNumber]' -- RegistrationNumber is a devdoc OPTIONAL on the hull path. But metadata models hull and registration number as SEPARATE search paths under one keyRef: QB set[BoatHullIdNumber] any[ImageIndicator] and QB set[RegistrationNumber] any[ImageIndicator]. Neither carries the other identifier in any[]. So when an officer fills hull AND reg number, the hull-over-regnum identifier-priority guardrail routes to QBN (hull), and QBN cannot carry RegistrationNumber without violating metadata FIELD authority. Riding it anyway would be an OVER-PERMIT. CONTRAST FL_FCIC v7.13, where the identical-looking finding WAS fixed by adding RegistrationNumber to FBQBoatHullIdNumber's any[] -- FL's metadata DID list it there (FBQ set[BoatHullIdNumber] any[DecalNumber, RegistrationNumber, Requestor, TitleLienInformation]), so riding it satisfied both authorities. Same symptom, opposite metadata, opposite answer. OFFICER IMPACT: entering hull + reg number sends the hull query only; the reg number is not transmitted. The reg number IS fully searchable on its own via QB. Alternative if Rob wants the combined fill honoured: drop the hull-over-regnum guardrail so QB (regnum) wins instead -- but that inverts the identifier priority and is a product decision, not a spec fix. FOUND ONLY 2026-07-31 after fixing the devdoc parser: NJ's devdoc puts the query name on the same line as the field-table headers, so 9 of 11 'Possible Combinations' blocks had no owner and were never parsed -- enforce 2p/2q reported PASS over them for months. | metadata-vs-devdoc | 2026-07-31
