NOT an invention: RegistrationNumber IS a metadata QB field (the set[] of the sibling alternative under the SAME keyRef), so this transmits a transaction-defined field. ORIGINAL OVERTURNED REASONING RETAINED FOR HISTORY: I claimed a GENUINE DEVDOC-vs-METADATA CONFLICT, and the FL precedent does NOT transfer. Devdoc BoatQuery #1 is 'BoatHullIdNumber [ImageIndicator, RegistrationNumber]' -- RegistrationNumber is a devdoc OPTIONAL on the hull path. But metadata models hull and registration number as SEPARATE search paths under one keyRef: QB set[BoatHullIdNumber] any[ImageIndicator] and QB set[RegistrationNumber] any[ImageIndicator]. Neither carries the other identifier in any[]. So when an officer fills hull AND reg number, the hull-over-regnum identifier-priority guardrail routes to QBN (hull), and QBN cannot carry RegistrationNumber without violating metadata FIELD authority. Riding it anyway would be an OVER-PERMIT. CONTRAST FL_FCIC v7.13, where the identical-looking finding WAS fixed by adding RegistrationNumber to FBQBoatHullIdNumber's any[] -- FL's metadata DID list it there (FBQ set[BoatHullIdNumber] any[DecalNumber, RegistrationNumber, Requestor, TitleLienInformation]), so riding it satisfied both authorities. Same symptom, opposite metadata, opposite answer. OFFICER IMPACT: entering hull + reg number sends the hull query only; the reg number is not transmitted. The reg number IS fully searchable on its own via QB. Alternative if Rob wants the combined fill honoured: drop the hull-over-regnum guardrail so QB (regnum) wins instead -- but that inverts the identifier priority and is a product decision, not a spec fix.
