NJ_NJCJIS -- PDF vs XML Inconsistencies
========================================
Created  : 2026-04-08
Sources  : NJ_NJCJIS.pdf (CommSys 2025) pp.2-3, section "Basic Queries Supported"
           NJ_NJCJIS.xml (ConnectCIC provider registration)
Scope    : Basic Queries Supported section only (ArticleSingleQuery, BoatQuery,
           DriverLicenseQuery, GunQuery, VehicleRegistrationQuery, VehicleStolenQuery).
           "Transactions Supported" (WMP-I) section not evaluated here.
Build rule: XML is the build authority. PDF-only fields excluded from config until
            confirmed on a live connection. See Section 4 for the vehicle testing
            precedent that PDF-only fields may be accepted by the server.

================================================================================

================================================================================

  VehicleStolenQuery  (PDF p.3, Basic Queries Supported)

  CommSys registering the transaction in the provider XML.

  PDF fields:
    ImageIndicator               O, 1    Y, N
    LicensePlateNumber           C, 2    (likely typo -- VehicleRegistrationQuery uses C,10)
    NCICNumber                   C, 10
    VehicleIdentificationNumber  C, 24
    VehicleMakeCode              O, 24

  PDF combinations:
    1. LicensePlateNumber [ImageIndicator, VehicleIdentificationNumber]
    2. NCICNumber [ImageIndicator]
    3. VehicleIdentificationNumber [VehicleMakeCode, ImageIndicator]

  Note: LicensePlateNumber listed as C,2 in PDF. Almost certainly a typo.
        VehicleRegistrationQuery uses C,10 for the same field. Confirm before building.

================================================================================
SECTION 2 -- XML MESSAGE KEYS INCOMPLETE
================================================================================

XML MessageKeys section declares only 5 keys:
  BQ, DQ, QA, QG, RQ

Missing from MessageKeys (used as keyReferences in combination definitions):
  BQN  (BoatQuery hull path)
  DQN  (DriverLicenseQuery OLN path)
  RQN  (VehicleRegistrationQuery VIN path)

Impact: None observed. Platform resolves keyReference from the combination
        definition, not the MessageKeys declaration. All three work correctly
        in live testing.

SECTION 3 -- FIELD AND COMBINATION INCONSISTENCIES
================================================================================

Each entry shows: what the PDF says / what the XML says / current config decision.

------------------------------------------------------------------------
ArticleSingleQuery
------------------------------------------------------------------------

  Fields
    PDF : ArticleSerialNumber (M,20), ArticleTypeCode (M,7), ImageIndicator (O,1)
    XML : ArticleSerialNumber (20), ArticleTypeCode (7)
          ImageIndicator -- NOT DEFINED in this transaction

  Combination
    PDF : ArticleSerialNumber, ArticleTypeCode [ImageIndicator]
          Both serial and type required; image optional
    XML : set=[ArticleSerialNumber, ArticleTypeCode], any=[] (no optional fields)

  Inconsistencies:
    1. ImageIndicator -- in PDF as optional; absent from XML entirely
       Config decision: excluded (follows XML)
    2. XML combination has no optional fields; PDF has ImageIndicator optional
       Config decision: any=[] (follows XML)

------------------------------------------------------------------------
BoatQuery
------------------------------------------------------------------------

  Fields
    PDF : BoatHullIdNumber (C,20), ImageIndicator (O,1,Y/N), RegistrationNumber (C,20)
    XML : BoatHullIdNumber (20), RegistrationNumber (8), State (2)

  Combination
    PDF : 1. BoatHullIdNumber [ImageIndicator, RegistrationNumber]
             Hull required; image and reg number optional
          2. RegistrationNumber [BoatHullIdNumber, ImageIndicator]
             Reg number required; hull and image optional
    XML : BQ  set=[RegistrationNumber], any=[State]
          BQN set=[BoatHullIdNumber],   any=[State]

  Inconsistencies:
    1. ImageIndicator -- in PDF as optional in both combinations; absent from XML
       Config decision: excluded (follows XML)
    2. State -- NOT in PDF; defined in XML as optional in both combinations
       Config decision: included (follows XML)
    3. RegistrationNumber size -- PDF says C,20; XML says maxLength=8
       Config decision: uses 8 (follows XML)
    4. Cross-optional fields -- PDF allows RegistrationNumber as optional when hull
       is primary (and vice versa); XML has no cross-referencing between the two paths
       Config decision: follows XML (no cross-referencing)

------------------------------------------------------------------------
DriverLicenseQuery
------------------------------------------------------------------------

  Fields
    PDF : BirthDate (C,8), OperatorLicenseNumber (C,20), ImageIndicator (O,1,Y/N),
          Name (C,30), SexCode (O,1,M/F/U), State (C,2)
    XML : BirthDate (8), Name (30), ImageIndicator (1), OperatorLicenseNumber (20),
          SexCode (1), State (2)
          All fields match between PDF and XML.

  Combinations
    PDF : 1. OperatorLicenseNumber, State [ImageIndicator]
             State is in the required part -- mandatory for OLN path
          2. (InState)    Name, BirthDate [ImageIndicator, SexCode]
          3. (OutofState) Name, BirthDate [ImageIndicator]
             Two separate name combinations; SexCode excluded for out-of-state
    XML : DQ  set=[BirthDate, Name], any=[SexCode, ImageIndicator, State]
              Single combination merging InState and OutOfState
          DQN set=[OperatorLicenseNumber], any=[ImageIndicator, State]
              State in Any[] (optional)

  Inconsistencies:
    1. State in DQN -- PDF requires State in OLN path (required, not optional)
       XML puts State in any[] (optional)
       Config decision: State in set[] (follows PDF -- required for OLN path)
       Confirmed working in live testing.
    2. InState vs OutOfState name combinations -- PDF has two separate combinations;
       XML merges into one with SexCode always optional
       Config decision: single DQ combination (follows XML)
       Practical impact: minimal -- SexCode is optional either way

SECTION 5 -- LIVE CONNECTION TEST PRIORITY
================================================================================

Vehicle testing confirmed: the NJ NJCJIS server accepts PDF-only fields not
registered in the XML (ImageIndicator and RandomRequest both confirmed 2026-04-08).

When a live connection is available, test the following PDF-only fields in order:

  1. GunQuery -- ImageIndicator (O,1,Y/N)
     Test: GunSerialNumber + ImageIndicator=Y. Check XML request for ImageIndicator.
     If accepted: add FormSelect YES_NO_UNKNOWN initialValue=N to Firearm form
     and add to gunQuery attributes + QG combination any[].

  2. GunQuery -- GunModel (O,11)
     Test: GunSerialNumber + GunModel value. Check XML request for GunModel.
     If accepted: add FormInput maxLength=11 to Firearm form
     and add to gunQuery attributes + QG combination any[].

  3. BoatQuery -- ImageIndicator (O,1,Y/N)
     Test: RegistrationNumber + ImageIndicator=Y. Check XML request.
     If accepted: add FormSelect to Boat form and boatQuery attributes + both
     BQ and BQN combination any[].

  4. ArticleSingleQuery -- ImageIndicator (O,1,Y/N)
     Test: SerialNumber + ArticleTypeCode + ImageIndicator=Y.
     If accepted: add FormSelect to Article form and artQuery attributes + QA any[].

  5. VehicleStolenQuery -- requires CommSys XML registration first.
     Cannot test until transaction appears in NJ_NJCJIS.xml.
