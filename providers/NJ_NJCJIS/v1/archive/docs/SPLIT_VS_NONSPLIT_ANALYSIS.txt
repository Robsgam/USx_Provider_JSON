NJ_NJCJIS / ConnectCIC -- Split vs. Non-Split Entity Configuration
===================================================================
Last updated: 2026-04-10
Author: Rob Sgambellone

This document tracks the trade-offs between split and non-split entity
configurations as discovered during NJ_NJCJIS development and testing.
Updated as new findings emerge.

Full platform limitation details: docs/NJ_NJCJIS_LIMITATIONS.txt

================================================================================
DEFINITIONS
================================================================================

NON-SPLIT (single merged config)
  - One QUERYINPUTFORM card per query type (e.g., one card for all vehicle
    searches -- NJ plate, OOS plate, VIN).
  - One QUERYINPUTDATAMAPPING per query type containing all combinations
    (NJ plate, OOS plate, VIN, etc.).
  - All fields for all sub-types are visible on the same card.
  - Platform routes the query by whichever combination fires first based on
    what the officer populates.

SPLIT (separate tabs per entity/sub-type)
  - Each sub-type gets its own tab (e.g., Vehicle - NJ, Vehicle - OOS,
    Person - NJ, Person - OOS).
  - Each tab has its own QUERYINPUTFORM with only the relevant fields.
  - Each tab has its own QUERYINPUTDATAMAPPING with only the relevant
    combinations.
  - Officer selects the correct tab before searching.

================================================================================
NON-SPLIT: PROS
================================================================================

1. Simpler JSON config
   - Fewer QUERYINPUTFORM nodes, fewer QUERYINPUTDATAMAPPING blocks.
   - Easier to read and maintain for small query sets.

2. No officer tab selection required
   - Officer fills whatever fields are relevant; platform routes automatically.
   - Lower cognitive load if officers are trained on NCIC-style "fill what you
     have" workflows.

3. Fewer keyReference uniqueness constraints
   - All combinations are in one QIDM; no _NJ suffix workarounds needed.
   - LIMITATION #19: Each combination within a single QIDM must have a
     distinct keyReference. In split configs, NJ and OOS sub-types that share
     a QIDM (e.g., VehicleRegistrationQuery) require unique suffixes such as
     _NJ on all NJ combinations to avoid import errors.

4. Fewer combinations needed overall
   - A single "all fields" combination can catch edge cases that a split config
     might miss if a user crosses tab boundaries (e.g., fills both plate and VIN).

5. Easier to validate during build
   - Fewer configs to verify; one pass covers all sub-types.

================================================================================
NON-SPLIT: CONS
================================================================================

1. No field isolation
   - LIMITATION #1: set[] and any[] control which combination fires, but ALL
     populated fields in the config are sent regardless of which combination
     matched. Example: OLN path fires but Name/DOB fields were pre-filled from
     a prior search -- those extras are sent along. Server has been observed
     tolerant of extras, but this is not guaranteed. True field isolation
     requires split configs.

2. Cluttered UX
   - All fields for all sub-types appear on one card.
   - Officer sees NJ plate, OOS plate, VIN, OLN, name, DOB, sex, race -- all
     at once, regardless of what they actually need.
   - LIMITATION #4: hidden is static only (true/false). No conditional
     show/hide based on user input or selected sub-type. No workaround
     available in JSON config.

3. Hidden state field ambiguity
   - NJ dual-field state pattern (SelH + InpH) must coexist on the same card
     with OOS state dropdown (codeTypeCategory=NJ_NIBRS_STATE).
   - Risk of field ID conflicts or unexpected RMS routing if hidden fields are
     not carefully namespaced.

4. Harder to document and test
   - Test matrix grows combinatorially -- every field combination must be
     verified against every routing path.
   - Split testing into separate tabs/sub-types is more natural.

5. Query display attribute ID issue is more visible
   - LIMITATION #18: The ConnectCIC summary widget surfaces the raw value of
     any field with attributeTypeId. The hidden SelH (RegistrationState,
     attributeTypeId=STATE) always displays its internal numeric attribute ID
     (e.g., 69509884952) instead of "NJ". No config fix -- server would need
     to support summary aliasing or accept plain 2-letter state codes. In a
     split config this cosmetic issue is isolated to the NJ tab only. In a
     merged card it appears on every search.

================================================================================
SPLIT: PROS
================================================================================

1. Clean UX per sub-type
   - Each tab shows only the fields relevant to that search type.
   - Officer intent is explicit: selecting the tab IS the routing decision.

2. True field isolation
   - Each tab's QUERYINPUTDATAMAPPING contains only the combinations for that
     sub-type. No risk of cross-contamination from sibling fields.

3. Simpler combination logic per tab
   - Fewer combinations per QIDM; each combination is easier to reason about.
   - Easier to add or remove combinations without affecting other sub-types.

4. Hidden field scoping
   - NJ dual-field state pattern is confined to the NJ tab.
   - OOS state dropdown is confined to the OOS tab.
   - No risk of the two hidden state fields interfering with each other.

5. Cleaner test logs
   - Each tab tested independently with a focused test plan.
   - Pass/fail is scoped to a specific sub-type version, not the whole config.

6. Easier to extend
   - Adding a new sub-type (e.g., Boat) is additive: new tab + new QIDM.
   - No changes to existing tabs or QIDMs.

================================================================================
SPLIT: CONS
================================================================================

1. keyReference uniqueness constraint
   - LIMITATION #19: When NJ and OOS sub-types share a QIDM
     (VehicleRegistrationQuery, DriverLicenseQuery), all keyReferences must be
     unique across the whole QIDM even if they live on separate tabs.
   - Resolution: suffix NJ combinations with _NJ (RQ_NJ, RQN_NJ, DQN_NJ).
     OOS combinations retain original names (RQ, RQN, DQ, DQN, BQ, BQN).

2. DQ combination isolation failure (tested v2.6)
   - LIMITATION #2: Splitting DL into two separate configs (OLN-only config +
     Name-only config) caused the Name (DQ) combination to fail when cold.
     OLN path worked; Name path did not fire -- no XML request was built.
     Root cause unknown. Hypothesis: platform locks onto the first-listed
     config and does not fall through to a second config for the same query.
   - Current production decision: Name + OLN merged in one QIDM.
   - See archive/SPLITDL_REFERENCE.txt for full source and retry strategy.
   - STATUS: revisit with live connection. May not apply in production.
   - FL_FCIC ALTERNATIVE (confirmed 2026-04-10): For multi-query person forms
     (e.g., DL + DH on the same tab), FL avoids split configs entirely by using
     DH-specific fieldId suffixes (NameFirstDH, NameLastDH, BirthDateDH, etc.).
     DH combinations require suffixed fieldIds; DL combinations require standard
     fieldIds. Officers fill one set or the other -- no cross-firing possible.
     Combined with autoSelect + queriesToDeselect on each QIDM, this fully
     handles mutual exclusion without split configs. See LIMITATION #22/#23.

3. Larger JSON config overall
   - More QUERYINPUTFORM nodes, more QUERYINPUTDATAMAPPING blocks.
   - More node IDs to keep unique across the full JSON.

4. Officer must select correct tab
   - Adds one step vs. non-split "fill and go" workflow.
   - Requires training / UI familiarity.

5. More build script complexity
   - More patches and form-builder helpers needed.
   - More test cases to maintain across all tabs.

================================================================================
PLATFORM LIMITATIONS AFFECTING BOTH APPROACHES
================================================================================

These are ConnectCIC platform constraints that apply regardless of split vs.
non-split. Full details in docs/NJ_NJCJIS_LIMITATIONS.txt.

--------------------------------------------------------------------------------
FORM LAYOUT
--------------------------------------------------------------------------------

LIMITATION #4 -- No conditional field visibility
  hidden is static only (true/false). Cannot show/hide based on user input.
  Workaround: single card with all fields visible; QIDM combinations handle
  query routing by what the user populates.

LIMITATION #5 -- No field styling
  No font size, color, weight, or emphasis props on any node type.
  Workaround: field ordering and Card titles only.

LIMITATION #6 -- No standalone text/label component
  Available components: Card, Row, FormInput, FormSelect, FormDate,
  FormCheckbox. No standalone text or label element exists.
  Workaround: Card.props.title for instructional text (plain text only).

LIMITATION #7 -- Card title prop renders plain text only
  HTML tags such as <strong> appear verbatim in the UI.
  Workaround: use ALL CAPS for emphasis in card titles.

--------------------------------------------------------------------------------
QUERY / COMBINATION BEHAVIOR
--------------------------------------------------------------------------------

LIMITATION #1 -- set[]/any[] control routing only; all populated fields sent
  set[] = required fields for the combination to fire.
  any[] = optional recognized fields; used for routing priority only.
  When a combination fires, ALL populated attributes in the config are sent,
  regardless of whether they appear in set[] or any[]. True field isolation
  requires split configs.

LIMITATION #2 -- DQ combination does not fire in isolation (split DL configs)
  See SPLIT: CONS #2 above.

LIMITATION #3 -- FormSelect blank/unselected field is not sent
  Platform does not serialize a FormSelect with no value selected.
  Fix: add initialValue to any FormSelect that should always be pre-populated.
  A cleared FormSelect (user clicked the platform clear button) is not sent.
  This is correct optional-field behavior.

--------------------------------------------------------------------------------
CODE TYPES / DROPDOWNS
--------------------------------------------------------------------------------

LIMITATION #8 -- YES_NO codeTypeCategory not recognized; use YES_NO_UNKNOWN
  YES_NO results in an empty dropdown. YES_NO_UNKNOWN (NIBRS) is confirmed
  working; shows Y, N, U. U cannot be suppressed at the FormSelect level.
  If U must be excluded, switch to FormInput maxLength=1 (free text).

LIMITATION #9 -- Article Type dropdown requires codeTypeSource=CA_CLETS
  NCIC_ARTICLE_TYPE lives under codeTypeSource "CA_CLETS" in this system.
  Using codeTypeSource "NCIC" results in an empty dropdown.

LIMITATION #10 -- Firearm Make and Caliber: no platform code list confirmed
  No confirmed codeTypeSource/codeTypeCategory for GunMake or GunCaliber in NJ.
  Resolution: FormInput with maxLength from XML spec. Confirmed correct by FL_FCIC.

--------------------------------------------------------------------------------
ARCHITECTURE
--------------------------------------------------------------------------------

LIMITATION #11 -- Duplicate QUERYINPUTFORM cards if added to both ENTITIES and RMS bundles
  Adding QUERYINPUTFORM to the RMS bundle causes each entity form to render twice.
  Resolution: QUERYINPUTFORM belongs only in the ENTITIES bundle (provider=MARK43).

LIMITATION #19 -- keyReference must be unique within a QUERYINPUTDATAMAPPING
  Import error: "Duplicate key references found in query input data mapping."
  Each combination within a single QIDM must have a distinct keyReference.

================================================================================
RMS ELASTIC SEARCH LIMITATIONS
================================================================================

These limitations affect what data RMS receives and can filter on. All are
SERVER-SIDE LIMITATIONS unless noted. Full details in docs/NJ_NJCJIS_LIMITATIONS.txt.

--------------------------------------------------------------------------------
STATE FIELD
--------------------------------------------------------------------------------

LIMITATION #13 -- attributeTypeId=STATE always sends internal attribute ID
  Any FormSelect with attributeTypeId=STATE sends the platform's internal
  attribute ID (e.g., NJ=69509884952, PA=69509887513), not the 2-letter code.
  This is correct for RMS elastic search but breaks CommSys outbound XML.
  Do NOT map a field with attributeTypeId=STATE in QIDM -- it sends the ID
  in the outbound XML and the provider will reject or misinterpret the query.

LIMITATION #14 -- RMS elastic search fatals on VIN/OLN queries when state is plain text
  RMS recognizes fieldId=RegistrationState and expects an internal attribute ID.
  When the value is plain text (e.g., "NJ"), RMS throws a fatal local error and
  the query does not complete. Plate-only queries do not trigger this validation.
  Fix: dual-field pattern (LIMITATION #15).

LIMITATION #15 -- Dual-field state pattern required for NJ in-state forms
  Two hidden fields serve different consumers:
    Field 1: SelH  fieldId=RegistrationState   attributeTypeId=STATE  initialValue=NJ
             RMS reads this field by fieldId; receives attribute ID. NOT in QIDM.
    Field 2: InpH  fieldId=RegistrationStateNJ  initialValue=NJ
             QIDM sourceField; sends literal "NJ" to outbound XML <State>.
  OOS forms use codeTypeCategory=NJ_NIBRS_STATE which sends the 2-letter code
  to outbound XML but cannot serve RMS -- see LIMITATION #20.

LIMITATION #18 -- Query display summary shows internal attribute ID for hidden state field
  The ConnectCIC summary widget surfaces the raw value of any field with
  attributeTypeId. The hidden SelH (RegistrationState) always shows the
  attribute ID (e.g., 69509884952) instead of "NJ". No config fix available.
  SERVER-SIDE LIMITATION: requires platform summary aliasing or RMS accepting
  plain 2-letter codes. Functional impact: NONE. CommSys XML and RMS searches
  both work correctly.

LIMITATION #20 -- OOS RMS plate/VIN searches fire without state filter
  codeTypeCategory fields (NJ_NIBRS_STATE) send 2-letter codes; RMS elastic
  requires attribute IDs. attributeTypeId=STATE fields send attribute IDs but
  break CommSys outbound XML. No config mechanism can serve both consumers from
  a single user-selected field.
  Current behavior (v3.16+): RMS fires with plate/VIN tag only (no state filter).
  Officer confirms state visually. Outbound XML state is always correct.
  SERVER-SIDE LIMITATION: requires a platform-level conversion handler.

--------------------------------------------------------------------------------
SEX FIELD
--------------------------------------------------------------------------------

LIMITATION #21 -- useAttributeId=True does NOT convert code values to attribute IDs
  Tested v3.20: NIBRS_SEX codeTypeCategory sends "M" to RMS sexAttrId -> 400 error.
  useAttributeId=True only passes through an already-resolved attribute ID from
  an attributeTypeId field. It does NOT convert code strings ("M") to numeric
  attribute IDs (69509891711).
  CA_CLETS has no sex code categories (tested 2026-04-10, all 5 categories empty).
  The only working sex dropdown is codeTypeCategory=NIBRS_SEX, codeTypeSource=NIBRS.
  This sends correct "M"/"F"/"U" codes to CommSys XML but cannot feed RMS sexAttrId.
  Current behavior (v3.21+): sex attributes removed from RMS person QIDM.
  RMS person searches run without sex filter. Sex filters CommSys XML only.
  SERVER-SIDE LIMITATION: no config mechanism converts code values to RMS
  attribute IDs.

--------------------------------------------------------------------------------
RMS DL / PERSON SEARCH
--------------------------------------------------------------------------------

  RMS DL search fires on dlNumber only -- no state filter applied (server-side).
  Same root cause as OOS vehicle RMS state issue (LIMITATION #20): the OOS state
  field (codeTypeCategory=NJ_NIBRS_STATE) sends a 2-letter code; RMS expects an
  attribute ID. Cannot be served from a single user-selected field.
  Confirmed behavior: dlNumber search returns cross-state results; officer
  confirms state visually.

  RMS person name search (lastName, firstName, dateOfBirth) confirmed working
  when name path fires. DOB is reformatted MMDDYYYY -> YYYY-MM-DD by QIDM.

--------------------------------------------------------------------------------
RMS VEHICLE SEARCH PATCHES APPLIED (build script)
--------------------------------------------------------------------------------

  Patch 1 (v3.15): RMS licensePlateIn combination was missing RegistrationState
  in any[]. Without this, NJ plate searches omit state from the RMS elastic
  query. Fixed by adding RegistrationState to licensePlateIn any[].

  Patch 2 (v3.16): RMS licensePlateOutAndState combination required
  RegistrationStateOut in set[], but: (a) form uses fieldId=RegistrationStateOOS
  (name mismatch), and (b) NJ_NIBRS_STATE sends a 2-letter code, not an
  attribute ID (value type mismatch). Fixed by dropping state requirement from
  set[] -- OOS plate RMS fires on tag only.

  Patch 3 (v3.21): RMS person QIDM sex attributes (sexAttrId, sexAttrIds,
  useAttributeId) removed. NIBRS_SEX sends "M" code; RMS expects numeric
  attribute ID. useAttributeId=True confirmed NOT to perform code conversion.
  Sex removed from RMS QIDM permanently.

--------------------------------------------------------------------------------
RMS ARCHITECTURE
--------------------------------------------------------------------------------

LIMITATION #12 -- VehicleStolenQuery not registered server-side
  NJ_NJCJIS.xml defines only 5 transactions: ArticleSingleQuery, BoatQuery,
  DriverLicenseQuery, GunQuery, VehicleRegistrationQuery.
  VehicleStolenQuery is not registered. A QUERYINPUTDATAMAPPING cannot be built
  until the server registers the transaction. SERVER-SIDE LIMITATION.

================================================================================
PRODUCTION DECISION: NJ_NJCJIS
================================================================================

Selected approach: SPLIT (phase 08_split_entities, v3.x)
Reason: Cleaner officer UX; field isolation eliminates cross-contamination risk;
        split tabs are easier to test and document independently.
Non-split baseline archived: phases/prerelease/NJ_NJCJIS_v2.7_NONSPLIT_BASELINE_2026-04-10.json

DL exception: Name + OLN merged in one QIDM (both Person NJ and Person OOS tabs
share the DriverLicenseQuery QIDM) due to DQ combination isolation failure on
fully split DL configs (LIMITATION #2). Revisit with live connection.
