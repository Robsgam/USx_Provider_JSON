# SUPPRESSION-SCOPE: direction-aware
#   Opted in 2026-08-01. Without this marker a registry row suppresses EVERY check for its
#   (query, keyRef, field) triple regardless of what the recorded decision actually said -- so a row
#   granting "this field may ride in any[]" also silences the OPPOSITE defect (a field wrongly
#   promoted INTO set[]), and the gate goes mute somewhere it was never granted.
#   Narrowing is STRICTER and CAN turn a provider red by un-silencing a real finding. That is the
#   point: if it does, investigate the finding -- do NOT remove the marker.
#   Measured before/after opting in; result recorded in the commit.

# set/any divergence that is intentional and correct, so the gate treats it as [NOTE] not [FAIL].

THIS providers metadata permits no such thing: BOTH VIN variants require VehicleMakeCode in <Set>. QV{VehicleIdentificationNumber} = Set[VehicleIdentificationNumber, VehicleMakeCode] Any[FormORI, RelatedHitSearchIndicator], and RQ{VehicleIdentificationNumber} = Set[VehicleIdentificationNumber, VehicleMakeCode, VehicleYear] Any[FormORI, State..State5]. There is no looser variant. The built QV.V (set[VehicleIdentificationNumber, VehicleMakeCode]) matches QV{VIN} exactly and RQ.V matches RQ{VIN} exactly. METADATA IS FIELD-AUTHORITY, devdoc is QUERY-authority (KB rule B4), so VehicleMakeCode stays mandatory. Building a VIN-only combination would emit a request NO metadata variant accepts -- it would MANUFACTURE a wire-invalid request. Note this also means an officer must supply the make with a VIN on this provider, which is a real usability consequence of the metadata, not a build choice. VehicleRegistrationQuery | QV.V | VehicleYear | devdoc-optional-unreachable | Devdoc VehicleRegistrationQuery #2 lists VehicleYear as an optional on the VIN search, but THIS providers metadata scopes it to the OUT-OF-STATE transaction ONLY. QV{VehicleIdentificationNumber} = Set[VehicleIdentificationNumber, VehicleMakeCode] Any[FormORI, RelatedHitSearchIndicator] -- VehicleYear is NOT defined there at all. RQ{VehicleIdentificationNumber} = Set[VehicleIdentificationNumber, VehicleMakeCode, VehicleYear] Any[FormORI, State..State5] -- there it is MANDATORY. The build routes correctly on that split: RQ.V is gated RegistrationState EXISTS and carries the year, QV.V is gated RegistrationState NOT_EXISTS and does not. So an IN-STATE VIN search drops a typed year, and that is metadata-correct: adding VehicleYear to QV.V any[] would OVER-PERMIT, transmitting a field the QV transaction does not define. The devdoc presents one flat optional list for the query while the metadata spreads those optionals across two transactions -- the same shape as a Choice branch scoping a field to one alternative. METADATA IS FIELD-AUTHORITY (KB rule B4). Verified against the raw XML Requirements 2026-08-01. | metadata-vs-devdoc | 2026-08-01

DriverLicenseQuery | DL.NAME | Attention | demoted-to-any | ATTENTION IS SUPPLIED BY THE PLATFORM HANDLER, NOT BY THE OFFICER -- so any[] is the only wiring that can work, and the wire is NOT incomplete. Read from the raw XML <Requirements> of DriverLicenseQuery/QUERY, the sanctioned exception: <Set><Choice><Field OperatorLicenseNumber/><Set><Field SexCode/><Field BirthDate/><Field Name/></Set></Choice><Field PurposeCode/><Field Attention/><Any><Field State/><Field ImageIndicator/></Any></Set>. Attention is a SIBLING of the Choice inside the outer <Set>, so metadata makes it MANDATORY on BOTH alternatives -- audit_metadata is right that it is demoted. WHY set[] IS NOT AVAILABLE: Attention is auto-populated by CommsysGetLastNameFirstNameInitialRuleHandler, which derives "LASTNAME F" at SEND time; there is no officer-entered value at FORM time. Routing tests field PRESENCE, so putting Attention in set[] would demand a form value that never exists and BOTH DL combos would become permanently unsatisfiable -- two combos that look built and can never fire, which is strictly worse than the demotion (the AZ_AZDPS DQPN/DQP lesson). The handler is not a convenience: BUILD_RULES names Attention THE ONE STANDING EXCEPTION to the visible-first mandate (directive 2026-06-22), specifies exactly this attribute shape (size 30, sourceField Attention, targetField Attention, rule CommsysGetLastNameFirstNameInitialRuleHandler), and says to scope it to ONLY the query whose metadata lists Attention -- which here is DriverLicenseQuery and nothing else. THE FIELD DOES REACH THE WIRE, which is why this is a demotion on paper only: HI_HCJDC_OFML is LIVE-PROVEN on 9 of 9 DriverHistory wires carrying <Attention>SGAMBELLONE R</Attention> from any[] membership ALONE, with NO prefill and NO combo default (its earlier initialValue=X was shown never to be the gate-feeder its note claimed). NM v2.2 follows that exact shape: attribute + any[] membership + a HIDDEN feeder control so the sourceField has something to bind to, no prefill, no default. Verified after wiring: audit_wiring_closure 0 breaks across all ten classes (so the control is not orphaned and the requirement is not unfillable), validator 66 PASS / 0 FAIL / 0 WARN, audit_cad 62 PASS / 0 FAIL. NOTE FOR THE DEVDOC READER: NM devdoc combinations #1 and #2 list [Attention, PurposeCode] in SQUARE BRACKETS, i.e. OPTIONAL -- the devdoc and the metadata genuinely disagree here. Metadata wins on field requirements (Rob 2026-08-18: "meta data wins over dev doc built to the spec"), which is why PurposeCode was PROMOTED into set[] at v2.2 rather than left out, and why Attention is registered rather than dismissed as devdoc-optional. | metadata-vs-devdoc | 2026-08-18
