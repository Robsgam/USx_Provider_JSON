  *** THE <Choice> IS WHY THIS WAS INVISIBLE, AND MY FIRST READ OF THE XML WAS WRONG. *** A flat XPath
  dump of the Set showed one alternative and no OLN variant, which would have meant our DL.OLN combo
  had no metadata basis at all. Fidelity said "QUERY[alt1/2]" and "QUERY[alt2/2]" -- TWO alternatives --
  and that contradiction is what forced reading the <Combination> VERBATIM:
      <Set>
        <Choice>
          <Field OperatorLicenseNumber/>
          <Set><Field SexCode/><Field BirthDate/><Field Name/></Set>   <-- nested Set = mandatory GROUP
        </Choice>
        <Field PurposeCode/>          <-- SIBLING of the Choice, so mandatory on BOTH branches
        <Field Attention/>            <-- same
        <Any><Field State/><Field ImageIndicator/></Any>
      </Set>
    So the two alternatives are {OLN, PurposeCode, Attention} and {SexCode, BirthDate, Name,
    PurposeCode, Attention}. Both our combos were paired CORRECTLY and both genuinely lacked the same
    two fields -- one root cause behind 4 fidelity findings and the 1 query_trace MISSING. This is
    exactly the trap usx-build Step 1 documents: <Choice> POSITION is load-bearing, a nested <Set>
    inside a Choice is a mandatory GROUP, and METADATA_REFERENCE.txt flattens all of it away.

  THE DEVDOC AND THE METADATA GENUINELY DISAGREE HERE, AND METADATA WINS. NM devdoc combinations #1
  and #2 both list "[Attention, PurposeCode, State, State2..State5]" -- SQUARE BRACKETS, i.e. OPTIONAL.
  The metadata puts both INSIDE <Set>. Rob 2026-08-18: "meta data wins over dev doc built to the spec".
  So PurposeCode was PROMOTED to set[] rather than left out, and Attention was REGISTERED rather than
  dismissed as "the devdoc says it is optional anyway". Recording this because the devdoc bracket is a
  perfectly convincing reason to do nothing, and it is the wrong authority for a field requirement.

  WHY PurposeCode GOES IN set[] AND Attention CANNOT -- the distinction that matters:
    PurposeCode is OFFICER-SUPPLIED. It gets a visible control, so set[] membership is satisfiable.
    Prefilling 'C' is SAFE here for the CA_CLETS reason, not by luck: it is mandatory in BOTH
    alternatives, so satisfying it equally for both cannot shadow one path over the other
    (audit_prefill_shadow: 14 ordered pairs, 0 FAIL). 'C' is NOT authority-derived -- the devdoc gives
    no value list for it -- it follows Rob's standing fallback ("use c for purpose code if you cannot
    find it", OH_LEADS 2026-08-18). If NMLETS rejects it, change the VALUE, not the routing.
    Attention is PLATFORM-SUPPLIED. CommsysGetLastNameFirstNameInitialRuleHandler derives "LASTNAME F"
    at SEND time; there is no officer value at FORM time. Routing tests PRESENCE, so set[] membership
    would demand a form value that never exists and BOTH DL combos would be permanently unsatisfiable
    -- two combos that look built and can never fire, which is strictly worse than the demotion (the
    AZ_AZDPS DQPN/DQP lesson). Hence any[] + handler, and a registry row that says so.
