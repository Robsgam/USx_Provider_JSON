SECTION 1 -- TRANSACTIONS IN DEVDOC NOT IN METADATA (or field-level mismatches)
================================================================================

  GunQuery -- RESOLVED (new MetaData received 2026-04-13)

  Previous state: DevDoc documented GunQuery with GINQ. Old MetaData had no standalone
  GunQuery transaction; only BEPStolenGunCancel/Entry/Clear with a different field structure.
  Old MetaData fields: FirearmCategoryCode (M), GunSerialNumber (M), ReasonCode (M),
  MiscellaneousDescriptiveText (O), PersonPropertyInSightIndicator (O).

  Resolution: New MetaData v8 and new DevDoc now agree:
    GunSerialNumber (M, 20) -- required
    GunCaliber (O, 4)       -- optional, NCIC code
    GunMake (O, 23)         -- optional, NCIC code
    RelatedHitSearchIndicator (O, 1) -- optional, Y or blank
  Combination: keyRef=GINQ -- set=[GunSerialNumber], any=[GunCaliber, GunMake, RelatedHitSearchIndicator]
  Build action: GunQuery rebuilt v1.7 per new MetaData and DevDoc.
  Remaining open: standalone GINQ transaction not confirmed in MetaData as a queryable
  transaction type; vendor confirmation needed before live testing.

================================================================================
SECTION 2 -- METADATA MESSAGEKEY CONFLICTS (BASIC QUERIES SCOPE)
================================================================================

  Two keyReferences are shared between BoatQuery and VehicleRegistrationQuery:

    RVEH -- BoatQuery (in-state registration path) and VehicleRegistrationQuery
            (in-state / OOS plate path)
    RCAR -- BoatQuery (NY hull path) and VehicleRegistrationQuery (NY VIN path)

  Impact: Platform behavior when RVEH or RCAR fires is ambiguous if both transactions
  are active. Platform may disambiguate by targetEntity (Vehicle vs. Boat); this is
  unconfirmed. Monitor for routing conflicts during BoatQuery live testing.
  Vendor question raised in GAPS_SUMMARY item #3.

BoatQuery
------------------------------------------------------------------------

  Fields
    DevDoc  : BoatHullIdNumber (C,20), ImageIndicator (O,1),
              RegistrationNumber (C,10), State (C,2)
    MetaData: All four fields defined -- sizes match

  Combinations
    DevDoc  : 1. (In)  BoatHullIdNumber [ImageIndicator]
              2. (In)  RegistrationNumber [ImageIndicator]
              3. (Out) BoatHullIdNumber, State [ImageIndicator]
              4. (Out) RegistrationNumber, State [ImageIndicator]
    MetaData (v8):
              keyRef=BVIN -- set=[BoatHullIdNumber], any=[ImageIndicator]          (In)
              keyRef=RVEH -- set=[RegistrationNumber], any=[ImageIndicator]        (In) *shared*
              keyRef=RCAR -- set=[BoatHullIdNumber], any=[ImageIndicator]          (Out) *shared*
              keyRef=BVEH -- set=[RegistrationNumber, State], any=[ImageIndicator] (Out)

  Inconsistencies:
    1. DevDoc defines one transaction; MetaData distributes across 4 keyRefs.
       Build decision: 4-combination structure per MetaData.
    2. RCAR (out-of-state hull path) -- State not in set[]; DevDoc requires State for Out.
       Build decision: follow MetaData (no State on RCAR); flag to vendor (GAPS_SUMMARY #4).
    3. RVEH and RCAR are shared with VehicleRegistrationQuery (see Section 2).

DriverHistoryQuery
------------------------------------------------------------------------

  Fields
    DevDoc  : BirthDate (C,8), ImageIndicator (O,1), Name (C,35),
              NyNyspinTransactionName (O,4), OperatorLicenseNumber (C,20),
              PurposeCode (C,1), Requestor (C,35), SexCode (C,1), State (C,2)
    MetaData (v8): BirthDate, ImageIndicator, Name, OperatorLicenseNumber, SexCode,
              State -- sizes match
              NyNyspinTransactionName (O,4) -- present in MetaData Choice structure
              PurposeCode (C,1)  -- present in MetaData Choice structure (Out path)
              Requestor (C,35)   -- present in MetaData Choice structure (Out path)

  Combinations
    DevDoc  : 1. (In)  BirthDate, Name, SexCode [ImageIndicator, NyNyspinTransactionName]
              2. (In)  OperatorLicenseNumber [ImageIndicator, NyNyspinTransactionName]
              3. (Out) BirthDate, Name, SexCode, State, PurposeCode, Requestor
                       [ImageIndicator, NyNyspinTransactionName]
              4. (Out) OperatorLicenseNumber, State, PurposeCode, Requestor
                       [ImageIndicator, NyNyspinTransactionName]
    MetaData (v8): keyRef=DALL
              OLN combination  : Choice([OLN], [OLN+PurposeCode+Requestor+State])
                                 plus any[ImageIndicator, NyNyspinTransactionName]
              Name combination : Choice([Name+DOB+SexCode], [Name+DOB+SexCode+PurposeCode+
                                 Requestor+State])
                                 plus any[ImageIndicator, NyNyspinTransactionName]

  Inconsistencies:
    1. In/Out distinction -- DevDoc distinguishes 4 combinations; MetaData uses Choice
       structure where Out fields (PurposeCode, Requestor, State) are required only when
       the Out Choice branch is selected.
       Build decision: 4 QIDMs (_OLN/_Name x Person-NY/Person-OOS forms). Person-NY form
       enforces In-state path; Person-OOS form exposes PurposeCode, Requestor, State.
       LIMITATION #2 risk: platform evaluates only ONE QIDM per (Person, DriverHistoryQuery).
       Vendor question raised in GAPS_SUMMARY #1.
    2. State optionality on Out path -- DevDoc requires; MetaData Choice branch requires
       on Out but optional otherwise.
       Build decision: Person-OOS form presents visible State selector (enforces intent at UI).

       with State always optional.
       Build decision: 2 QIDMs (_OLN/_Name) matching MetaData. Person-NY and Person-OOS
       forms separate in-state and out-of-state presentation.

VehicleRegistrationQuery
------------------------------------------------------------------------

  Fields
    DevDoc  : ImageIndicator (O,1), LicensePlateNumber (C,10),
              LicensePlateTypeCode (C,2), LicensePlateYear (C,4), State (C,2),
              VehicleIdentificationNumber (C,20), VehicleMakeCode (O,4), VehicleYear (O,4)
    MetaData (v8): All eight fields defined -- sizes match

  Combinations
    DevDoc  : 1. (In)  LicensePlateNumber [ImageIndicator, LicensePlateTypeCode]
              2. (In)  VehicleIdentificationNumber [ImageIndicator]
              3. (Out) LicensePlateNumber, LicensePlateTypeCode, LicensePlateYear, State
                       [ImageIndicator]
              4. (Out) VehicleIdentificationNumber, State [ImageIndicator, VehicleMakeCode,
                       VehicleYear]
    MetaData (v8):
              keyRef=RVEH -- set=[LicensePlateNumber], any=[ImageIndicator]            *shared*
              keyRef=RCAR -- set=[VehicleIdentificationNumber], any=[ImageIndicator]   *shared*
              keyRef=RVIN -- set=[VehicleIdentificationNumber, State],
                             any=[ImageIndicator, VehicleMakeCode, VehicleYear]

  Inconsistencies (v1.11 build):
    1. State on Out paths -- DevDoc requires State on combinations 3 and 4; MetaData has
       State in RVEH any[] (optional) and RVIN set[] (required).
       Build decision: RVEH fires on LicensePlateNumberIn (shared fieldId); State optional.
       RVIN fires when VehicleIdentificationNumber + RegistrationStateOOS both populated.
       Live test T3 confirmed: OOS plate fires RVEH with plate only, no State in XML --
       correct per DevDoc Choice option 1 (plate alone is sufficient for in-state path;
       Choice option 2 adds TypeCode+Year+State for OOS -- NYSPIN server-side routing).
    2. LicensePlateYear / LicensePlateTypeCode -- DevDoc requires both on Out plate path
       (combination 3). MetaData does not include them in RVEH set[].
       Build decision: follow MetaData; both fields available on form as optional.
    3. RVEH and RCAR shared with BoatQuery -- see Section 2.

  v1.11 build note (LIMITATION #2 fix):
    VehicleRegistrationQuery_NY and _OOS were originally split configs. Live testing
    confirmed platform evaluates only ONE QIDM per (targetEntity, query) -- _OOS was
    never evaluated. Fix: merged into single QIDM. Both Vehicle-NY and Vehicle-OOS entity
    forms use fieldId 'LicensePlateNumberIn' for plate. One RVEH combination covers both.
