CROSS-REFERENCE: CA_CLETS PATTERNS
===================================

CA_CLETS DriverLicenseQuery built combos:
  IN.L1     DMV by Name       set[CaPurpose, Name]                any[DOB]
  NLTS.DQ   Nlets by OLN      set[CaPurpose, OLN, State]          (none)
  ID.L1     DMV by OLN         set[CaPurpose, OLN]                 (none)

Contra Costa equivalents:
  INL1  ≈ CA_CLETS IN.L1   (DMV by Name)     — MATCH (same pattern, different keyRef name)
  DQ    ≈ CA_CLETS NLTS.DQ (Nlets by Name)   — PARTIAL (Contra Costa requires Name+DOB+Sex,
                                                 CA_CLETS uses OLN. Both require State.)
  DNQ   — NO CA_CLETS equivalent             — NEW (Nlets Name-only, no DOB required)
  IR.QVC — CA_CLETS has this but SKIPPED      — Contra Costa builds what CA_CLETS deferred
  IW.N   — CA_CLETS has no JAWS queries       — Contra Costa-specific

KEY DIFFERENCES FROM CA_CLETS:
  1. NO OperatorLicenseNumber — not in any transaction. All queries are by Name.
  2. NO Vehicle queries — no VehicleRegistrationQuery, no VehicleStolenQuery
  3. NO Boat/Gun/Article queries — Person entity only
  4. NO DriverHistoryQuery — no KQ/DH transaction
  5. RequestingAgencyId required on ALL combos — unique to Contra Costa
  6. Age field present — alternative to BirthDate in IR.QVC and INL1
  7. Address/AddressCity fields — not in CA_CLETS basic DL queries
  8. Choice construct in IR.QVC — BirthDate OR Age, not seen elsewhere

  1. CaContraCostaJawsWarrantQuery  — IN METADATA ✓
  2. CaContraCostaJawsPersonQuery   — IN METADATA ✓

CLETSPersonSuperQuery devdoc combos (3):
  1. (In/Out) OperatorLicenseNumber
  2. (In/Out) Name, SexCode, Age
  3. (In/Out) Name, SexCode, BirthDate, [State]

This is the ONLY transaction with OLN queries. It exists in CA_CLETS
metadata (as a separate transaction) but is ABSENT from the Contra
Costa metadata XML. Since metadata is bible, this transaction is NOT
buildable until the XML is updated to include it.

If/when CLETSPersonSuperQuery is added to metadata, it would add:
  - OLN-based driver queries (the missing query path)
  - An additional 3 combos bringing total to 9


COMBO PRIORITY ANALYSIS (for build ordering)
=============================================
Combo ordering must be most-specific first. Analyzing field overlap:

  Combo    Required fields (set[])                  Specificity
  -------  ---------------------------------------- -----------
  DQ       CaPurpose+Name+DOB+Sex+State+ReqAgId     6 fields (MOST)
  DNQ      CaPurpose+Name+State+ReqAgId             4 fields + any[]
  IR.QVC   CaPurpose+Name+ReqAgId+Choice(DOB|Age)   4 fields + any[]
  INL1     CaPurpose+Name+ReqAgId                   3 fields + any[]
  IW.N     Name+ReqAgId                             2 fields + any[]

Recommended combo order in QIDM:
  1. DQ       (most specific — 6 set[] fields, no any[])
  2. DNQ      (4 set[] + State — OOS only)
  3. IR.QVC   (4 set[] with Choice — in-state multipurpose)
  4. INL1     (3 set[] — in-state DMV)
  5. IW.N     (2 set[] — lightest, catches everything else)

STATE ROUTING:
  - DQ and DNQ require State → OOS queries (Nlets)
  - IR.QVC, INL1, IW.N do NOT require State → in-state queries
  - Same DQ/FDQ pattern as FL_FCIC: State presence differentiates
    OOS (DQ/DNQ) from in-state (IR.QVC/INL1/IW.N)
  - MC layout will be needed to isolate State-required vs
    State-absent combos for full path coverage (same finding as FL)
