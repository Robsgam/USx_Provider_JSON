================================================================
  NEW PROVIDER ONBOARDING PROCEDURE
  Last updated: 2026-05-14
================================================================

This document describes the end-to-end steps for introducing a new
ConnectCIC provider into the USx_Provider_JSON monorepo. It reflects
the current build architecture: 3 shared modules, KB-based RMS,
no external template dependencies.

Prerequisites:
  - Metadata XML file from the provider (e.g., WA_WACIC.xml)
  - CommSys devdoc PDF (optional but strongly preferred)
  - Access to this monorepo

================================================================
  PHASE 0 — SCAFFOLD
================================================================

0.1  NAMING
     Open the metadata XML. The provider folder name MUST match the
     XML filename minus .xml. Example: NM_NMLETS_OFML.xml -> NM_NMLETS_OFML.
     Mismatched names require renaming 10+ files later.

0.2  RUN new_provider.ps1
     powershell -ExecutionPolicy Bypass -File tools\new_provider.ps1 `
       -XmlPath "C:\path\to\PROVIDER.xml" -PdfPath "C:\path\to\PROVIDER.pdf"

     This creates:
       providers/<PROVIDER>/
         docs/        (STATUS.txt, BUILD_NOTES.txt, SQVR.txt, JSON_INVENTORY.md)
         docs/base/   docs/mc/
         scripts/     (build stubs for BASE + MC)
         source/      (copies XML + PDF)
         tests/       phases/base/  phases/mc/  release/

0.3  EXTRACT METADATA REFERENCE
     powershell -ExecutionPolicy Bypass -File tools\extract_metadata_reference.ps1 `
       -XmlPath providers\<PROVIDER>\source\<PROVIDER>.xml -OutFile providers\<PROVIDER>\docs\<PROVIDER>_METADATA_REFERENCE.txt -All

     This generates the authoritative field definitions, combo requirements,
     and coverage report. Use this file (not raw XML) for all field questions.

0.4  READ DEVDOC
     The devdoc "Basic Queries Supported" section is the ONLY authority
     for which queries to build. Metadata existence != authorization.
     Identify: supported entities, query types, field constraints, date
     formats, state-specific behaviors.

================================================================
  PHASE 1 — BASE BUILD (single-card, proof of concept)
================================================================

1.1  REPLACE BUILD SCRIPT STUB
     The scaffold creates a TODO stub. Replace it with a real build script.
     Every build script follows the same structure:

     --- Header ---
     param / version / paths / $currentYear

     --- Dot-source shared modules ---
     . "$PSScriptRoot\..\..\..\tools\_build_rms_bundle.ps1"
     . "$PSScriptRoot\..\..\..\tools\_build_layout_helpers.ps1"
     . "$PSScriptRoot\..\..\..\tools\_build_provider_helpers.ps1"

     --- BUNDLE 1: PROVIDER ---
     $auth    = Build-Auth -ProviderName '<PROVIDER>'
     $results = Build-ProviderQrdm -ProviderName '<PROVIDER>'
     $qmf     = Build-Qmf -ProviderName '<PROVIDER>'
     <QIDM definitions — one per query type>

     $providerBundle = [PSCustomObject]@{
         configurations = @($auth, $results, $qmf, $vehRegQuery, $dlQuery, ...)
         description    = "Provider configuration for <PROVIDER> v${Version}"
         name           = '<PROVIDER>'
         type           = 'BUNDLE'
         provider       = '<PROVIDER>'
     }

     --- BUNDLE 2: ENTITIES ---
     <QIF layout definitions using MakeLayouts, Inp, Sel, Dt, InpH, SelH>

     $entitiesBundle = Build-EntitiesBundle -Configurations @($vehicleForm, $personForm, ...)

     --- BUNDLE 3: RMS ---
     $rmsBundle = Build-RmsBundle              # standard
     $rmsBundle = Build-RmsBundle -KeepSsn     # if SSN attr needed (MC only)
     $rmsBundle = Build-RmsBundle -SkipRace    # if provider doesn't support race

     --- OUTPUT ---
     $output = [PSCustomObject]@{ bundles = @($entitiesBundle, $providerBundle, $rmsBundle) }
     Write-ProviderJson -BundleObject $output -OutPath $OUT `
         -PhasePath $VEROUT -Label "Built <PROVIDER> v${Version}"

1.2  QIDM CONSTRUCTION RULES
     - Read METADATA_REFERENCE.txt for field definitions and combo requirements
     - One QIDM per query type (merge when all keyRefs are distinct)
     - If duplicate keyRefs in metadata: invent distinct ones (e.g., QA -> QA.S, QA.N)
     - Combination ordering: most-specific (most set[] fields) FIRST
     - set[] = fields the officer MUST fill; any[] = fields platform ignores for matching
     - initialValue fields go in any[], not set[] (platform ignores defaults for set eval)
     - state = 'In/Out' on all CommSys QIDMs
     - DL+DH on same entity: use DH-suffix fieldIds, queriesToDeselect (one-directional)
     - Date fields: CommsysParseDateRuleHandler with provider-specific format
     - Name fields: FormatStringRuleHandler with composite sourceField
     - State field: NCIC pattern preferred (attributeTypeId='STATE', codeTypeProvider='NCIC')
     - ImageIndicator: size=1, initialValue='Y' (or 'N' for vehicle), in set[] or any[]
     - All visible fields must be exposed as FormInput/FormSelect/FormDate first
     - Do NOT use CommsysGetLastNameFirstNameInitialRuleHandler on Attention (add visible field)

1.3  QIF LAYOUT RULES
     - Phase 1: single card per entity, all fields on one card
     - Use shared helpers: Inp (visible input), InpH (hidden input), Sel (visible select),
       SelH (hidden select), Dt (date), MakeLayouts (builds all 3 layout variants)
     - PlateType: initialValue='PC'. PlateYear: initialValue=$currentYear
     - No State initialValue when provider has separate in-state vs OOS keyRefs
     - fieldId must be camelCase for CAD auto-populate
     - Same fieldId on multiple cards = Internal Server Error (use OPTIONS card pattern)

1.4  PROVIDER-SPECIFIC FLAGS
     Check these against metadata + devdoc:
       - -SkipRace on Build-RmsBundle if provider doesn't support race attribute
       - -KeepSsn on Build-RmsBundle (MC only) if SSN search supported
       - Build-Auth -ExtraAttributes/-ExtraAny if provider needs non-standard AUTH fields
       - Build-EntitiesBundle -DefaultOrder if Person-first instead of Vehicle-first
       - No State initialValue if separate in-state/OOS keyRefs (LIMITATION #30)
       - CaRequestPurposeCode if California provider (visible Inp, not InpH)
       - purposeCodeDH if DH queries present (FormInput maxLength=1, initialValue=C)

1.5  RUN BUILD + REPORT
     powershell -ExecutionPolicy Bypass -File providers\<PROVIDER>\scripts\build_<provider>.ps1
     powershell -ExecutionPolicy Bypass -File tools\build_report.ps1 -Path providers\<PROVIDER>\<PROVIDER>_BASE.json

     build_report.ps1 runs 8 checks:
       1. validate.ps1          (structural: encoding, bundles, QIF types, QIDM refs, combos)
       2. render_layout.ps1     (layout tree)
       3. test_commsys.ps1      (combo fire simulation)
       4. report_picklists.ps1  (dropdown audit)
       5. render_html.ps1       (visual HTML report)
       6. verify_build.ps1      (banned patterns, fieldId consistency)
       7. audit_metadata.ps1    (QIDM vs XML metadata alignment)
       8. audit_cad.ps1         (CAD dispatch field alignment)

     TARGET: 0 FAIL / 0 WARN. Fix all before proceeding.

1.6  GATE 1 — COMMIT
     git add providers/<PROVIDER>/
     git commit -m "Add <PROVIDER> v1.0 BASE — <N>P/0F/0W"
     git push

================================================================
  PHASE 2 — MC BUILD (multi-card, production)
================================================================

2.1  CREATE MC BUILD SCRIPT
     Same structure as BASE with these differences:
       - Multi-card layout: one card per search path + shared OPTIONS card
       - Cross-entity combos (e.g., vehicle by owner name on separate card)
       - PascalCase fieldIds in MC where applicable (MC-specific sourceField casing)
       - DH-suffix hidden fields on separate hidden card
       - CAD_DISPATCH and FIRST_RESPONDER context cards (automatic via MakeLayouts)

2.2  MC-SPECIFIC RULES
     - Fields shared by multiple combos -> OPTIONS card (avoid duplicate fieldId ISE)
     - Each combo path gets its own card with a descriptive title
     - Combo ordering same as BASE (most-specific first)
     - -KeepSsn allowed on MC Build-RmsBundle (never on BASE)
     - Version number must match BASE (no -mc suffix)

2.3  RUN BUILD + REPORT (same as 1.5, targeting MC JSON)

2.4  GATE 2 — COMMIT
     git add providers/<PROVIDER>/
     git commit -m "Add <PROVIDER> v1.0 MC — <N>P/0F/0W"
     git push

================================================================
  PHASE 3 — DOCUMENTATION + CROSS-CHECK
================================================================

3.1  UPDATE PROVIDER DOCS
     - STATUS.txt: update phase, scores, test matrix
     - BUILD_NOTES.txt: log version with CHANGED/REASON
     - JSON_INVENTORY.md: add both BASE and MC entries
     - SQVR.txt: mark all queries [PENDING]

3.2  GENERATE TEST MATRIX
     powershell -ExecutionPolicy Bypass -File tools\build_report.ps1 -Path providers\<PROVIDER>\<PROVIDER>_BASE.json
     This generates docs/base/TEST_MATRIX.txt. Repeat for MC.

3.3  UPDATE CLAUDE.md
     Add provider to the Provider Status table with version, scores, and notable patterns.
     Or run: powershell -ExecutionPolicy Bypass -File tools\sync_provider_table.ps1

3.4  CROSS-PROVIDER AUDIT
     powershell -ExecutionPolicy Bypass -File tools\audit_cross_provider.ps1
     Verify new provider is consistent with existing providers on:
       - Default values (PlateType=PC, PlateYear=current, ImageIndicator=Y)
       - Field types (FormInput vs FormSelect must match across all providers)
       - queryLabel values (standard labels from CLAUDE.md)
       - Code type pairings (NCIC_LICENSE_PLATE_TYPE, NIBRS_SEX, etc.)

3.5  ENFORCE GATE
     powershell -ExecutionPolicy Bypass -File tools\enforce.ps1 -Provider <PROVIDER>
     Must exit 0. Checks: build freshness, validator scores, doc sync, cross-provider,
     repo integrity. Cannot declare done without this.

3.6  FINAL COMMIT + PUSH
     git add -A && git commit -m "Complete <PROVIDER> v1.0 onboarding" && git push

================================================================
  PHASE 4 — LIVE TESTING (when work order reaches this provider)
================================================================

4.1  PRE-TEST: create test log stubs
     powershell -ExecutionPolicy Bypass -File tools\new_test_log.ps1 -Provider <PROVIDER> ...

4.2  IMPORT SEQUENCE
     Import BASE first (proof of concept). If 0 FAIL, import MC.
     Test NCIC state pattern (ST-1) on first import of any new provider.

4.3  8-PHASE TEST MATRIX (per TESTING_REQUIREMENTS.txt)
     T1-T3:   Render + picklists + basic combos (one field at a time)
     T4-T10:  Each ANY field individually
     T11-T15: All ANYs together
     T16-T20: OOS queries (if applicable)
     T21-T30: Priority routing + cross-QIDM co-fire
     T31-T47: Negatives (missing required fields, wrong field types)

4.4  POST-TEST: save results immediately
     powershell -ExecutionPolicy Bypass -File tools\post_test.ps1 -Provider <PROVIDER> ...

================================================================
  SHARED MODULE REFERENCE (what you DON'T write per provider)
================================================================

The following are handled by shared modules. Do NOT duplicate inline.

  _build_rms_bundle.ps1:
    Build-RmsBundle [-KeepSsn] [-SkipRace]  — complete RMS bundle (AUTH, QMF, QIDM x2, QRDM, layout)
    Build-CommsysQrdm -ProviderName <name>  — CommSys QRDM for PROVIDER bundle

  _build_layout_helpers.ps1:
    N, Inp, InpH, Sel, SelH, Dt             — field/node constructors
    BuildMultiCardLayout                     — multi-card layout engine
    AddCadNodes, AddFrNodes                  — CAD/FR context cards
    MakeLayouts                              — builds all 3 layout variants

  _build_provider_helpers.ps1:
    Build-Auth -ProviderName [-ExtraAttributes] [-ExtraAny]
    Build-Qmf -ProviderName
    Build-ProviderQrdm -ProviderName
    Build-EntitiesBundle -Configurations [-DefaultOrder] [-CadOrder] [-FrOrder]
    Write-ProviderJson -BundleObject -OutPath [-PhasePath] [-Label]

  What each provider script IS responsible for:
    - QIDM definitions (attributes, combinations, query routing)
    - QIF layout definitions (which fields on which cards)
    - Provider-specific flags (-KeepSsn, -SkipRace, entity order)
    - Assembling the 3 bundles into $output

================================================================
  COMMON PITFALLS
================================================================

  1. keyReference not keyRef — wrong property name silently nulls, import rejects
  2. Duplicate fieldId across cards = Internal Server Error — use OPTIONS card
  3. initialValue on State field changes combo routing — omit when in-state/OOS split
  4. Bidirectional queriesToDeselect causes error popup — use one-directional only
  5. CommsysGetLastNameFirstNameInitialRuleHandler without visible field = hidden automation
  6. ENTITIES bundle must be FIRST in bundles array — forms don't render otherwise
  7. Platform ignores initialValue for set[] combo evaluation — put defaulted fields in any[]
  8. LicensePlateNumberIn is BANNED — use licensePlateNumber; only valid in QRDM rename map
  9. FormSelect must have correct codeTypeCategory/codeTypeSource — empty dropdown otherwise
  10. Run build_report.ps1 after EVERY build — never import without 0 FAIL
